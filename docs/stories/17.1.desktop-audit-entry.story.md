### The design

**1. Where the row is written.** In `finalize_document` (`core/document_processor.py:2015-2073`), the one function both desktop review paths end in (`finalization_worker.py:121`, `batch_worker.py:460`; no other caller in the app, `grep "finalize_document(" gdpr_pseudonymizer/gui`). The success row goes right after `write_file` (`:2058`), on the same database session (`ctx.audit_repo`) and through the same `_log_success_operation` as `process_document` (`:2139-2143`). Nothing else in the app calls `finalize_document`, so a path that logs today cannot log twice:
- desktop batch without review calls `process_document` (`batch_worker.py:330`);
- CLI `process` and `batch` call `process_document` (`cli/commands/process.py:219`, `cli/commands/batch.py:126`, `:620`).

Every call writes exactly one row: success, or the failure row of its `except` (`:2072-2073`).

**2. How the input file and the model version reach it.** Three new keyword parameters of `finalize_document`, last, with defaults:
- `input_path: str = ""`, the input document;
- `model_version: str | None = None`, the version of the model that detected the document (None: the processor's own, `_get_model_version()`);
- `detection_seconds: float = 0.0` (point 4).
- **Desktop single.** `DetectionWorker` reads the version from its own processor after it detected, through a new read-only property `DocumentProcessor.model_version` (it returns `_get_model_version()`). It hands the version on in a new `DetectionResult` field, `model_version: str = ""`. The review screen passes it to `FinalizationWorker` (`validation.py:1183-1192`) with the result's `input_file` (already passed, `:1189`) and its `detection_time_seconds`. `FinalizationWorker` passes them on to `finalize_document`.
- **Why not the finalize processor's own version.** `FinalizationWorker` builds a fresh processor (`:108`) that never detected, so its version reads `fr_not_loaded-unknown` (PM and SM). Asking it to detect would load spaCy a second time (seconds, several hundred MB), which the epic rules out.
- **Desktop batch with review.** The batch's processor detects and finalizes (`batch_worker.py:278`, `:421`, `:460`), so its own version is right. `_process_with_validation` passes `input_path=str(file_path)` and `detection_seconds`, and no `model_version`.

**3. The failure rows, equal to the CLI's.** They go through the CLI's `_handle_processing_error` (`:1888-1910`), then `_log_failed_operation` (`:2439-2471`). That gives the same sanitized error, `entity_count` 0 and the same « cannot open the database: application log only » rule (`:2469-2471`).
- **The write fails** (desktop single, desktop batch with review). `finalize_document`'s `except` passes `input_path` and `model_version` instead of `""` (`:2073`), so today's `[""]` row becomes the CLI's row; it is replaced, never added to. `_handle_processing_error` and `_log_failed_operation` get the same optional `model_version: str | None = None` as `_log_success_operation`. On None they read the processor's own version, so every CLI call is unchanged.
- **Desktop single: the read or detection fails.**
  - `DetectionWorker` names its processor before the `try` (`processor = None`, `:163`).
  - In both its `except` branches (`:197`, `:211`) it first calls `processor._handle_processing_error(e, self._file_path, "", start_time)` when the processor exists, then shows the message it shows today.
  - The version is its own processor's: `fr_not_loaded-unknown` if the read failed, the loaded one if detection failed after the model loaded, as on the CLI.
- **Desktop batch with review: the read or detection fails.**
  - `_process_with_validation` wraps its two lines (`:420-421`, kept as they are) in `try`/`except Exception`.
  - The `except` calls `processor._handle_processing_error(e, str(file_path), str(output_file), detect_start)` and re-raises.
  - The run loop's `except` blocks (`:368`, `:376`) then count and show the failure exactly as today, and write nothing.
- **No row, as today and as on the CLI:**
  - a wrong passphrase: refused before any analysis (`detection_worker.py:113-125`, `batch_worker.py:242-251`), and `_log_failed_operation` could not open the database either;
  - a database that cannot be created; a processor that cannot be built;
  - a review stopped or cancelled before the write (desktop single: no finalize; batch: `_process_with_validation` returns None, `:445-449`);
  - previews that fail (non-fatal, `detection_worker.py:249-253`: the document still goes to the review).
- **Never a second row.** `FinalizationWorker`'s `if not result.success` (`:135-138`) and `except` (`:127-133`) log nothing. Neither do `_run_batch`'s `else` branch (`:361-366`) and `except` blocks (`:368-382`). The mutants of Test Plan pin each one.

**4. What `processing_time_seconds` means on the desktop** (the SM's choice; the epic leaves it to the SM, Lionel's approval not needed).
- **The rule.** It is the time the app spent working on the document: its analysis plus its finalize, without the time the review was open.
  - Desktop single: `DetectionResult.detection_time_seconds` (the analysis, from `DetectionWorker`'s start, `:104`, to the review shown, `:264`), plus `finalize_document`'s own clock up to the row.
  - Desktop batch with review: from just before the read to the end of detection (`detect_start`, in `_process_with_validation`), plus the finalize.
  - A failure row counts the same way, up to the failure.
- **Why.**
  - The architecture defines the field as performance tracking: `processing_time_seconds: float - Performance tracking (NFR1-2 validation)` [Source: architecture/4-data-models.md#Operation, l.73]; "Performance analytics (average processing time…)" [Source: architecture/audit-logging.md#Overview].
  - The time a person keeps the review open is not the app's performance, and the desktop gives no bound on it: the review stays open while the user moves between documents.
  - It keeps the desktop rows comparable with the desktop batch without review, which has no review (`process_document`, read to write).
- **How it is carried.** `finalize_document` starts the row's clock `detection_seconds` before its own start (`audit_start = start_time - detection_seconds`). The `ProcessingResult` it returns keeps its finalize-only `processing_time_seconds` (`:2060`), which the results screen shows (`results.py:204`). The numbers on screen do not change. On a failed write, the `ProcessingResult` that `_handle_processing_error` returns now carries `input_file` and a time counted from `audit_start`; no screen reads either on a failure (`finalization_worker.py:135-138` and `batch_worker.py:361-366` read `error_message` only).
- **Harmless for `stats`:** `gdpr-pseudo stats` never reads the field (`cli/commands/stats.py:103-109` counts rows), the database screen reads only the timestamp (`database_worker.py:155-168`), and `AuditRepository.get_average_processing_time` has no caller in the app (PO, `grep`).
- **What differs from the CLI.** The CLI's clock starts before the read and stops after the write, so its row includes the human review (PM: 11.1 s with review, 3.1 s without). The batch summary's per-document time (`DocumentResult.processing_time`, `batch_worker.py:340`, `:347`) still includes the review; this story does not change it.

**5. What the row holds** (each field as the CLI's, the epic's Scope):
- `operation_type` PROCESS;
- `files_processed` `[input path]` (never the temporary output, `finalization_worker.py:97-99`);
- `model_name` the processor's (`"spacy"`, the default on all three processors);
- `model_version` as point 2;
- `theme_selected`;
- `entity_count` = `len(validated_entities)`, every entity sent, written or not (Lionel's Q5, Story 15.1);
- `processing_time_seconds` as point 4;
- `success`, `error_message` sanitized or None, `user_modifications` None.

The path is what the desktop was given: the absolute path the file dialog returns, or the batch's file path. The CLI writes the path it was given.
