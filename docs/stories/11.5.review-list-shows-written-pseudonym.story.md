## Story

**Decided by Lionel, 2026-11-10** (word for word): "indeed, if i knew it was systematic, i wouldn't have accepted it. as usual, i don't care if it's old, i want it fixed. so i pick option number one". What he chose: the pseudonym shown in the review is kept when the document is written, if it is still free at that moment; otherwise another one is drawn and the user is told which pseudonym changed and to what.

**As a** user who reviews a document in the desktop app or the command line,
**I want** these things:
- the pseudonym shown next to each name in the review list to be the one written in the document and saved;
- when I change a name's type, or set a custom pseudonym that another listed name must share, the list to update at once (desktop);
- when a pseudonym shown can no longer be used at the end, to be told which one changed and to what;
- the list never to show, as a pseudonym, a name of the document;

**so that** what I approve is what I get.

### Context

#### The list shows a throw-away draw

For every name not yet stored, the review list shows a pseudonym from a draw that is thrown away. Finalization then draws again. So the pseudonym shown is written only by chance.

**Desktop:**
- `DetectionWorker` calls `build_pseudonym_previews` (`gui/workers/detection_worker.py:230`; `core/document_processor.py:1208-1252`). That method opens its own session and context and calls the assigner (`_build_pseudonym_assigner`, `:285-333`), which calls `compositional_engine.assign_compositional_pseudonym` and, through it, `secrets.choice` (`pseudonym/library_manager.py:613`, `:677`, `:732`, `:767`).
- The result is stored as `suggested_pseudonym` (`gui/models/validation_state.py:235-236`), read by `get_pseudonym` (`:1281-1288`) and shown in the list.
- Finalization runs `FinalizationWorker` (`gui/workers/finalization_worker.py:100-120`), then `finalize_document` (`core/document_processor.py:1254-1307`), which has no way to receive what was shown.
- Under `pseudonym_lock`, it calls `_reset_pseudonym_state` (`:1020-1043`, which clears the preview's state), then `_resolve_pseudonyms` (`:855-976`), then `_assign_new_pseudonym` (`:718-758`): a new draw.

**CLI:** `process_document` (`:1309-1374`) builds the assigner (`:1332`), runs the review with it (`:1334-1343`), then resets and draws again under the lock (`:1346-1353`). The spreadsheet path does the same (`_process_document_tabular`, `:1376-1445`). `docs/validation-ui-spec.md:246` promises "Accept entity and suggested pseudonym".

**Desktop batch:** `gui/screens/batch.py:1034-1038` builds the previews the same way; `BatchWorker._process_with_validation` (`gui/workers/batch_worker.py:376-437`) then calls `finalize_document` with no preview.

**Measured on `fe44a7d`** (SM, 2026-11-13; Dev Notes "Reproduction"; real spaCy detection, a new database per run, every name confirmed):

| Path | Runs | Names shown and written the same |
|---|---|---|
| CLI `process`, text (three French documents) | 30 | **0 of 190** groups |
| CLI `process`, `.csv` | 5 | **0 of 20** |
| Desktop, single document, fresh database | 15 | **0 of 95** rows |
| Desktop batch, theme `neutral` | 3 | 1 of 30 rows (« Toulouse » shown and written « Toulon », by chance) |
| Desktop batch, theme `star_wars` | 3 | **0 of 33** rows |

It is systematic by construction: a name not yet stored is drawn twice, so the two agree only by chance (about 1 in 80 for a place, 1 in 196 for an organisation, far less for a person). Nothing leaked and no two people were merged; the user approves a pseudonym that is never written.

This reopens B36 (Story 10.11 follow-up (h), `docs/stories/10.11.custom-pseudonym.story.md:457`; `docs/qa/assessments/epic-10-close-out-summary.md:142`), accepted under Q-H on a "may differ" preview (`gui/screens/validation.py:763-767`).

#### The list can show a name of the document

Story 11.6 made every draw refuse a value that is a real name of the document (`core/custom_pseudonym.py:516-533`, `real_name_check`; the selectors at `pseudonym/library_manager.py:613-616`, `:677-680`, `:732-735`, `:767-770`). But the rule is set only inside `_resolve_pseudonyms`, under the lock (`core/document_processor.py:887-889`). The preview draws come before it, with no rule (`_real_name_check` is `None` in a new context, `library_manager.py:125`).

- **The written file is protected** (measured on `fe44a7d`, `logs\realname_probe.log`): a forced draw of the name's own words (« Élodie Martin », « Marseille ») and of Lionel's case (« Martin » drawn « Dupont » while « Jean Dupont » is named) are drawn again. On `8bf265d` the same probe left « Élodie Martin a présenté le budget à Marseille. » unchanged. Unforced, 900 finalizations of three documents wrote **0** values that the rule refuses.
- **The list is not:** of 300 previews per document, the list showed at least one value that the rule refuses in 1 (`lionel.txt`), 50 (`shapes.txt`) and 27 (`hr.txt`). Seen in the CLI runs: « Bordeaux » shown as « Bordeaux »; the place « Élodie » shown « Marseille » in a document naming Marseille; « Nicolas Duarte » shown while a real Nicolas Roux is named.

So the real-surname case that Lionel put in 11.5 ("include the real surname case in 11.5", 2026-11-10) is closed for the file by Story 11.6, and stays open for the list only. Once the shown pseudonym is kept, a list value the rule refuses would be drawn again and reported for nothing. This story sets the rule before the preview draws (AC8).

#### Two smaller gaps in the same list

- **Stored titled name.** `build_pseudonym_previews` puts the title in front (`core/document_processor.py:1239-1250`). `classify_known_entities` then overwrites it with the bare stored pseudonym (`gui/models/validation_state.py:270`). So the list shows « Isabelle Almeida » for « Mme Élodie Martin », while the file reads « Mme Isabelle Almeida ».
  - Measured, desktop single document, second document on the same database: **15 of 15** stored titled rows were shown without their title (« Mme Élodie Martin », « M. Karim Benali », « Madame Sophie »); the other 80 stored rows matched.
  - The batch review runs the same `classify_known_entities` on a document shown for the first time (`gui/screens/validation.py:336-347`), so it has the gap too (read in code).
- **Desktop batch theme.** `gui/screens/batch.py:1034-1037` builds the previews with `DocumentProcessor(db_path=..., passphrase=...)`, so with the default `theme="neutral"` (`core/document_processor.py:168`). The batch worker writes with the configured theme (`gui/screens/batch.py:721`, `:763`). Measured with `star_wars`: **33 of 33** previews came from `neutral.json` and all 33 written values from `star_wars.json`. The single-document path passes the theme (`gui/screens/processing.py:275-281`; `gui/screens/validation.py:1133`).

### Lionel's answers (2026-11-13)

The four review questions of v2.0, as he decided them (his words in Dev Notes "Decisions Recorded"):

1. **A name's text corrected in the review keeps the pseudonym shown.** « Élodie Mart » showing « Sofia Renault », corrected to « Élodie Martin », is written « Sofia Renault » (desktop and command line). Tests: T24.
2. **A type changed in the review updates the list at once.** « Élodie » found as a place and showing « Lyon », changed to a person, shows a person's pseudonym (for example « Sofia Renault ») right away, and that is what is written if it is still free at the end. Tests: T25, T36, T37, T38.

A lone « Élodie » row shows « Aurore » too, which closes B32. Tests: T34, T35, T38.
4. **The double title is a known limitation.** « M. le Dr Paul Lefèvre » (1 of 14 title forms measured) keeps today's behaviour; KL-011 records it (Dev Notes "Exact texts").

5. **The command line after a custom pseudonym (2026-11-14):** once [C] sets a custom pseudonym, the groups reviewed **after** it already show the matching part. [C] « Aurore Bruneau » for « Élodie Martin »: a later group « Élodie Dupont » shows « Aurore … », not « Sofia Gautier ». So a pseudonym shown before a [T] or a [C] that can no longer be used is drawn again at the end and listed by the end message (C1-C3), as AC6 says; only the groups reviewed after a [C] change (answer 5).

### Fix design

#### A. The library's one acceptance check, `pseudonym/assignment_engine.py` and `pseudonym/library_manager.py`

1. **`PseudonymManager.accepts_value(self, value: str, kind: str, real_component: str | None = None) -> bool`**, abstract. Docstring: "Whether a draw would accept this value now (Story 11.5): the real-name check (Story 11.6), and the value not taken. ``kind`` is "first_name", "last_name", "LOCATION" or "ORG"."
2. **`LibraryBasedPseudonymManager.accepts_value`**, extracted from the four selector loops without changing what they accept:
   - False when `self._real_name_check` refuses it;
   - `first_name` / `last_name`: False when its folded value is the part of another real component of the same kind, or any part of the other kind (`_select_first_name` `:618-644`, `_select_last_name` `:682-703`);
   - `LOCATION` / `ORG`: False when it is in `_used_pseudonyms` (`:736`, `:771`).
3. Each loop calls it in place of its inline test; the record of the new component mapping and the exhaustion paths stay where they are. `TestBuildPseudonymAssigner`, `test_library_manager*.py` and `test_generated_pseudonym_document_words.py` stay green unchanged.
4. A small public `is_used(self, pseudonym_full: str) -> bool` (`pseudonym_full in self._used_pseudonyms`), declared in `PseudonymManager` too, for the full-pseudonym condition.
   - The only subclass of `PseudonymManager` is `LibraryBasedPseudonymManager` (`git grep -n "PseudonymManager)" -- tests/unit gdpr_pseudonymizer` on `fe44a7d`); no test double subclasses it, so the two new abstract methods break no test. Story 11.6 added `set_real_name_check` the same way without changing a test double.
5. No logging of a value; a debug event with the kind only is allowed.

#### B. The processor, `core/document_processor.py`

1. **Types**, beside `ProcessingResult`:

       pseudonym_last: str | None

       """A name written with another pseudonym than the one shown (Story 11.5)."""

   `ProcessingResult` (`:91-118`) and `_ResolveResult` (`:136-145`) gain `pseudonyms_changed: list[ChangedPseudonym] = field(default_factory=list)`.
2. **The preview assigner keeps what it showed.** `_build_pseudonym_assigner(self, ctx, proposals: dict[NameKey, PseudonymProposal] | None = None)`: when `proposals` is given, each new assignment is recorded there, keyed by (mapping key, type), from the `PseudonymAssignment` and `self.theme` (`setdefault`, beside `preview_cache`).    - in `build_pseudonym_previews`, after `_init_processing_context` (`:1232`), with its new `document_text` (empty by default: the names half alone still refuses a name's own words).
   - `reset_preview_state` leaves the check as it is (`library_manager.py:205-213`), and `_resolve_pseudonyms` sets it again from the names sent (`:887-889`), unchanged.
4. **`build_pseudonym_previews(self, detected_entities, document_text: str = "", proposals: dict[CandidateKey, PseudonymProposal] | None = None)`.** The return type is unchanged. 5. **`_resolve_pseudonyms(..., proposals: Mapping[NameKey, Sequence[PseudonymProposal]] | None = None)`.** Each sent name carries every distinct proposal shown for it, in the order of its rows or groups; the first is the one checked and kept, all are compared for the report (AC6). Right after `_register_custom_pseudonyms` (`:891-898`), so after the real-name check is set from the names sent, a new `_register_proposals(ctx, proposals, entity_cache, new_entities, validated_entities)` keeps the free ones. **One round, in the order of the names' first places** (PO v2.2: the order today's per-occurrence loop resolves names in, and the order both previews draw in: the desktop in detection order, sorted by position; the CLI by group first occurrence). (v2.1's two rounds, multi-word names first, would have written the lone name with the full name's part alone while the list showed two parts, and reported it every time.)

   A name is skipped (the loop resolves it) unless every condition holds:
   1. it has no custom pseudonym (`name not in entity_cache`);
   2. it has no stored row now (`find_by_full_name_and_type`);
   3. `proposal.entity_type` is the name's type (a CLI [T]; on the desktop the list has already drawn one of the new type, D.6);
   4. `proposal.theme == self.theme`;
