### Context: why a lone first name is missed today

- **The label map drops MISC.** `SpaCyDetector._map_entity_type` (`nlp/spacy_detector.py:194-213`) maps PER, LOC, GPE and ORG (and their long forms); every other label, MISC included, gives `None`, and `detect_entities` keeps only mapped entities (`:169-188`). spaCy's French model often labels a lone first name MISC: 1,507 of QA's 7,390 cases, and 79.9% of the misses (QA, `measure.log` (d)). The Doc is kept (`self._last_doc = doc`, `:166`; `last_doc`, `:237-244`), so a rule can still read the MISC spans.
- **How « Bonjour X, » already reaches PERSON.** Story 10.4's R-SAL-BARE (`hybrid_detector.py:1526-1563`) adds a regex PERSON for a known first name on a salutation line (`_salutation_lines`, `:1310-1359`): shape 1, one or two names alone on a line ending with a comma; shape 2, an opener of `salutations.yaml` (« Bonjour », « Merci », « Bonne initiative », « Félicitations ») then the name and `, . !` or the end of the line. "Known" means `NameDictionary.is_first_name` (`name_dictionary.py:81-91`) over `french_names.json`'s 451 names. So « Bonjour X, » works for those 278 library names that are also in `french_names.json` (0 missed of 278) and not for the 461 others (204 missed); « Merci X pour … » is not a salutation line (a word follows the name), nor is « Cordialement,⏎X » (no comma after the name).
- **The other 20%: spaCy finds nothing** (350 of 1,738 misses; 206 of them in « Réponse de X : »). No rule that reads spaCy's labels reaches them; the wide rule does not read them, so it reaches these too.
- **What the user sees** (epic): a missed name is not in the desktop review list (`gui/workers/detection_worker.py:167-191`) and can be caught only by selecting it and using « Ajouter comme entité » (`gui/widgets/entity_editor.py:359-367`); if nothing at all was found, the panel says « Aucune entité détectée. Le document ne contient peut-être pas de données personnelles… » and « Continuer ▶ » is still offered (`gui/screens/processing.py:170-174`, `:317-319`).

### The mechanism: the wide rule (Q6)

**What it does, in plain words.** The app keeps two lists of first names: the default pseudonym library's 739 and `french_names.json`'s 451 (898 together, accents ignored, so « Elodie » matches « Élodie »). With this story, a word that starts with a capital and is on one of those lists becomes a person wherever it stands alone: after « Bonjour », « Salut » or « Merci », on a line of its own after « Cordialement », after a dash, at the start of a sentence, after a title (« le Dr Nadia »), in the middle of a sentence. Nothing is needed from spaCy and no cue word is needed. "Stands alone" means only two things (Fix design 2): no person detection already holds the word (so « M. Bernard » keeps its title and « Jean Dupont » stays one person), and no place or organisation detection holds it as part of a longer name on the same line (so « Azure » in a detected « Microsoft Azure » organisation is left alone). A word that is also an ordinary word (« Pierre de taille », « Teinte : Ambre ») or a product (« Azure ») is offered as a person when it starts with a capital, and the user rejects it in the review: Lionel's own reason at Q5, "if it's first names, then it's first names … it's still time to reject afterwards". A word in lower case is never taken (« une rose », « en avril »).

**What goes.** CD's two parts (Q1) and the cues (Q3 (a), Q3 (b), Q5): the wide rule finds every name the cues found, on every sentence measured, so the cue list, its resource `first_name_cues.yaml` and the "other"-label rule with its two guards (after a title; next to another capitalised word) are not built. No cue stays. A cue for names outside the lists (« Réponse de Muriel ») was never part of CD and is not added (Known limitations).

**Measured** (in memory, on today's detector, `4c40dc2`'s files; `r143\sm3\wide143.py`, `logs\wide143.log`, and `wide143b.py`; QA's harness and buckets, a name is "missed" when no PERSON, LOCATION or ORG detection overlaps it). ### Fix design (the wide rule, Q6)

The rule is the measured one, copied from the probe `r143\sm3\wide143.py` (`w_rule`, `WORD`, and the patch point `_sal_w`), so Task 2.4 can require the shipped code to reproduce the measured numbers exactly. Where this text and the probe differ, the probe is right and the difference is reported, with one exception: the probe's `SMALL` list is not built (PO v1.7, guard (b) below), and the dev's copy drops it too (Task 2.4). It sits where the cue rule was measured: right after R-SAL-BARE, its PERSONs joining the regex list, so the boundary fixes, the merge and the dedup run on them as on any regex PERSON. Nothing else in the pipeline moves. v1.5's "other"-label rule, its two guards, the cue rule and `first_name_cues.yaml` are not built.

1. **The list (`nlp/hybrid_detector.py`, a new loader).**
   ```python
   @functools.lru_cache(maxsize=1)
   def load_lone_first_names() -> frozenset[str]:
       """First names a lone token may be (Story 14.1): the default pseudonym
       library's first names and french_names.json's, through _fold."""
   ```
   - It reads `first_names` (every key: `male`, `female`, `neutral`) of `PSEUDONYMS_DIR / "neutral.json"` and `first_names` of `FRENCH_NAMES_PATH` (`resources/__init__.py`), always `neutral.json`, whatever theme the user picked, and returns `frozenset(_fold(n) for n in …)` (`_fold`, `hybrid_detector.py:295-300`: accents removed, case-folded). 898 names (912 with accents kept).
   - It is read only by step 2. It is never merged into `NameDictionary.first_names` (Project Structure Notes; AC11).
   - A token is **listed** when `token[:1].isupper()` and `_fold(token)` is in this set.
2. **The rule (`HybridDetector._lone_first_names(self, text: str, spacy_entities: list[DetectedEntity], regex_entities: list[DetectedEntity]) -> list[DetectedEntity]`).**
   - **The tokens:** every match of `_LONE_TOKEN_RE = re.compile(f"(?<![\\w-])({_NAME_TOKEN})(?![\\w-])")` in `text`, in order (`_NAME_TOKEN`, `hybrid_detector.py:211`: a capital, then letters, hyphen-joined parts each starting with a capital; Python `re` on `str`, so `\w` is any Unicode letter, digit or underscore). What that gives (`wide143.log`, "tokenisation examples"):
     - « Jean-Pierre a signé. » → one token « Jean-Pierre », not listed (the lists hold no compound), so nothing; « Nadia-Rose » the same;
     - « Merci d'Hélène et de l'Ambre. » → « Merci », « Hélène », « Ambre »: an apostrophe is not a word character, so the elided article does not join the name; « Hélène » and « Ambre » are listed;
     - « NADIA a appelé. » → « NADIA », listed (capital first letter, folded); « nadia a appelé. » → no token;
     - « Nadia2 », « Nadia_x » → no token (a word character follows);
     - « Elodie » and « Élodie » → both listed;
     - « Marie Claire » → two tokens, both listed, so two persons; « Marie-Claire » → one token, not listed;
     - « le Dr Nadia » → « Dr » (a title, not listed) and « Nadia »;
     - « Nadia.Martin@ex.fr » → « Nadia » and « Martin », both listed; with the real detector the whole address is already a place, so guard (b) leaves both (PO v1.7; Known limitations).
   - **A listed token stands alone unless** one of these holds, checked against `spacy_entities + regex_entities` and the PERSONs the rule already added:
     - **(a) a person holds it:** a PERSON overlaps it (`a.start_pos < end and start < a.end_pos`). So « M. Bernard » keeps its title (the regex PERSON « M. Bernard » holds « Bernard »), « Jean Dupont » stays one person, and the same name is never added twice. **PO v1.7:** through the whole pipeline the merge would drop the inner « Bernard » anyway (two PERSONs that nest: the longer is kept), so (a) is not what keeps « M. X » whole; what it guarantees is that no detection of today changes (without it, one detection of the 25 dev documents changes: today's wrong person « Architecte » in « Laurent Benoit⏎Architecte Cloud », email_chain, disappears through the boundary fixes; a gain of one, but not this story's change, and AC7 says no removal), and its test calls the rule directly (L4);
     - **(b) it is part of a longer place or organisation name:** a LOCATION or ORG overlaps it and holds, on the same line as the token (no « \n » between them), another token of the same pattern that is not a title (`is_title`, as below). So « Azure » inside a detected « Microsoft Azure », « Claude » and « Bernard » in the detected organisation « Université Claude Bernard » (dev documents, interview_01), « Charles » in the detected place « Place Charles de Gaulle », and « Madeleine » in the detected place « La Madeleine » are left alone. **PO v1.7:** v1.6 also let a small word (« La », « De », « Au »…, the probe's `SMALL`) not count as another token; that changed nothing on any measured set (grid, chat and e-mail lines, 156 sentences, 25 documents: `po143w.log` and `po143w2.log`, mode `noSmall`) and its only effect found was a wrong person « Madeleine » inside the place « La Madeleine » (`po143w3.log`), so it is not built. **The title exception is kept:** on « Le Dr X est là. » spaCy holds « Dr X » as a place or an organisation for 12 of 739 names, and the exception gives them a person too (both rows, as for a place on exactly the word); L1[`title_in_an_org`] tests it. The same-line check matters: the pipeline splits a detection at a line break afterwards, so a word on the next line is not part of the name (the SM's first run looked across lines and left 24 names of « Cordialement,⏎X⏎Responsable du projet » as an organisation only; `logs\wide143_v1_crossline.log`, kept for the record).
     A token is a title when `re.fullmatch(f"(?:{FRENCH_TITLE_PATTERN})", t.strip() + " ", re.IGNORECASE)` or the same on `t.strip()` matches (`FRENCH_TITLE_PATTERN`, `utils/french_patterns.py:18`).
   - **Else** `DetectedEntity(text=token, entity_type="PERSON", start_pos=start, end_pos=end, confidence=0.80, source="regex")`.
   - **What that decides** (Lionel's "wherever it stands alone"; each measured, Dev Notes "Measurements"):
     - **after a title:** a title is not a name, so the name is alone unless a detection already holds the title with it ((a)). « Le Dr X est là. »: 518 of 739 missed today, 0 with the rule; « Le rapport de M. X est prêt. »: « M. X » kept whole for 723 names, as today, and none shrinks;
     - **at the start of a sentence or a line:** taken. « Selon X, le contrat est prêt. » and « Hier X a signé le contrat. »: 98 and 81 missed today, 0 with the rule; « Pierre de taille pour la façade nord. » gives a person;
     - **when a place or organisation detection is exactly that word** (or that word with a preposition, « à Sarah »): taken, and both rows stay (Q4; Story 15.1 marks the one not written). « Réponse de Diego : d'accord. », « reportera à Sarah », « Kevin » in the dev documents;
     - **when spaCy's place or organisation span also swallows the word before the name** (« Cher X » as a place, « Salut X », « Bonsoir X », « Merci X », « Hier X » as an organisation or a place): (b) applies, since that word is another capitalised token on the line, so no person is added and the name stays replaced as a place or an organisation (Known limitations, with the counts);
     - **a word in lower case:** never taken (no token).
   - No log line holds a token's text (AC11): at most `logger.debug("lone_first_name_added", start=…, end=…)`, as R-SAL-BARE logs positions only.
3. **The call (`HybridDetector.detect_entities`, `hybrid_detector.py:836-839`).** Right after R-SAL-BARE: `regex_entities = regex_entities + self._lone_first_names(text, spacy_entities, regex_entities)`. `spacy_detector.py` does not change; the rule does not read spaCy's Doc or its labels.
4. **Nothing else.** No change to the review, the writer, `entity_grouping`, the mapping table or the hover text: those are Story 15.1's, as merged in `<base>`.
