## Story

**I want** a name or place found by the regex layer to stay on the list when spaCy found the same text with another type,
**so that** I choose the right type during validation instead of the candidate being silently lost.

### Context (epic, verbatim)

Copied from the epic at `d976a4d`. The dry-run figures are re-measured in Task 1 (AC2).

`HybridDetector._merge_entities` (definition `:667`; its `_is_exact_match` call at `:708`) skips a regex detection when `_is_exact_match` (defined at `hybrid_detector.py:2030-2053`) finds a spaCy detection with the same span or the same normalized text. (Line numbers at `main` `4f3cf30`, after PR #90.) The check ignores entity type, so a regex detection is dropped even when spaCy gave the text another type. Example: regex LOCATION "Nice" is dropped because spaCy found ORG "Nice".

**10.3a dry-run measure (local dump on 10.3a's starting code; MX tried as a fall-through into the existing branches, so the Cabinet special case ran first; NOT a CI result, NOT a target):** PERSON TP +2 / FP +2 / FN −2; LOCATION +2 / 0 / −2; ORG 0 / +2 / 0 (10.3a story, Dry-Run Results, "MX alone"). The PERSON FP figure is net: +4 regex PERSON on hyphenated place or company names ("Sophia-Antipolis", "Saint-Gobain" twice, "Clermont-Ferrand") and −2 spaCy PERSON "Cabinet …" removed by the special case; the ORG FP +2 are those two regex "Cabinet …" ORGs. The kept regex entity is flagged `is_ambiguous`.

## Acceptance Criteria

AC1 to AC5 are copied from the epic's story 10.3c word for word. The story-level precisions in "AC precisions (story-level)" below add detail; they do not change the epic text. AC6 to AC10 are story-level.

1. **AC1 — Type-aware exact match:** the exact-match skip applies only when both detections have the same entity type. When the span or normalized text matches but the types differ, both detections are kept, the regex detection is flagged `is_ambiguous = True`, and a distinct log event records the decision without logging entity text beyond current practice. Same-type exact matches keep today's behaviour (regex skipped). The 10.2 same-type overlap rule and the regex-ORG-over-spaCy-PERSON special case (`_should_prefer_regex_org`) are unchanged.
2. **AC2 — Re-measure first:** the dry-run figures above were taken on top of 10.3a. Before coding, the story re-measures them on the 10.3b close-out baseline and reports the per-type FN/FP delta. Only the cited G1 run counts as a result.
3. **AC3 — Hyphenated place names:** the new PERSON FP on hyphenated place names ("Saint-Gobain", "Clermont-Ferrand" in the dry-run) are reported. A rule that removes them is in scope only if it is generic (no lexicon built from corpus strings) and keeps to the Cross-Story Rules. Otherwise they are recorded as accepted FP with Lionel's sign-off: both candidates reach the mandatory validation step, flagged ambiguous.

### AC precisions (story-level)

- **AC1:**
  - **"Both detections are kept"** means: the regex entity is appended to the merged list (today it is skipped with `break` and no append), `regex_entity.is_ambiguous` is set to `True`, and the spaCy entity is left untouched. The outcome is the same as the existing different-type partial-overlap branch (`hybrid_detector.py:728-739`), with its own log event.
  - **"Exact match"** keeps today's meaning: `_is_exact_match` (`:2030-2053`) is true for the same `start_pos`/`end_pos`, **or** for the same text after `strip_french_titles` (`_normalize_entity_text`, `:2011-2028`; no preposition stripping, no case folding, internal whitespace kept). By default, `_is_exact_match` stays a span/text test and the type comparison is made in the merge loop (Candidate Rules, R-MX). Its only caller is `:708`.
  - **Placement versus `_should_prefer_regex_org`: settled, R-MX is AC1's reading (PO validation, 2026-10-09); not a question for Lionel.** In the loop, the exact-match test (`:708`) runs before the Cabinet special case (`:716`). Today a regex "Cabinet …" ORG that exactly matches a spaCy PERSON is skipped by the exact match, so the special case never sees that pair. If the new type-aware test simply fell through to the existing branches, the pair would reach the special case, which removes the spaCy PERSON (`:719`).
    - **These pairs exist on the main corpus.** The baseline dump `rgpd-analysis/r103b/qafix_dump.json` holds the spaCy PERSON "Cabinet Bredin Prat" @10508 and "Cabinet Wilson Sonsini" @10572 (partnership_agreement.txt). 10.3a's "MX alone" dry-run was such a fall-through: it removed both spaCy PERSONs and left 6 characters in 2 spans uncovered at coverage level 1 (`rgpd-analysis/r103a/dry1/dryrun_report.txt:1875-1889`).
    - A fall-through (R-MX-CAB) therefore contradicts AC1 ("both detections are kept"; the special case "unchanged") and would need an AC7 coverage sign-off. **R-MX** puts the new different-type branch **before** the special case, so the special case keeps seeing exactly the pairs it sees today. R-MX-CAB stays in the dry-run as an information-only row (it reproduces the 10.3a measurement, AC2).
  - **Distinct log event:** for example `cross_type_exact_match_kept` (debug), with fields `regex_type`, `spacy_type`, `match` (`span` or `normalized_text`), `regex_start`, `regex_end`, `spacy_start`, `spacy_end`, and **no entity text**. `_is_exact_match` returns a bool and is not changed. The merge loop derives the match kind itself: `span` when `start_pos` and `end_pos` are equal, checked first; otherwise `normalized_text`. "Current practice" in the merge loop logs entity text in three debug events: `duplicate_entity_removed` (`:710-714`), `org_supersedes_person` (`:721-726`) and `ambiguous_entity_added` (`:733-738`). Those stay as they are. The new event follows the practice of the 10.2–10.3b events, which log offsets only. [Source: architecture/19-coding-standards.md#19.1, rule 3]
  - **"Unchanged"** for the 10.2 same-type overlap rule means that `_dedup_same_type_overlaps` (`:1825-1874`) and its pair rules (`:1676-1823`) are not edited. Their input can now hold more detections (the regex entities that are kept), and the dry-run reports any outcome this changes.
  - **The first overlapping spaCy entity decides.** Every branch of the inner loop ends in `break` (`:715`, `:727`, `:739`, `:744`), so the base code is already order-dependent for partial overlaps. R-MX keeps this. Looking at every overlapping spaCy entity instead (R-MX-ALL) is a technical decision of the dev, reported as information (Task 1.6), not a question for Lionel.
  - The flag stays on the regex entity even if a post-filter later drops its spaCy partner. Task 1.4 counts these cases.
  - **Where the user sees the flag:** only in the CLI validation ("⚠️ … (ambiguous)", `validation/ui.py:267`; reason "Entity flagged as ambiguous by detection algorithm", `validation/workflow.py:415-429`). The GUI does not display `is_ambiguous`; it only carries it (`gui/models/validation_state.py:304`). In the GUI the two candidates appear as two entries of different types. This story makes no UI change (epic "Enhancement Details").
- **AC2:** "the 10.3b close-out baseline" is run D `37641796495`, reproduced by `37891970847`, and the local dump of `4f3cf30` must reproduce it (Task 1.1). Task 1.4 therefore compares them with the R-MX-CAB row, and gives R-MX against a stated expectation (Dev Notes "Previous Story Insights").

### Dry-Run Protocol (lessons from 10.2, 10.3a and 10.3b)

- **Reproduce first.** No dry-run number is trusted until the baseline dump reproduces run D exactly (1.1) and the local per-document JSON gives an all-zero paired delta against `37891970847` (1.2).
- **Patch in the script, run the real pipeline.** The rule is patched in the script (monkeypatched method or subclass), never in product code, and every document goes through `detect_entities`. The merge sits between the 10.3b steps (both `_fix_person_boundaries` calls and the guarded re-merge before it; R-SPLIT late, W-JOIN and R-ROLE-LATE after it), and a re-merge of captured lists would miss their interplay.
- **Net, not gross.** `match_entities` (`tests/accuracy/conftest.py:108-149`) is exact text + type, one-to-one, with position only as a tiebreaker. A kept second candidate can therefore show up as a TP gain, as a TP loss elsewhere, or as nothing. Re-score the **whole** post-rule dump and report the per-type net delta. STOP R and STOP G3 use the net delta.
- **Classify every lost TP:**
  - **position loss**: no detection now matches that annotation at its position, so it becomes an FN;
  - **taken over**: another detection now matches it;
  - **cross-position scorer artefact**: the lost TP was matching a same-text annotation elsewhere.
  Gained TPs are classified the same way (real fix or artefact).
- **Coverage table** for every rule and composition (levels 1, 2 and 2b, Coverage Invariant).
- **Fires on non-targets.** Report every firing of a rule on a shape it was not meant for, even when the net delta is zero (10.3a's first W-JOIN fired on a label line).
- **Dumps include `is_ambiguous`.** The 10.3b dumps compare text, type, offsets, source and `is_ambiguous`; keep that, because AC1 changes the flag.
- **Scripts:** start from `scripts/accuracy_particles_noise_dryrun.py` (10.3b) and `scripts/accuracy_runon_dryrun.py` (10.3a). New scripts are named `scripts/accuracy_*.py`, use `Path(__file__).resolve().parent.parent`, and call `_load_corpus_documents()` only. Dumps and outputs are written outside the repo and never committed. Run them via `cmd.exe` + `poetry run python`.

### Pseudonym Continuity (CHANGELOG upgrade note, AC5)

The schema is unchanged. The mapping key is the entity text with titles stripped (and prepositions, for places) and every whitespace run collapsed to one space (`DocumentProcessor._normalize_entity_text`, `core/document_processor.py:210-232`). **The key has no entity type, and every lookup is type-blind**: `find_by_full_name(key)` at `:254`, `:304` and `:507`, and the per-run `entity_cache` keyed by text only (`:489`). [Source: prd/epic-10 "Risk Mitigation"] Describe, with invented examples only:

1. **New second candidates.** Where the regex layer and spaCy found the same text with different types (regex LOCATION "Zorbaville", spaCy ORG "Zorbaville"), both are now offered. Validation shows them as two entries, one per type, and the CLI marks the regex one "(ambiguous)". Rejecting one gives today's outcome for the other.
2. **If the user confirms both,** they share one key. The first one resolved gets (or creates) the row; the second reuses its pseudonym through the text-only cache. Both carry the same pseudonym, and one row is stored, with the first one's type. At the same span, the output applies one replacement (`_apply_replacements`).
3. **Existing databases (the pre-existing type-blind lookup, flagged by the PR #86 QA probe).** If the key is already in the database, whatever its type, `_run_validation` auto-accepts **both** candidates as known entities (`:297-308`), and neither is shown for review. Both get the stored pseudonym. So, for a known key, AC1's type choice never reaches the user. No text is left in clear. **For such a key the output is the same as today:** the same stored pseudonym and, at the same span, the same replacement; and the second candidate was not shown before either, because the merge dropped it. Nothing gets worse. The behaviour is not new, but 10.3c makes it reachable more often. Changing it is a `core/`/`data/` change outside this story. **At STOP R Lionel chose a follow-up story (2026-10-09): Story 10.7, Type-Aware Mapping Lookup** (epic, `cff1828`), where the same text under another type gets its own row and pseudonym.
4. **Recommendation:** as in 10.2–10.3b, keep the same mapping database across versions, and re-process with the old version if byte-identical output is required.
