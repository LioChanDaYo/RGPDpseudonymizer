## Story

**As a** desktop-app user correcting a detected name in the review list,
**I want** my edit to apply to every occurrence of that name and type, as it does in the CLI,
**so that** no other occurrence of the name is left in clear.

**Priority:** HIGH — it is a leak path: after an edit, the other occurrences of the name are not pseudonymized. It must land before the next release. It is not a 10.3c regression: the behaviour is in every desktop release since v2.0.0 (Story 6.8, PR #57), and the code is unchanged since v2.2.0.
**Change type:** desktop app review only. No detection change, so G1, G3 and G5 are N/A. No file under `gdpr_pseudonymizer/nlp/`, `gdpr_pseudonymizer/resources/`, `tests/accuracy/` or `tests/test_corpus/` changes. If any file the accuracy suite loads is touched, one regular accuracy run on the branch shows the 16 lines identical to `38212303870`.
**Ordering:** outside the detector chain. It goes after Story 10.8, because both change `gui/models/validation_state.py`, and never in the same PR as 10.8 (10.8 stays narrow: keys only).
**Epic:** [Epic 10: v2.3 — Detection Precision Quick Wins](../prd/epic-10-v2.3-detection-precision-quick-wins.md) (story 10.9)
**Branch:** `story/10.9-gui-edit-all-occurrences`, cut from `main` at `51d8429` (PR #95, Story 10.6 B15 close-out). It carries the PM's epic commit `ae7f308` (`docs/prd/` only: it adds Story 10.9). The story commit comes after it. The branch has no upstream until the dev pushes it after the rebase (Task 0.1); nothing is ever pushed to `main`.

The row the user acts on directly is always changed, even if it was rejected, because acting on it is explicit. Every other row the correction reaches today is still reached, including rows still to review ("en attente"), which become "modifié"; only rejected rows are skipped. One undo restores exactly the rows the correction changed, and nothing else. Single-document and batch validation. Test T17.

### AC precisions (story-level)

- **AC1, "every occurrence of that name and type":** in single-document validation, every occurrence in the row's variant group: the variant-map entry of the row, looked up with the key Story 10.8 stores for the row at init. This includes other spellings that the grouping puts in the same row ("Dr Quentrel Zorbalia" and "Quentrel Zorbalia"; "Zorbalia" alone joins "Quentrel Zorbalia", P5b), as the CLI's groups do. In batch validation, where each occurrence is its own row, every row of the edited row's (text, type) group, the group accept and reject use since 10.8. The edited row is always included.
- **AC1, "each with its edited span":** the edited row keeps the span its caller passes; the edit dialog computes that span with the CLI's rule. Every other occurrence gets `ValidationWorkflow._locate_modified_span(document_text, occurrence, new_text)`, relative to its own current span: the edited text where it overlaps that span, otherwise the current span itself, with the edited text. Before any edit the current span is the detected span; after an edit it is the span that edit gave the place (amendment, AC10). No occurrence is ever dropped: where the edited text is absent, the place stays pseudonymized on its current span, as in the CLI (T2, T15).
- **AC1, the sent entity:** text is the edited text, type is the row's current type, and the other fields (confidence, gender, ambiguity flag, source, context label) come from the occurrence, as `get_validated_entities` builds the edited row today (`validation_state.py:296-308`).
- **AC1, "One undo reverts the whole edit":** in single-document validation the edit stays one `_ModifyTextCommand`. The other occurrences' spans are computed when the edit is made and stored with that command (Fix Design step 12, amendment), so one undo reverts all of them and one redo re-applies them (T4, T15). In batch validation the edit is one undo macro over the group's rows, the shape accept and reject use (`validation_state.py:129-134`) (T6). One exception in single-document validation: a row added by hand with the same text and type as a detected row makes a group of two rows (Consumer Trace #14), so its edit is one macro too, as in batch.
- **AC1, highlights:** for an edited row, `get_all_entity_ranges` returns exactly the spans finalization sends (T5). The editor shows them: it rebuilds its ranges after every edit, type change, undo and redo, so the highlights, the tooltip and a click on any edited place follow the state (T14; UI-001, Decisions Recorded; Fix Design step 10). This is what the CHANGELOG clause "the highlights show exactly the places that will be pseudonymized" and Consumer Trace #8, #19 and #20 promise.
- **AC1 is checked at the output:** T1–T3, T7, T13 and T15 finalize and assert that no part of the invented name is left in the output.
- **AC2, the list:** the tests-first commit holds 9 tests that fail on the unfixed code (T1–T7, T11–T12) and 3 guard tests that pass on it (T8–T10). The dev records both lists with their local outcomes (Task 1.2). The amendment's tests-first commit (Task 8) holds 3 tests that fail on `9c5dee2` (T13–T15) and 1 guard that passes on it (T16); the dev records them the same way (Task 8.2).
- **AC2, "Existing GUI and CLI validation tests stay green":** no existing test changes. On the SM's prototype, the existing GUI, document-processor and validation suites give the same result with and without the 10.9 change (Reproduction Evidence, item 11).
- **AC3, the wording:** Dev Notes "CHANGELOG Entry".
- **AC4, G1 condition:** the accuracy suite loads 13 product files (10.8 SM import probe; 10.8 Dev Notes "Code Map"): `gdpr_pseudonymizer/__init__.py`, eight files of `nlp/`, `resources/__init__.py`, `utils/__init__.py`, `utils/french_patterns.py` and `utils/logger.py`. - **AC10, the pre-fill:** `current = review.user_modification or review.entity.text` (`gui/screens/validation.py:572-578` at `9c5dee2`): the dialog shows `current` and applies the edit only when `ok and text and text != current`. `review.entity.text` is never changed by an edit (`_ModifyTextCommand` moves the span only), so the fallback is the detected text, or the selected text for a row added by hand. An undo restores `user_modification` (`_ModifyTextCommand.undo`), so the dialog follows undo and redo with no extra code.
- **AC10, "builds on the first":** at the row's own place the dialog already anchors on the row's current span (`_ModifyTextCommand` moves `review.entity`'s span in place). At every other place: in batch validation each row's span is moved in place the same way, so batch already does it today (T16, guard); in single-document validation the other places are not rows, so their spans are stored with each edit (Fix Design step 12; T15).
- **AC10, "no name part from the first edit is ever left unreplaced":** this is about a second edit that keeps the first edit's text, as one built from the pre-filled text does. A second edit that deliberately removes part of the name (for example "Quentrel Zorbalia Quentrix" back to "Quentrel Zorbalia") is the user's choice, as in the CLI: the removed part is no longer part of the name.
- **AC11, the rule (Lionel, 2026-10-14; Decisions Recorded):** the rows a text correction or a type change reaches are the row acted on, then every other row of its group (`_action_rows`) whose state is not REJECTED at the time of the correction. A rejected row is skipped however it was rejected: alone (a one-row selection through the bulk reject, as in the PO's probe), as a row alone in its group, or by a group reject. So after a group reject, correcting one of its rows changes that row only.
- **AC11, why the type change too:** Lionel's Q3 on Story 10.10 (2026-10-14, "Every place (Rec.)") bundles a correction of the name or of its type, and 10.10's AC3 and AC13 carry the two together ("A text correction or a type change on any row …"). One rule covers both, in one place (Fix Design step 13).
- **AC11 and AC1, AC9, AC10:** "every occurrence of that name and type" (AC1, AC9) and "applies to every occurrence, as the first one did" (AC10) mean every occurrence the user has not rejected. In single-document validation the occurrences of a row's variant group are not rows, so the user cannot reject one of them alone; there, AC11 applies to the rows a correction on a row added by hand reaches (Consumer Trace #14).
- **AC11, what does not change:** accept, reject and the bulk actions keep their group rule (Story 7.1; Lionel's Q3 correction on 10.10, "Keep group action (Rec.)"). A group accept still reaches a row rejected alone (SM observation, Reproduction Evidence item 14; Notes for the PO and PM, item 14).

### Product Constraints (non-negotiable, verbatim from the epic)

These apply to every story in this epic. A story that cannot meet its goal inside them stops and goes back to Lionel; it does not relax them.

1. **Local NLP only.** No LLM, no generative model, no API call, no cloud service, no telemetry. Every change is a deterministic rule, lexicon or pattern that runs offline.

```python
def _edited_occurrences(self, review, edited):
    key = self._candidate_key_by_id.get(review.entity_id)     # 10.8's stored key
    if key is None or key not in self._variant_occurrences:
        return None
    out = []                     # ValidationWorkflow imported at module level (step 1)
    for occ in self._variant_occurrences[key]:
        if occ is review.entity:
            out.append(edited)
            continue
        start, end = ValidationWorkflow._locate_modified_span(
            self._session.document_text, occ, edited.text)
        out.append(DetectedEntity(text=edited.text, entity_type=edited.entity_type,
                                  start_pos=start, end_pos=end, confidence=occ.confidence,
                                  gender=occ.gender, is_ambiguous=occ.is_ambiguous,
                                  source=occ.source, context_label=occ.context_label))
    return out if any(o is edited for o in out) else [edited, *out]
```
