## Story

**As a** desktop-app user reviewing a batch of documents,
**I want** "Précédent", "Suivant" and "Valider et continuer" to keep each document's own decisions and positions, and an action on a name I added by hand to act on that name,
**so that** no name is left in clear and no document is written with another document's positions.

**Priority:** HIGH — three leak paths in desktop batch review; PRE-001 also damages the output text. They must land before any release. None is a 10.3c regression: QA found the code involved unchanged since v2.2.0, and PRE-001 contradicts Story 6.7.3 (v2.0.0).
**Change type:** desktop batch review only. No detection change, so G1, G3 and G5 are N/A. No file under `gdpr_pseudonymizer/nlp/`, `gdpr_pseudonymizer/resources/`, `tests/accuracy/` or `tests/test_corpus/` changes. If any file the accuracy suite loads is touched, one regular accuracy run on the branch shows the 16 lines identical to `38212303870`.
**Ordering:** outside the detector chain. It may run in parallel with Story 10.9, never in the same PR; if both touch `gui/models/validation_state.py`, the second to merge rebases. PRE-003's fix changes the group lookup that 10.9's edit also uses (`_group_ids`, `validation_state.py:164-176`): once 10.10 stops grouping a hand-added row with detected rows, 10.9's edit on such a row follows automatically (10.9 story, Consumer Trace #14).
**Epic:** [Epic 10: v2.3 — Detection Precision Quick Wins](../prd/epic-10-v2.3-detection-precision-quick-wins.md) (story 10.10)
**Branch:** `story/10.10-batch-review-fixes`, cut from `main` at `e16d15a` (PR #97, Story 10.8). It carries the PM's epic commit `8e879d5` (`docs/prd/` only: it adds Story 10.10) and the story commits. The branch has no upstream until the dev pushes it (Task 1.5); nothing is ever pushed to `main`.
**Baseline:** none for accuracy (epic "Ordering"; AC6). The behavioural baseline is the desktop app at `8e879d5` (product code identical to `e16d15a`) and the SM's reproduction (Dev Notes "Reproduction Evidence").
**Code authorship:** GPT/Forge may write or review this story's code. Lionel's 2026-10-09 decision lifted the restriction for detector code (Dev Notes "Decisions Recorded"); this story's code is desktop-app code and was never under it.

## Acceptance Criteria

AC1 to AC6 are copied from the epic's Story 10.10 at `8e879d5` word for word. "AC precisions (story-level)" adds detail and does not change the epic text. AC7 to AC12 are story-level.

1. **AC1 — PRE-001:** "Valider et continuer" always applies to the document it belongs to, or is blocked with a clear message. A list built on one document is never stored for, or sent as the result of, another document, and a re-submit of a previous document never wakes the worker.
2. **AC2 — PRE-002:** navigating with "Précédent" and "Suivant", in any order and any number of times, never loses a decision already made on a document (accept, reject, edit, type change, added row).
3. **AC3 — PRE-003:** an action on a row added by hand acts on that row only. The rule: a row with no stored candidate key (a row added by hand) is its own group of one, so accept, reject and edit on it reach no other row. Detected rows keep 10.8's grouping by their stored (text, type) key, which never includes a hand-added row.

### Fix Design (pre-decided; AC1 subject to Q1)

The SM prototype (`make_proto_110.ts`) implements it; the dev writes the real code.

**AC1 (PRE-001): only the waiting document can be validated.**

1. **The batch screen knows which document the worker waits on.** `BatchScreen` gets `_awaiting_doc_index: int | None` and `_review_states: dict[int, GUIValidationState]`, both created in `__init__` (`batch.py:52-63`), so code paths that skip `_launch_worker` (10.8's T8 harness, this story's T6–T10) still work, and reset in `_launch_worker` next to `:648-649`. `_on_validation_required` sets `_awaiting_doc_index = doc_index` before navigating (`:917`). It is cleared when a list is accepted (step 2), in `_on_finished` (`:770`) and in `_on_error` (`:810`). A read-only property `awaiting_doc_index` exposes it. Why not `_docs_completed`: it is moved by the `DOC_DONE` progress messages (`:718-721`); the worker's own `validation_required` names the document it waits on.
2. **The list carries its document.** `validation_complete = Signal(int, object)` (`validation.py:46`): (document index, validated list). `BatchScreen._on_validation_complete(doc_index, validated_entities)` (`batch.py:919`): if `doc_index != self._awaiting_doc_index`, it logs `batch_validation_result_refused` with the two indices only (no entity text; [Source: architecture/19-coding-standards.md#19.1, rule 3]) and returns: nothing stored, nothing submitted, no navigation. Otherwise it clears `_awaiting_doc_index`, stores the list under `doc_index`, sets that row's status, submits and navigates as today. The disconnect and connect of `:699-710` keep working with the same bound method.
3. **The screen applies the rule.** In batch mode, after the review is shown (step 2 of AC2 below), the finalize button is enabled only when the shown document is the waiting one (`batch.awaiting_doc_index == self._doc_index`); otherwise it is disabled and the line is shown. Order matters: `set_context` updates the batch header at `:352-354`, then `start_validation` re-enables the button at `:319`, so the rule runs last. `_on_finalize` in batch mode returns without emitting when the shown document is not the waiting one: a guard behind the disabled button (T1[handler]). It emits `(self._doc_index, validated)` otherwise.
4. **The line.** A `QLabel` with object name `batchDocumentNotice`, word-wrapped, placed right under the batch header (`validation.py:108-109`), hidden by default, visible only in batch mode on a document other than the waiting one. Its text is set in `retranslateUi` and is Lionel's wording (Q2; STOP, Task 2.4). No separate accessible-name string: a label's text is what assistive tools read.
5. **`_validation_results`** stays, keyed by the accepted document's index. It still has no reader (Notes for the PO and PM, item 5).

**What the user sees (option A of Q1; the line's wording is Q2's):**
- On the document waiting for validation ("Document 2 de 3"): nothing changes. "Valider et continuer ▶" (or "Valider et terminer ▶") is active, and no line shows.
- After "◀ Précédent", on a document already pseudonymized: the same button, greyed out, and the line under the "Document X de Y" header. The rows show the decisions the document was written with.
- "Suivant ▶" leads back towards the waiting document; on it the button is active again and the line is gone, with every decision made there still in place.

**AC2 (PRE-002): each document keeps its review state.**

1. **Where it lives:** one `GUIValidationState` per document of the batch run, kept by `BatchScreen` in `_review_states` (AC1, step 1), with the same lifetime as the context cache. Two small methods: `review_state(doc_index) -> GUIValidationState | None` and `store_review_state(doc_index, state)`. The validation screen reaches the batch screen as it already does for the cache (`validation.py:704-711`, `:763-770`).
2. **How it is restored:** in `set_context`, batch mode: if the batch screen keeps a state for `doc_index`, the screen re-attaches it: it sets `_validation_state`, binds the editor and the panel (`set_validation_state`, `entity_editor.py:91-96`, `entity_panel.py:197-201`), refreshes the status label, hides the finalization progress, and keeps the `DetectionResult` it built. No `init_from_detection_result`, no `classify_known_entities`, no new signal connection: the state's signals were connected once, when it was created (`validation.py:301-303`). Otherwise the screen builds the review as today (the body of today's `start_validation`, moved to a private `_begin_review`) and stores the new state with `store_review_state`.
3. **Why the object, not a snapshot:** it already holds every kind of decision (row states; type and text edits made in place; custom pseudonyms; rows added by hand; the undo history). A snapshot replayed onto a rebuilt state would have to redo each of them, and the rebuild would run the known-entity pass again, which confirms a known name the user rejected (`validation_state.py:121-124`; SM check T4 on `base`).
4. **The cache overwrite goes** (`batch.py:931-933`): the kept state is what "◀ Précédent" shows, so the cached `entities` stay the detections the state was built from.
5. **Lifetime:** the states stay alive for the batch run. They are children of the validation screen (`GUIValidationState(self)`, `validation.py:292`), as today, where every `start_validation` makes a new child state and never frees the old one; nothing is freed explicitly (the screen may still show the last one).
6. **With Story 10.9 merged:** its batch edit and type change are macros on the same state, kept the same way.

**AC3 (PRE-003): a row added by hand is a group of one.** `_group_ids` (`validation_state.py:164-176`): a row without a stored key returns `[review.entity_id]`; a detected row keeps its stored (text, type) lookup in `_group_index` (`(key[0], key[2])`), which holds detected rows only (`:92-102`; `_AddEntityCommand.redo` `:598-617` never adds to it). The docstring says so. Accept and reject on a hand-added row then reach that row only; with Story 10.9 merged, its text edit and type change too. Nothing else in the file changes.

**AC11: the single-document entry leaves batch mode.** The public `start_validation` (called by `processing.py:369`) sets `_batch_mode = False`, hides the batch header, the "Annuler le lot" button and the line, shows "◀ Retour", calls `retranslateUi`, then builds the review (`_begin_review`). `set_context` calls `_begin_review` directly, so batch mode is not reset there. `processing.py` does not change.
