14. **AC14 — Group actions keep the decisions made on one place (story-level; Lionel, 2026-10-14: "Skip rejected (Rec.)" for a group accept, then Q5 "Skip your own (Rec.)", Q6 "Skip rejected (Rec.)", Q7 "Whole group back (Rec.)", and "Stay rejected (Rec.)" for Ctrl+Shift+R).** In the desktop app, in single-document and batch validation:
    - **(a) One memory per row.** For each row, the review state remembers whether the row's current decision was made on that place alone (the row's "own" decision) or came with an action that reached several places. Its own: a row ticked in the list and accepted or rejected with the selection; a row rejected with Ctrl+Shift+R (Lionel, 2026-10-14, the PO's P1); a row added by hand; a custom pseudonym (it acts on one row); and an accept, a reject, a correction or a type change that reached that row only. A row reached by a group action keeps the memory it had if its decision stays of the same kind (kept: accepté, modifié, ajouté; or dropped: rejeté), and loses it otherwise. One undo restores the rows and their memory; a redo gives them back as the action left them. The memory stays with the document's review state when the user moves between documents (AC2).

    - **(e) "Accepter les déjà connues"** accepts the known places still to review only: a rejected place stays rejected, and a corrected place stays "modifié", with its correction (Q6).
    - **(f) Not changed:** the rows these act on: the list selection, exactly the rows ticked; "accept all of type", Ctrl+Shift+A and Ctrl+Shift+R, the rows still to review only. What changes is the memory (a): the list selection and Ctrl+Shift+R make their decisions the user's own, so a later correction or group accept leaves the places rejected with Ctrl+Shift+R as they are; "accept all of type" and Ctrl+Shift+A make theirs follow the group, so a later reject of the name still reaches the places they accepted.

### Product Constraints (non-negotiable, verbatim from the epic)

[Source: prd/epic-10-v2.3-detection-precision-quick-wins.md#Product Constraints]

These apply to every story in this epic. A story that cannot meet its goal inside them stops and goes back to Lionel; it does not relax them.

1. **Local NLP only.** No LLM, no generative model, no API call, no cloud service, no telemetry. Every change is a deterministic rule, lexicon or pattern that runs offline.
2. **No encoder NER models.** Introducing a transformer/encoder NER model (e.g. CamemBERT-NER) is a Lionel decision that belongs to Epic 9. It must not be introduced in this epic, including as an optional dependency or experiment committed to the repo.
3. **Mandatory human validation stays.** No auto-accept mode, no `--no-validate`, no confidence-based skipping. Precision gains reduce the reviewer's workload; they do not replace the reviewer.
4. **No user data** for training, tuning or evaluation. All corpus and held-out documents are synthetic.
5. **Recall over precision.** Missing a real person is worse than showing an extra candidate. Any drop in overall recall or in any per-type recall needs Lionel's sign-off (gate G3).
6. **No public accuracy claim without CI evidence.** Every number that reaches README, FAQ, docs, CHANGELOG or the QA report comes from a cited CI accuracy run (gate G1).

### Fix Design (pre-decided; AC1 as Lionel answered Q1 and Q1b; AC3 and AC13 as he answered Q3 and its correction; AC14 as he answered on 2026-10-14, Q5, Q6 and Q7 included)

**AC1 (PRE-001): only the waiting document can be validated.**

1. **The batch screen knows which document the worker waits on.** `BatchScreen` gets `_awaiting_doc_index: int | None` and `_review_states: dict[int, GUIValidationState]`, both created in `__init__` (`batch.py:52-63`), so code paths that skip `_launch_worker` (10.8's T8 harness, this story's T6–T10) still work, and reset in `_launch_worker` next to `:648-649`. `_on_validation_required` sets `_awaiting_doc_index = doc_index` before navigating (`:917`). It is cleared when a list is accepted (step 2), in `_on_finished` (`:770`) and in `_on_error` (`:810`). A read-only property `awaiting_doc_index` exposes it. Why not `_docs_completed`: it is moved by the `DOC_DONE` progress messages (`:718-721`); the worker's own `validation_required` names the document it waits on.
2. **The list carries its document.** `validation_complete = Signal(int, object)` (`validation.py:46`): (document index, validated list). `BatchScreen._on_validation_complete(doc_index, validated_entities)` (`batch.py:919`): if `doc_index != self._awaiting_doc_index`, it logs `batch_validation_result_refused` with the two indices only (no entity text; [Source: architecture/19-coding-standards.md#19.1, rule 3]) and returns: nothing stored, nothing submitted, no navigation. Otherwise it clears `_awaiting_doc_index`, stores the list under `doc_index`, sets that row's status, submits and navigates as today. The disconnect and connect of `:699-710` keep working with the same bound method.
3. **The screen applies the rule.** In batch mode, after the review is shown (step 2 of AC2 below), the finalize button is enabled only when the shown document is the waiting one **and** the review shown is the one the batch screen keeps for it: `batch.awaiting_doc_index == self._doc_index and batch.review_state(self._doc_index) is self._validation_state` (the identity guard, PO F1). Otherwise it is disabled and the line is shown. The identity guard refuses a single document whose screen still carries batch fields, whatever path led there (Consumer Trace #28; PO probe `midbatch_single_stale_mode`). Order matters: `set_context` updates the batch header at `:352-354`, then `start_validation` re-enables the button at `:319`, so the rule runs last. `_on_finalize` in batch mode applies the same check and returns without emitting when it fails: a guard behind the disabled button (T1[handler]). It emits `(self._doc_index, validated)` otherwise.
4. **The line.** A `QLabel` with object name `batchDocumentNotice`, word-wrapped, placed right under the batch header (`validation.py:108-109`), hidden by default, visible only in batch mode on a document other than the waiting one. Its text, set in `retranslateUi`, is exactly AC12's string (Lionel, 2026-10-14), French only. No separate accessible-name string: a label's text is what assistive tools read.
5. **`_validation_results`** stays, keyed by the accepted document's index. It still has no reader (Notes for the PO and PM, item 3).

**What the user sees (Lionel: Q1 "Greyed out", Q1b "Allowed, not applied", Q2b the text of AC12):**
- On the document waiting for validation ("Document 2 de 3"): nothing changes. "Valider et continuer ▶" (or "Valider et terminer ▶") is active, and no line shows.
- After "◀ Précédent", on a document already validated: the same button, greyed out, and under the "Document X de Y" header the line « Ce document a déjà été validé. Les modifications faites ici ne seront pas appliquées. Revenez au document en attente de validation avec le bouton Suivant. » The rows show the decisions the document was validated with. Accept, reject, edit and the other actions still work there, through the editor's right-click menu and keys and the panel (A1): the change shows on screen, stays with that document, and is never applied.
- "Suivant ▶" leads back towards the waiting document; on it the button is active again and the line is gone, with every decision made there still in place.
- A single document opened with Ctrl+O or from the recent-files menu while a batch waits shows as a single document ("Finaliser ▶", "◀ Retour", no batch header); validating it never touches the batch.
- Correcting a name, or changing its type, on any row reaches every place of that name and type, found or added by hand, with one pseudonym, except the places the user rejected on their own; accepting or rejecting a found place reaches every found place of the name, and a place added by hand is accepted or rejected alone (Lionel's Q3 and its correction; Fix Design, AC13).
- A decision made on one place (ticked in the list, a place added by hand, a custom pseudonym, a place rejected with Ctrl+Shift+R) is not undone by an action on the whole name: rejecting the name from another place leaves a place accepted on its own accepted; accepting the name brings back every place except one rejected on its own. "Accepter les déjà connues" leaves rejected and corrected places as they are (Lionel's Q5–Q7 and his Ctrl+Shift+R answer; Fix Design, AC14).

**AC2 (PRE-002): each document keeps its review state.**

1. **Where it lives:** one `GUIValidationState` per document of the batch run, kept by `BatchScreen` in `_review_states` (AC1, step 1), with the same lifetime as the context cache. Two small methods: `review_state(doc_index) -> GUIValidationState | None` and `store_review_state(doc_index, state)`. The validation screen reaches the batch screen as it already does for the cache (`validation.py:704-711`, `:763-770`).
2. **How it is restored:** in `set_context`, batch mode: if the batch screen keeps a state for `doc_index`, the screen re-attaches it: it sets `_validation_state`, binds the editor and the panel (`set_validation_state`, `entity_editor.py:91-96`, `entity_panel.py:197-201`), refreshes the status label, hides the finalization progress, and keeps the `DetectionResult` it built. No `init_from_detection_result`, no `classify_known_entities`, no new signal connection: the state's signals were connected once, when it was created (`validation.py:301-303`). Otherwise the screen builds the review as today (the body of today's `start_validation`, moved to a private `_begin_review`) and stores the new state with `store_review_state`.
3. **Why the object, not a snapshot:** it already holds every kind of decision (row states; type and text edits made in place; custom pseudonyms; rows added by hand; the undo history). A snapshot replayed onto a rebuilt state would have to redo each of them, and the rebuild would run the known-entity pass again, which confirms a known name the user rejected (`validation_state.py:121-124`; SM check T4 on `base`).
4. **The cache overwrite goes** (`batch.py:931-933`): the kept state is what "◀ Précédent" shows, so the cached `entities` stay the detections the state was built from.
5. **Lifetime:** the states stay alive for the batch run. They are children of the validation screen (`GUIValidationState(self)`, `validation.py:292`), as today, where every `start_validation` makes a new child state and never frees the old one; nothing is freed explicitly (the screen may still show the last one).
6. **With Story 10.9 merged:** its batch edit and type change are macros on the same state, kept the same way.

**AC3 (PRE-003): a row added by hand is a group of one.** `_group_ids` (`validation_state.py:164-176`): a row without a stored key returns `[review.entity_id]`; a detected row keeps its stored (text, type) lookup in `_group_index` (`(key[0], key[2])`), which holds detected rows only (`:92-102`; `_AddEntityCommand.redo` `:598-617` never adds to it). The docstring says so. Accept and reject on a hand-added row then reach that row only. Text corrections and type changes do not use `_group_ids` (Fix Design AC13). In this file AC3 changes only `_group_ids` and its docstring.

**AC11: the single-document entry leaves batch mode.** The public `start_validation` (called by `processing.py:369`, the end of every single-document route: Ctrl+O, the recent-files menu and the home screen; Consumer Trace #28) sets `_batch_mode = False`, hides the batch header, the "Annuler le lot" button and the line, shows "◀ Retour", calls `retranslateUi`, then builds the review (`_begin_review`). `set_context` calls `_begin_review` directly, so batch mode is not reset there. A batch that waits keeps waiting: its review state is still kept by the batch screen, and in single-document mode the single document's list goes to `_start_finalization`, never to the batch screen. The identity guard (AC1, step 3) is only a fallback, for a screen that would still carry stale batch fields. `processing.py`, `home.py` and `main_window.py` do not change. A way back from the single document to the waiting batch document is not part of this story (epic Follow-up (f)).

**AC13 (AC3's edit rule; Lionel's Q3 and its correction; built on 10.9's merged code).** Accept and reject keep `_group_ids` exactly as AC3 above sets it. Text corrections and type changes use 10.9's `_action_rows`, which this story widens:
1. **A fixed name for every row.** A detected row's name is its stored key's (text, type) (`_candidate_key_by_id`, 10.8). A row added by hand gets one too: `_hand_key_by_id: dict[str, tuple[str, str]]`, created in `__init__` and cleared in `init_from_detection_result` next to 10.9's `_edited_spans_by_id`, filled by `_AddEntityCommand.redo` with the text and type the row was added with and emptied for that row by its `undo`. A private `_name_key(review) -> tuple[str, str] | None` returns the one or the other. Why fixed: `_ChangeTypeCommand` retypes `review.entity` in place, so a name read from the row's current type would drop a retyped row out of its group before the next correction (the same reason 10.8 stores keys).
2. **`_action_rows(review)`:** the row itself first, always (even if it is rejected), then every other row of the session whose `_name_key` equals the row's, found or added by hand, **except a row rejected on its own** (AC14 (d); Lionel's Q7, 2026-10-14). It no longer reads `_group_ids`. **10.9's rejected-places filter is replaced:** 10.9 put it inside `_action_rows` (`a9c447a`; `other.state != EntityReviewState.REJECTED`, `:220` at `bdd3743`). The rewritten function skips instead a row whose state is REJECTED and which holds that decision on its own (`_decided_alone(other, _DROPPED)`, Fix Design AC14 step 1), for found and hand-added rows alike. A row rejected only by a group reject is reached and becomes "modifié" (Q7); a row rejected with Ctrl+Shift+R is the user's own, so it is not (the Ctrl+Shift+R answer). In batch validation that is every row of the name; in single-document validation it is the found row of the name (which stands for its variant occurrences) and the rows added by hand.
3. **Its docstring** says so: the rows a text correction or a type change acts on are every row of the same name and type, found or added by hand (Lionel's Q3 on Story 10.10); accept and reject do not use it, they use `_group_ids`, where a row added by hand is alone. 10.9's sentence "a row added by hand joins the detected row of its text and type" goes.
4. **Nothing else changes in 10.9's code.** `modify_entity_text` and `change_entity_type` already make one macro over `_action_rows` and place every other row with `_locate_modified_span` from its own current span, and `_occurrence_spans_for_edit` already returns `None` for a row added by hand (no stored key), so a hand row is placed and sent like a batch row. As in 10.9, a row reached by a correction becomes "modifié"; a row rejected on its own is never reached (step 2), so it stays rejected and is left as is in the output. `modify_entity_text` and `change_entity_type` also pass AC14's `alone` to their commands (Fix Design AC14, step 3).
5. **What the user sees:** correct the name on any row, found or added, and every row of that name and type shows the corrected text, with one pseudonym in the output, except the places the user rejected on their own, which stay rejected and are left as is (Lionel's "Saint-Zorbal" case); a place rejected only with the rest of its name takes the correction (Q7); one Ctrl+Z reverts the whole correction. Accept or reject a found place: every found place of that name and type follows ("Accepter le groupe"), the places added by hand do not. Accept or reject a place added by hand: that place only.

**AC14 (group actions keep the decisions made on one place; Lionel, 2026-10-14: the group-accept answer, then Q5, Q6, Q7 and the Ctrl+Shift+R answer).** In `validation_state.py` (lines at `bdd3743`, 10.9's head; Task 0.4), and two handlers of `validation.py`:
1. **The memory.** `GUIValidationState.__init__` creates `_own_ids: set[str]`, the ids of the rows whose current decision is their own, with a comment, next to `_hand_key_by_id`; `init_from_detection_result` clears it. Two module constants name the kinds of decision: `_KEPT` = {CONFIRMED, MODIFIED, ADDED} (the row is sent) and `_DROPPED` = {REJECTED}; PENDING is neither. Two private helpers: `_decided_alone(review, kinds)`, true when the row's id is in `_own_ids` and its state is in `kinds`; and `_set_own(entity_id, own)`. The known-entity pass (`classify_known_entities`) never touches the set. Why a set on the state and not a field of `EntityReview`: Decisions Recorded, "Pre-decided by the SM".
2. **The commands keep it exact under undo and redo.** `_SingleActionCommand`, `_ModifyTextCommand` and `_ChangeTypeCommand` take a keyword `alone: bool = False`. In `redo`, each records the row's flag (`entity_id in _own_ids`) next to the old state it already records, applies its change, then sets the flag to `alone or (old flag and _same_kind(old state, new state))`; `_same_kind` is true when both states are in `_KEPT`, or both in `_DROPPED`. In `undo`, each restores the recorded flag with the old state. `_ChangePseudonymCommand` always sets the flag (it acts on one row) and restores it on undo. `_AddEntityCommand.redo` adds the new row's id; its `undo` removes it with the row. A redo after an undo starts from the state and the flag the undo restored, so it gives back exactly what the first run gave.
3. **Who passes `alone=True`.** `accept_entity`, `reject_entity`, `modify_entity_text` and `change_entity_type`: in their one-command branch, that is when, after the skips of step 4, they reach the row acted on only; in their macro branch every command gets `alone=False`, the row acted on included (Decisions Recorded, "How "on its own" is read"). `bulk_accept(entity_ids, alone=True)` and `bulk_reject(entity_ids, alone=True)`: the list selection keeps the default. `ValidationScreen._handle_bulk_action` takes `alone: bool = True` and passes it on; `_on_accept_all` (Ctrl+Shift+A, which calls it with the pending rows) passes `alone=False`; `_on_reject_all` (Ctrl+Shift+R) does not change and keeps the default, so each place it rejects counts as rejected by the user (Lionel, 2026-10-14, the PO's P1). `add_entity` and `change_pseudonym` set the flag through their commands (step 2). `accept_all_of_type` and `accept_all_known` keep the default, `alone=False`.
4. **The skips; the row acted on is always changed.** `accept_entity`: the row clicked, then every other id of `_group_ids(review)` except a row for which `_decided_alone(other, _DROPPED)` (Q7; it replaces v1.4's "state is not REJECTED"). `reject_entity`: the row clicked, then every other id except a row for which `_decided_alone(other, _KEPT)` (Q5). `_action_rows` (AC13 step 2): every other row of the name except `_decided_alone(other, _DROPPED)` (Q7). The rest stays: one command when one row remains; otherwise one "Accepter le groupe", "Rejeter le groupe", "Modifier le texte du groupe" or "Changer le type du groupe" macro. A skipped row gets no command, so undo and redo never touch it.
5. **"Accepter les déjà connues"** (`accept_all_known`): the known rows whose state is PENDING, in place of the known rows not CONFIRMED (Q6). A rejected row and a corrected row are left as they are.
6. **Not changed:** the rows `bulk_accept` and `bulk_reject` act on (exactly the ticked rows); `accept_all_of_type` and the pending-row lists of Ctrl+Shift+A and Ctrl+Shift+R; `_group_ids` (AC3); `_validated_rows`; and what each command does to a row's state, text, span, type and pseudonym.
7. **Docstrings:** `accept_entity`, `reject_entity`, `_action_rows` and `accept_all_known`, and the comment on `_own_ids`, say what they skip and cite Lionel's answers (2026-10-14; Q5–Q7).
8. **What the user sees:** in batch validation, "Saint-Zorbal" rejected on its own stays rejected when the name is accepted again from another place, and is accepted when the user accepts that place itself; a place accepted on its own (ticked in the list) stays accepted and pseudonymized when the name is rejected from another place; accepting the name and then rejecting it from any place rejects every place; after a group reject made by mistake, accepting the name from any place brings back every place except one rejected on its own, and a correction reaches them the same way; "Accepter les déjà connues" leaves rejected places rejected and corrected places "modifié". The places rejected with Ctrl+Shift+R stay rejected when the name is corrected or accepted again. In single-document validation, nothing visible changes but "Accepter les déjà connues" (it no longer accepts again a known name the user rejected).
