### Product Constraints (non-negotiable, verbatim from the epic)

[Source: prd/epic-10-v2.3-detection-precision-quick-wins.md#Product Constraints]

These apply to every story in this epic. A story that cannot meet its goal inside them stops and goes back to Lionel; it does not relax them.

1. **Local NLP only.** No LLM, no generative model, no API call, no cloud service, no telemetry. Every change is a deterministic rule, lexicon or pattern that runs offline.
2. **No encoder NER models.** Introducing a transformer/encoder NER model (e.g. CamemBERT-NER) is a Lionel decision that belongs to Epic 9. It must not be introduced in this epic, including as an optional dependency or experiment committed to the repo.

4. **No user data** for training, tuning or evaluation. All corpus and held-out documents are synthetic.

6. **No public accuracy claim without CI evidence.** Every number that reaches README, FAQ, docs, CHANGELOG or the QA report comes from a cited CI accuracy run (gate G1).

### Fix Design (pre-decided; AC1 as Lionel answered Q1 and Q1b; AC3 and AC13 as he answered Q3 and its correction)

The SM prototype implements it: `make_proto_110.ts` and `make_proto_110b.ts` (AC1, AC2, AC3's accept and reject rule, AC11), then `make_proto_110c.ts` on 10.9's code (AC13). The dev writes the real code, on 10.9's merged code (Task 0.4).

**AC1 (PRE-001): only the waiting document can be validated.**

1. **The batch screen knows which document the worker waits on.** `BatchScreen` gets `_awaiting_doc_index: int | None` and `_review_states: dict[int, GUIValidationState]`, both created in `__init__` (`batch.py:52-63`), so code paths that skip `_launch_worker` (10.8's T8 harness, this story's T6–T10) still work, and reset in `_launch_worker` next to `:648-649`. `_on_validation_required` sets `_awaiting_doc_index = doc_index` before navigating (`:917`). It is cleared when a list is accepted (step 2), in `_on_finished` (`:770`) and in `_on_error` (`:810`). A read-only property `awaiting_doc_index` exposes it. Why not `_docs_completed`: it is moved by the `DOC_DONE` progress messages (`:718-721`); the worker's own `validation_required` names the document it waits on.
2. **The list carries its document.** `validation_complete = Signal(int, object)` (`validation.py:46`): (document index, validated list). `BatchScreen._on_validation_complete(doc_index, validated_entities)` (`batch.py:919`): if `doc_index != self._awaiting_doc_index`, it logs `batch_validation_result_refused` with the two indices only (no entity text; [Source: architecture/19-coding-standards.md#19.1, rule 3]) and returns: nothing stored, nothing submitted, no navigation. Otherwise it clears `_awaiting_doc_index`, stores the list under `doc_index`, sets that row's status, submits and navigates as today. The disconnect and connect of `:699-710` keep working with the same bound method.
3. **The screen applies the rule.** In batch mode, after the review is shown (step 2 of AC2 below), the finalize button is enabled only when the shown document is the waiting one **and** the review shown is the one the batch screen keeps for it: `batch.awaiting_doc_index == self._doc_index and batch.review_state(self._doc_index) is self._validation_state` (the identity guard, PO F1). Otherwise it is disabled and the line is shown. The identity guard refuses a single document whose screen still carries batch fields, whatever path led there (Consumer Trace #28; PO probe `midbatch_single_stale_mode`). Order matters: `set_context` updates the batch header at `:352-354`, then `start_validation` re-enables the button at `:319`, so the rule runs last. `_on_finalize` in batch mode applies the same check and returns without emitting when it fails: a guard behind the disabled button (T1[handler]). It emits `(self._doc_index, validated)` otherwise.
4. **The line.** A `QLabel` with object name `batchDocumentNotice`, word-wrapped, placed right under the batch header (`validation.py:108-109`), hidden by default, visible only in batch mode on a document other than the waiting one. Its text, set in `retranslateUi`, is exactly AC12's string (Lionel, 2026-10-14), French only. No separate accessible-name string: a label's text is what assistive tools read.
5. **`_validation_results`** stays, keyed by the accepted document's index. It still has no reader (Notes for the PO and PM, item 4).

**What the user sees (Lionel: Q1 "Greyed out", Q1b "Allowed, not applied", Q2b the text of AC12):**
- On the document waiting for validation ("Document 2 de 3"): nothing changes. "Valider et continuer ▶" (or "Valider et terminer ▶") is active, and no line shows.
- After "◀ Précédent", on a document already validated: the same button, greyed out, and under the "Document X de Y" header the line « Ce document a déjà été validé. Les modifications faites ici ne seront pas appliquées. Revenez au document en attente de validation avec le bouton Suivant. » The rows show the decisions the document was validated with. Accept, reject, edit and the other actions still work there, through the editor's right-click menu and keys and the panel (A1): the change shows on screen, stays with that document, and is never applied.
- "Suivant ▶" leads back towards the waiting document; on it the button is active again and the line is gone, with every decision made there still in place.
- A single document opened with Ctrl+O or from the recent-files menu while a batch waits shows as a single document ("Finaliser ▶", "◀ Retour", no batch header); validating it never touches the batch.
- Correcting a name, or changing its type, on any row reaches every place of that name and type, found or added by hand, with one pseudonym; accepting or rejecting a found place reaches every found place of the name, and a place added by hand is accepted or rejected alone (Lionel's Q3 and its correction; Fix Design, AC13).

**AC2 (PRE-002): each document keeps its review state.**

1. **Where it lives:** one `GUIValidationState` per document of the batch run, kept by `BatchScreen` in `_review_states` (AC1, step 1), with the same lifetime as the context cache. Two small methods: `review_state(doc_index) -> GUIValidationState | None` and `store_review_state(doc_index, state)`. The validation screen reaches the batch screen as it already does for the cache (`validation.py:704-711`, `:763-770`).
2. **How it is restored:** in `set_context`, batch mode: if the batch screen keeps a state for `doc_index`, the screen re-attaches it: it sets `_validation_state`, binds the editor and the panel (`set_validation_state`, `entity_editor.py:91-96`, `entity_panel.py:197-201`), refreshes the status label, hides the finalization progress, and keeps the `DetectionResult` it built. No `init_from_detection_result`, no `classify_known_entities`, no new signal connection: the state's signals were connected once, when it was created (`validation.py:301-303`). Otherwise the screen builds the review as today (the body of today's `start_validation`, moved to a private `_begin_review`) and stores the new state with `store_review_state`.
3. **Why the object, not a snapshot:** it already holds every kind of decision (row states; type and text edits made in place; custom pseudonyms; rows added by hand; the undo history). A snapshot replayed onto a rebuilt state would have to redo each of them, and the rebuild would run the known-entity pass again, which confirms a known name the user rejected (`validation_state.py:121-124`; SM check T4 on `base`).
4. **The cache overwrite goes** (`batch.py:931-933`): the kept state is what "◀ Précédent" shows, so the cached `entities` stay the detections the state was built from.
5. **Lifetime:** the states stay alive for the batch run. They are children of the validation screen (`GUIValidationState(self)`, `validation.py:292`), as today, where every `start_validation` makes a new child state and never frees the old one; nothing is freed explicitly (the screen may still show the last one).
6. **With Story 10.9 merged:** its batch edit and type change are macros on the same state, kept the same way.

**AC3 (PRE-003): a row added by hand is a group of one.** `_group_ids` (`validation_state.py:164-176`): a row without a stored key returns `[review.entity_id]`; a detected row keeps its stored (text, type) lookup in `_group_index` (`(key[0], key[2])`), which holds detected rows only (`:92-102`; `_AddEntityCommand.redo` `:598-617` never adds to it). The docstring says so. Accept and reject on a hand-added row then reach that row only; with Story 10.9 merged, its text edit and type change too. Nothing else in the file changes.

**AC11: the single-document entry leaves batch mode.** The public `start_validation` (called by `processing.py:369`, the end of every single-document route: Ctrl+O, the recent-files menu and the home screen; Consumer Trace #28) sets `_batch_mode = False`, hides the batch header, the "Annuler le lot" button and the line, shows "◀ Retour", calls `retranslateUi`, then builds the review (`_begin_review`). `set_context` calls `_begin_review` directly, so batch mode is not reset there. A batch that waits keeps waiting: its review state is still kept by the batch screen, and AC1's rule refuses the single document's list (step 3). `processing.py`, `home.py` and `main_window.py` do not change. A way back from the single document to the waiting batch document is not part of this story (epic Follow-up (f)).

**AC13 (AC3's edit rule; Lionel's Q3 and its correction; built on 10.9's merged code).** Accept and reject keep `_group_ids` exactly as AC3 above sets it. Text corrections and type changes use 10.9's `_action_rows`, which this story widens:
1. **A fixed name for every row.** A detected row's name is its stored key's (text, type) (`_candidate_key_by_id`, 10.8). A row added by hand gets one too: `_hand_key_by_id: dict[str, tuple[str, str]]`, created in `__init__` and cleared in `init_from_detection_result` next to 10.9's `_edited_spans_by_id`, filled by `_AddEntityCommand.redo` with the text and type the row was added with and emptied for that row by its `undo`. A private `_name_key(review) -> tuple[str, str] | None` returns the one or the other. Why fixed: `_ChangeTypeCommand` retypes `review.entity` in place, so a name read from the row's current type would drop a retyped row out of its group before the next correction (the same reason 10.8 stores keys).
2. **`_action_rows(review)`:** the row itself first, then every other row of the session whose `_name_key` equals the row's, found or added by hand. It no longer reads `_group_ids`. In batch validation that is every row of the name; in single-document validation it is the found row of the name (which stands for its variant occurrences) and the rows added by hand.
3. **Its docstring** says so: the rows a text correction or a type change acts on are every row of the same name and type, found or added by hand (Lionel's Q3 on Story 10.10); accept and reject do not use it, they use `_group_ids`, where a row added by hand is alone. 10.9's sentence "a row added by hand joins the detected row of its text and type" goes.
4. **Nothing else changes in 10.9's code.** `modify_entity_text` and `change_entity_type` already make one macro over `_action_rows` and place every other row with `_locate_modified_span` from its own current span, and `_occurrence_spans_for_edit` already returns `None` for a row added by hand (no stored key), so a hand row is placed and sent like a batch row. As in 10.9, a row reached by a correction becomes "modifiée" whatever its state, a rejected row included (Questions for Lionel, item 4).
5. **What the user sees:** correct the name on any row, found or added, and every row of that name and type shows the corrected text, with one pseudonym in the output; one Ctrl+Z reverts the whole correction. Accept or reject a found place: every found place of that name and type follows ("Accepter le groupe"), the places added by hand do not. Accept or reject a place added by hand: that place only.

def _name_key(self, review: EntityReview) -> tuple[str, str] | None:
    key = self._candidate_key_by_id.get(review.entity_id)          # detected row: 10.8's stored key
    if key is not None:
        return (key[0], key[2])
    return self._hand_key_by_id.get(review.entity_id)              # row added by hand: as added

def _action_rows(self, review: EntityReview) -> list[EntityReview]:
    rows, name = [review], self._name_key(review)
    if name is not None:
        rows += [r for r in self._session._entity_reviews
                 if r is not review and self._name_key(r) == name]
    return rows

# validation_state.py (AC3, accept and reject)
def _group_ids(self, review: EntityReview) -> list[str]:
    key = self._candidate_key_by_id.get(review.entity_id)
    if key is None:
        return [review.entity_id]
    return self._group_index.get((key[0], key[2]), [review.entity_id])
