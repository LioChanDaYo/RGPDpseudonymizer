### Context

At `main` `0be4073`. The release review's finding 3 (verbatim): "**P0 — Concurrent processing writes pseudonyms that were never saved.** [core/document_processor.py:946], [mapping_repository.py:866] Two CLI batch workers can both find **“Élodie Dupont”** absent and generate different pseudonyms. The losing insert correctly returns the winner’s persisted mapping through `_save_batch_with_retry()`, but `_resolve_pseudonyms()` ignores that return value and writes its original pseudonym. Both documents report success; one output has no corresponding saved mapping. This pre-existing integrity bug remains. **Plausibility:** yes—one person appearing in several documents is routine. **Fix:** serialize allocation and persistence, or reconcile replacements and dependent component mappings with the rows actually committed before writing output."

QA's verification (`VERIFY.md`, "Finding 3"; the real `gdpr-pseudo batch` command with its default 4 workers and the real spaCy model, on 8 short documents that all name one person; probes `r230rel/qa/probes/f3_cli_batch.py` and `test_f3_atomic.py`; logs `f3_main.log`, `f3_main8.log`, `f3_v220.log`, `f3det_main.log`):

- `main`: 2 of 11 runs wrote an output file whose pseudonym is not in the database (run 1: the database keeps « Élodie Mendes », `doc1_pseudonymized.txt` reads « Compte rendu : Sandra Meyer a présenté le budget au conseil. »); every run ends « ✓ All files processed successfully ». v2.2.0: 1 of 8 runs.
- Two saves held together (`test_f3_atomic.py -k generated_same_name`): `STORED: {'Elio Silveira'} WRITTEN: {'Elio Silveira', 'Charly Bourgeois'}`.
- QA: "REALISTIC. `gdpr-pseudo batch ./dossier/` is the simplest batch command, its default is 4 parallel workers, and one person appearing in several files of one folder is the normal case. It needs no second program." QA's lean: block.

**Why** (re-read at `0be4073`, Code Map): each worker of the parallel batch is its own process with its own `DocumentProcessor` and its own connection to the one database file (`cli/commands/batch.py:73-139`, `Pool` `:240`; `--workers` defaults to 4, `cli/config.py:55`). For each document a worker reloads the saved rows (`_reset_pseudonym_state`, `core/document_processor.py:1005-1023`), then for each name looks it up (`find_by_full_name_and_type`, `:905`), and when the name is absent chooses a new pseudonym in memory (`_assign_new_pseudonym`, `:930`), writes it into the replacements (`:942`), and only at the end saves the new rows (`save_batch`, `:946`). Nothing stops a second worker from doing the same between the first one's look-up and its save. The save that comes second fails on the database's one-row-per-(name, type) rule (`data/models.py:30-34`), falls back to one row at a time and returns the row the other worker kept (`_save_batch_with_retry`, `data/repositories/mapping_repository.py:842-883`, the look-up `:871`), but `_resolve_pseudonyms` drops that return value: the file is written with the pseudonym chosen in memory.

**The same gap reaches further than the full name** (measured by the SM, Reproduction Evidence; each case fails on `main` with two saves held together):

- **A name's parts.** The library builds a person's pseudonym from a first-name part and a last-name part and reuses them (« Zorbal Mestrix » takes the first-name part of « Zorbal Quentrix », a lone « Quentrix » takes its last-name part; `pseudonym/assignment_engine.py:340-381`, `core/document_processor.py:621-671`). A worker that loses the save of « Zorbal Quentrix » has also written its own last-name part for the lone « Quentrix » of the same document; and two workers that each choose a first-name part for « Zorbal » save two different ones, so the database no longer has one first-name pseudonym for « Zorbal ».
- **Places and organisations:** the same as persons (`LOCATION`, `ORG`).
- **Two people, one pseudonym.** The library avoids the pseudonyms already saved (`_used_pseudonyms`, `pseudonym/library_manager.py:442`; `load_existing_mappings` `:761`), but only those it read before the other worker saved. With the `neutral_id` theme the pseudonyms are counters (« PER-001 »), so two workers that each meet a new person both give « PER-001 »: two different people saved with one pseudonym (Q2).
- **Two programs on one database** (the old #5; Q1): the desktop app's single-document and batch reviews finalize through the same two functions (`finalize_document`, `process_document`; `gui/workers/finalization_worker.py:108`, `:115`, `gui/workers/batch_worker.py:280`, `:399`, `:405`). One desktop app never runs two finalizations at once (Story 10.14), but a desktop app and a CLI batch on one database do. Then the same gap holds, and a custom pseudonym (Stories 10.11, 10.16) can be silently not saved, or saved for two different names: its last check reads the database before the save, outside any lock (`_register_custom_pseudonyms`, `:548-619`, the check `:578-593`; the old #5's second half, `r23codex/review_out.txt`, finding 5).

**Not reached by this story:** a name the detector leaves in clear (no change to detection); a database written by v2.2.0 or an older program running at the same moment, which takes no lock (Notes for the PO and PM).

(« Élodie Dupont », « Élodie Mendes » and the other real-looking names above are QA's and Codex's, in their measurement files only. This story's tests use invented names: AC10.)

## Acceptance Criteria

AC1 to AC12 are story-level (no epic text for 10.22). "AC precisions" adds detail.

1. **AC1 — One document at a time chooses and saves.** For each document, the reload of the saved rows, the last checks of custom pseudonyms, the choice of every new pseudonym and the save of the new rows run as one step under the database's write lock (`BEGIN IMMEDIATE`). No other connection, worker or program saves anything in between; another document that reaches that step waits until the first one's save is committed, then reads what it saved.
2. **AC2 — Every pseudonym written is the one saved.** After the step of AC1, every pseudonym written into an output file is the one the database holds for that name and type, and so is every part of it: a first name or a last name written alone takes the part of the row the database holds, and one real first name or last name has one part in the database, as when the documents run one after the other. This holds for every type (`PERSON`, `LOCATION`, `ORG`), for text files and spreadsheets, in the parallel batch (`process_document` with `skip_validation`), and, per Lionel's Q1, for the desktop app's finalizations and custom pseudonyms beside a batch on the same database (AC precisions).
3. **AC3 — Waiting never breaks a batch, and the review holds no lock.** A document that waits for another one's save waits as long as the lock is held, up to `PSEUDONYM_LOCK_BUSY_TIMEOUT_SECONDS` (300 s), never failing at SQLite's default 5 s. The lock is taken after the review, never during it: while the CLI's `process` or `batch --workers 1` waits for a key, or the desktop app shows its review, another program on the same database can save.
4. **AC4 — What must not change.** Documents processed one after the other give the same outputs and the same saved rows as on `0be4073` (the same names reused, the same parts, the same refusals). No schema, mapping-key, library or detection change; no new visible text. A custom pseudonym that can no longer be used when its document is finalized is refused with Lionel's approved 10.11 texts, as today, and nothing is written for that document.
5. **AC5 — Two people, one pseudonym (per Lionel's Q2).** With the step of AC1, two different names saved in one parallel batch never share a generated pseudonym, with any theme (`neutral_id` included).
6. **AC6 — Tests first, invented names only:** the BMAD dev agent writes the tests of the Test Plan and commits them before the fix. They drive the real `DocumentProcessor` paths with the real database, two documents in two threads on two connections, detection replaced, the library's draw fixed per thread. Two saves are held together: the first document waits at its save until the second one has finished, unless the first already holds the database's write lock. Each expected failure is an `assert` on the written file or the saved rows, made after the preconditions hold; each failing test is `xfail(strict=True, raises=AssertionError)` on the old code.
7. **AC7 — The real batch command, stress and cost.** The real `gdpr-pseudo batch <folder>` command (default workers, real spaCy) gives 0 runs, out of at least 20, where an output file holds a pseudonym the database does not hold for that person, and 0 runs where two saved names share a pseudonym. On `0be4073` the same runs show the failure in some runs only, as the timing allows (Reproduction Evidence, item 6): a set of runs on `0be4073` without a failure is no reading, not a pass. The batch's wall time with and without the fix is measured and reported (Test Plan, S1 and S2).

### AC precisions (story-level)

- **AC1, the step:** `_reset_pseudonym_state(ctx)` (the reload of every saved row into the library: its used pseudonyms, its parts, its counters, and the stored custom values, `core/document_processor.py:1005-1023`) and `_resolve_pseudonyms(...)` (the custom pseudonyms' last check and registration, every look-up, every choice, the save and its commit, `:843-961`). The save's commit (`save_batch`, `mapping_repository.py:792-840`) releases the lock; when the document has no new name, the end of the block commits nothing and releases it; on an error it rolls back and releases it. The output file is written after the block, from the replacements chosen under the lock, which are exactly the rows committed.
- **AC1, why the lock and not "use the rows the save returns" (QA's one-function fix):** taken alone, that fix corrects the full name of the losing document and nothing else. Measured on the SM's mutant `m6` (Reproduction Evidence; it takes the full names from the rows `save_batch` returns): the full-name tests pass, and every test of a part (T3, T4), of two people (T5 ×2), of a custom pseudonym (T7 to T9) still fails. A fix after the save that also corrects the parts (the review's second option) was not measured. It still cannot reach T4, T5 and T9. There the two documents save different names, so both saves succeed and there is no conflict to correct: two first-name parts for one first name (T4), one pseudonym for two people (T5), one chosen pseudonym for two names (T9). Only the lock prevents them. The lost row's parts are already written into the same document, and already saved in its other rows; a custom pseudonym the user chose would be silently replaced by the other worker's. Under the lock the save can never keep another worker's row, so no reconciliation is needed after it, and `_save_batch_with_retry` stays as it is (no caller reaches it for a document that holds the lock).
- **AC2, the paths:** the four places that choose and save are `finalize_document` (`:1218-1267`: the desktop single-document and batch reviews), `process_document` (`:1269-1330`: the CLI's `process` and `batch`, both modes, and the desktop batch without review), `_process_document_tabular` (`:1332-1397`: the same for `.xlsx` and `.csv`) and `finalize_document_tabular` (`:1451-1501`: no caller in the product today, searched at `0be4073`; wrapped the same so that every path follows one rule). In one CLI parallel batch only `process_document` and `_process_document_tabular` race; the desktop paths race only with another program (Q1).
- **AC2, the parts, read as the library reads them:** a lone word whose real word is the saved row's `last_name` (or `first_name`) is written with that row's `pseudonym_last` (or `pseudonym_first`) (`_check_component_match`, `:621-671`; `find_standalone_components`, `assignment_engine.py:340-381`); two saved full names with the same real `first_name` have the same `pseudonym_first`, as two documents run one after the other give.
- **AC3, the wait:** 300 s per document. Measured (Reproduction Evidence): one document holds the lock 0.01 s on an empty database, 0.05 s at 1,000 saved rows and 0.52 s at 10,000 (the reload decrypts every saved row; item 5), so with the most workers the batch allows, eight, the last of them queued waits about 3.6 s at 10,000 rows and pass SQLite's 5 s near 14,000. By the same arithmetic, 300 s leaves room for databases of several hundred thousand rows. That figure is an estimate, not a measurement: SQLite's wait is not a queue, and once a document holds the lock longer than another one takes to detect, the batch runs its documents one at a time. SQLite's default (5 s, `sqlite3.connect`'s `timeout`, which `create_engine` keeps, `data/database.py:190-194`) would make a document fail with « database is locked » after 5 s; the conversion's own lock already waits 30 s (`CONVERSION_BUSY_TIMEOUT_SECONDS`, `:45`). A wait longer than 300 s fails that document only, through the existing error path (`_handle_processing_error`, `:1120-1143`): no output, the batch goes on with the next document, as for any other error.
- **AC3, what a user sees** (read in the code at `0be4073`; the timeout case measured by the PO's probe, `r1022/po/probe_po_1022.txt`, with the lock held from outside and the timeout set to 2 s). No new text. While a document waits, the CLI batch's progress bar does not count it yet and goes on counting the others. The desktop keeps « Application des remplacements... » on screen (`finalization_worker.py:94`); the window does not freeze. A click on cancel takes effect only when the wait ends, as for any finalization today. When a wait runs out, no output file is written. The document's line in the batch's error list, or the desktop's error message, is the database library's own text: « OperationalError: (sqlite3.OperationalError) database is locked » with `[SQL: BEGIN IMMEDIATE]`. On `0be4073` the same case fails after 5 s with « DatabaseError: Batch save failed: (sqlite3.OperationalError) database is locked » and the SQL. Neither is a product text. If the lock is still held, the failed document's audit entry is then lost after SQLite's 5 s (`_log_failed_operation` opens its own connection and catches the error), as on `0be4073`.
- **AC3, the review:** in `process_document` and `_process_document_tabular` the review (`_run_validation`) runs before the block, with the database open but no lock held; the CLI's [P] and the desktop's custom pseudonyms are checked again inside the block (`_register_custom_pseudonyms`), which is why that last check now sees every row saved before it (AC4, T7 to T9).
- **AC4, the refusals:** under the lock, the second of two documents that set or meet the same name's custom pseudonym meets 10.11's last check with the first one's row already saved. When the name now has another pseudonym: « CustomPseudonymError: A pseudonym you chose can no longer be used: the name now has a pseudonym in the mapping database. Nothing was written. »; when the chosen pseudonym is now another name's: « CustomPseudonymError: A pseudonym you chose can no longer be used: it, or a part of it, is now used for another name. Nothing was written. » (Lionel's Q-A on 10.11, `core/custom_pseudonym.py:876-907`). Both are today's texts; no text is new.
- **AC5:** the library's used pseudonyms and its `neutral_id` counters are reloaded inside the step (`_reset_pseudonym_state`), so the second document sees the first one's pseudonyms before it chooses.
- **AC7, what the stress run counts:** a run is counted when an output file holds none of the pseudonyms the database keeps for a person named in its source document (a person the detector left in clear is not counted: that is detection, not this story); a second count is runs where two different saved names share one pseudonym (Q2).

### Fix Design (pre-decided)

1. **`data/database.py`:**
   - Beside `CONVERSION_BUSY_TIMEOUT_SECONDS`: `PSEUDONYM_LOCK_BUSY_TIMEOUT_SECONDS = 300.0`, with a comment: how long a document waits for another document's pseudonyms to be saved (Story 10.22).
   - `pseudonym_lock(db_session: DatabaseSession) -> Iterator[None]`, a `contextlib.contextmanager`, with a docstring that says what it holds and why:
     - `session = db_session.session`; `session.commit()` (ends any transaction this session left open; nothing is pending at the four call sites);
     - `connection = session.connection()`; `connection.exec_driver_sql(f"PRAGMA busy_timeout = {int(PSEUDONYM_LOCK_BUSY_TIMEOUT_SECONDS * 1000)}")`; `connection.exec_driver_sql("BEGIN IMMEDIATE")`;
     - `yield` inside `try`; on any exception `session.rollback()` and re-raise; after the body, `session.commit()` (releases the lock when the body saved nothing; a no-op after the save's own commit).
     - The `busy_timeout` stays on the connection after the block; it is not restored. The session keeps that one pooled connection, so the document's audit entry (`_log_success_operation`, after the block) also waits up to 300 s for another document's step. The PO's probe reads 300000 ms at that write on the prototype and 5000 ms on `0be4073` (`r1022/po/probe_po_1022.txt`).

In thread `A` only, before the real save: a probe connection (`sqlite3.connect(db, timeout=0, isolation_level=None)`, `BEGIN IMMEDIATE`, then `ROLLBACK`, closed) tells whether another connection holds the database's write lock. **Not held** (the unfixed code): `A` waits until `B` has finished (`B` runs its whole document, save included, meanwhile). **Held** (the fix: `A` holds it): `A` goes on at once, since `B` cannot save before it anyway; with `settle=True`, `A` first waits up to 3 s for `B` to enter `_reset_pseudonym_state` (wrapped too, a signal only), so that a fix that reloads the saved rows before taking the lock is caught (the SM's mutant `m2`). `B` starts only once `A` has reached its save (`PRE` if not within 120 s). Both threads joined within 120 s (`PRE` otherwise), each result a `ProcessingResult` (`PRE` otherwise, with the exception shown).
- **The library's draw fixed per thread:** `gdpr_pseudonymizer.pseudonym.library_manager.secrets` replaced by a stand-in whose `choice(seq)` returns, in thread `A`, `seq[0]`, `seq[1]`… in order, and in thread `B` `seq[-1]`, `seq[-2]`… (two workers drawing different values, the real case almost always), or with `same=True` the same order as `A` (T5's second case); any other thread draws as today. So on the unfixed code the two documents always choose different pseudonyms for one name, and never by chance the same.
- **Reading the results:** the saved rows through `open_database` and `SQLiteMappingRepository.find_all()` (name, type, pseudonym, first name, last name, the two parts); the text written at each place by matching the output against the source's unchanged segments (the 10.16 tests' `_replacements`).

### CHANGELOG Entry (Task 4)

`### Fixed`, a new bullet after the last Epic 10 entry (AC8; the PM may prefer other wording). With Q1 and Q2 answered A (the recommendation):

- **One person, one pseudonym, when documents are saved at the same moment (Story 10.22).** `gdpr-pseudo batch` runs several documents at once (4 by default). When two of them met the same new person at the same moment, each chose a pseudonym, the mapping database kept one, and the other document's output file was written with a pseudonym the database never saved: the person appeared as two people across the batch, that file could not be traced back through the database, and its pseudonym could later be given to someone else. The same happened to a first or last name written alone, and two different people could be saved with one pseudonym (with the `neutral_id` theme, « PER-001 » for both). It was already so in v2.2.0. Now a document chooses and saves its pseudonyms while no other document can: the next one waits, then reuses what was saved. The same holds when the desktop app and the command line work on one mapping database at the same time; there, a pseudonym you chose in the desktop review is either saved and used by both, or refused with the usual « can no longer be used » message when the other program saved first, and nothing is written for that document. This never left a name in clear. Detection, the database schema and the accuracy figures do not change.

With Q1 B, the sentence « The same holds when the desktop app … for that document. » is dropped; with Q2 B, « and two different people could be saved with one pseudonym (with the `neutral_id` theme, « PER-001 » for both) » is dropped.
