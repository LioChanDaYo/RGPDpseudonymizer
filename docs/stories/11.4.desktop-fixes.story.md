### Context

#### The first passphrase trap: a short passphrase for a new database (since Story 6.3, 2026-02-18)

Lionel hit it on 2026-11-10, with a 2.3.1 Windows build.

1. **The window accepts any passphrase that is not blank.** In `PassphraseDialog` (`gui/widgets/passphrase_dialog.py`), `_update_confirm_state` (l.266-271) turns « Continuer ▶ » on once the field is not blank and a database is chosen. `_on_confirm` (l.273-279) accepts. « Mémoriser pour cette session » is ticked by default (l.97-100).
2. **The single-document path reuses the remembered passphrase without asking.** `HomeScreen._on_file_selected` (`gui/screens/home.py:271-278`) sends the cached `(db_path, passphrase)` straight to the processing screen.
3. **Creation refuses it on every document.** `ProcessingScreen._start_processing_worker` (`gui/screens/processing.py:265-280`) starts a `DetectionWorker`. When the database does not exist, the worker calls `init_database` (`gui/workers/detection_worker.py:103-124`). `init_database` refuses any passphrase that `EncryptionService.validate_passphrase` refuses (`data/database.py:283-285`): fewer than 12 characters (`data/encryption.py:215-219`). The refusal comes before any file is created. The worker emits « La phrase secrète doit contenir au moins 12 caractères. » (l.112-115).
4. **Nobody forgets the passphrase.** `ProcessingScreen._on_error` (`processing.py:335-349`) shows the message and goes back home. It never clears the cache. The database screen does clear it, flag-based (`database.py:494-509`, `DatabaseWorker.is_passphrase_error`). The batch screen clears it by matching "passphrase"/"decrypt" in the message (`batch.py:937-939`). That match catches only the creation refusal, whose batch message carries `init_database`'s English "Invalid passphrase: ..." (`batch_worker.py:219-223`). It never matches « Phrase secrète incorrecte ». So on the single-document path the user loops until the app is closed.

#### The second passphrase trap: a wrong passphrase for an existing database (found by the SM, 2026-11-10)

1. **Nothing checks the passphrase before the review.** The worker skips creation for an existing file. `DocumentProcessor` opens no database to detect entities.
2. **The failure is swallowed.** The first open is in `build_pseudonym_previews` (`core/document_processor.py:1202` at `3cd82ba`, `open_database`). It raises `ValueError("Incorrect passphrase. ...")`, and the worker swallows it as "non-fatal" (`detection_worker.py:202-207`). The review then shows no pseudonyms.
3. **The end fails in English.** Finalization fails with « Erreur de pseudonymisation » and "ValueError: Incorrect passphrase. Please check your passphrase and try again."
4. **The passphrase is never forgotten.** It stays cached, so the next document goes the same way.

The worker already has the right message, for a case that never fires at detection: « Phrase secrète incorrecte. Veuillez réessayer. » (`detection_worker.py:182-185`, also `processing_worker.py:165` and `batch_worker.py:237`).

#### The same trap in a batch (read by the PO, measured by the SM, 2026-11-10)

1. **Nothing checks the passphrase before the files.** `BatchWorker._run_batch` (`gui/workers/batch_worker.py:200`) creates the database only when it is missing (l.212-222). It then builds a `DocumentProcessor` (l.225-243), whose `__init__` opens no database (`core/document_processor.py:158-199` at `3cd82ba`). So its « Phrase secrète incorrecte. Veuillez réessayer. » branch (l.233-237) never fires on a wrong passphrase.
2. **With a review per document, the review shows no pseudonyms.** The batch screen builds each review's previews in a `try` that swallows the failure (`gui/screens/batch.py:1019-1028`).
3. **Each file fails at the end, in English.** `finalize_document`/`process_document` turn the error into a failed result. The worker counts every file as failed with "ValueError: Incorrect passphrase. Please check your passphrase and try again." (l.307-328), and the run ends with `finished` (l.346), not `error`.
4. **The passphrase is never forgotten.** `BatchScreen._on_error` (l.930-946) never runs. Even if it ran, its text match ("passphrase"/"decrypt", l.937-939) would not catch the French « Phrase secrète incorrecte ». So the next batch, or the next single document, goes the same way.

**Both traps reproduced by the SM on `8bf265d`** (Dev Notes "Reproduction"):
- **Short passphrase for a new database:**
  - the window was shown once, with « Continuer » enabled;
  - three documents in a row were each refused;
  - the passphrase stayed cached, and the database file was never created.
- **Wrong passphrase for an existing database:**
  - two documents in a row went through detection with no error and no pseudonyms, then failed at « Finaliser » in English;
  - the window was never shown again, and the passphrase stayed cached.
- **The same wrong passphrase in a batch** of two files, without a review:
  - two runs in a row each ended with 0 files done and 2 failed, each failure "ValueError: Incorrect passphrase. ...";
  - no error window, the window never shown again, the passphrase kept.
  - With a review per document, the first review opened with no pseudonyms.

**How a user stuck today gets out.**
- **Today:** close the app. The cache lives in memory only (`main_window.py:68-69`, "cleared on exit"). For the first trap nothing was written to disk: no database file. The GUI config only remembers the chosen path, which the window does not list while the file does not exist (`passphrase_dialog.py:166-173`). The next start asks again.
- **After the fix:**
  - The first trap cannot form, because the window refuses the short passphrase.
  - A wrong passphrase for an existing database is refused when the document starts, before detection, and when a batch starts, before any file.
  - Any passphrase refused at that start is forgotten, so the next document or batch opens the passphrase window again. That covers a passphrase too short for creation and a wrong one for an existing database.

   - **It follows the selection and the typing.** The state is computed again on every keystroke and on every change of database (`_on_db_combo_changed` already calls `_update_confirm_state`, l.251).
