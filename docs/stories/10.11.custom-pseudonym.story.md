## Acceptance Criteria

AC1 to AC11 are copied from the epic's Story 10.11 at `b40d385` word for word. "AC precisions (story-level)" adds detail and does not change the epic text. AC12 to AC18 are story-level.

1. **AC1 — Used in the written file, at every place (Q3):** a custom pseudonym set in the desktop app or the CLI replaces that name, for that type, at every occurrence written (the file holds one pseudonym per name and type). In batch review, setting it on one place applies it to every place of that name and type, found or added by hand, except a place the user rejected on its own, as corrections do (10.9, 10.10); the list shows it on each of those rows, and one undo reverts it everywhere. A custom pseudonym that reached several places follows the group like a correction (Q-B): rejecting the name from another found place rejects those places too, and a place the user rejected on its own before is never reached. The tests assert the written file, not the list.
2. **AC2 — Stored and reused (Q1, Q4):** the custom pseudonym is stored in a new mapping row for that (text, type), so later documents and later runs, in the desktop app and the CLI, reuse it. A name that already has a stored pseudonym keeps it: the custom pseudonym is refused, with a message that says why and how to proceed (remove the name with `delete-mapping` first). For a person, the custom pseudonym is split at its last space: the part before is stored as the first-name part, the part after as the last-name part, so a later first or last name used alone gets the matching part. A one-word custom pseudonym is stored for the full name only, so a later first or last name alone gets its own generated pseudonym. A real first name that already has a stored first-name part keeps it (Q-D, not the recommendation): if "Quentrel" alone is already written "Aubin", a custom pseudonym whose first part is not "Aubin" is refused, with a message saying it must start with "Aubin" (for example "Aubin Vellion"). The same holds for a real last name that already has a stored last-name part, which must then be the custom pseudonym's last part; the SM states this case precisely and the PO checks it.
3. **AC3 — Clashes are refused (Q2, Q-C):** a custom pseudonym is refused, with a message that names the clash, when it equals the stored pseudonym of another name, when a part of it is already used for another person, or when it equals a real name. A real name is any word or words of the document that start with a capital letter, found by the detector or not, a sentence-initial word included, plus the full names already in the mapping database; words in small letters do not count. Capitals and accents are ignored when comparing, and for a person each part of the custom pseudonym (before and after its last space) is checked on its own. Later generated pseudonyms: a generated full pseudonym never equals a stored one (the library's used set), and a stored part that has a real part beside it is never reused. A part stored without one (a one-word custom pseudonym, or the last part on a one-word name) is not tracked by the library (`pseudonym/library_manager.py:788-797`, `:637-643`), so the story adds a check in `core/` that a generated pseudonym never reuses a part of a stored custom pseudonym. The same gap for generated pseudonyms of one-word names predates 10.11 and is a follow-up.

### Product Constraints (non-negotiable, verbatim from the epic)

### Q2 Lookup: Index and Encryption (SM findings, 2026-10-15)

- **No index on `pseudonym_full`** (`data/database.py:42-51`; [Source: architecture/9-database-schema.md#9.2]). An index would be a schema change after 10.7's 1.1.0; it is not needed.
- **Every name and pseudonym column is encrypted, deterministically** (AES-256-SIV; `mapping_repository.py:537-565`; `data/encryption.py:9`; [Source: architecture/9-database-schema.md#9.3]). An exact match could be looked up in SQL on the ciphertext, as `find_by_full_name_and_type` does, a table scan without an index.
- **What Lionel's answers need.** Q-C ignores capitals and accents, and Q2, Q-D and AC3 compare parts with the real parts they stand for: neither can be done on ciphertext. The checks read every row decrypted (`find_all()`, `:412-441`) and compare in Python.
- **Cost.** Finalization already decrypts every row twice per document (`_init_processing_context` `:733`, `_reset_pseudonym_state` `:706`); AC3's untracked values are taken from the second read, so a finalization without custom pseudonyms reads nothing more. The set-time check adds one `find_all()` per dialog or [C]. No new repository method (the epic's Integration Points agree since `b40d385`).

### Fix Design (pre-decided; product choices as Lionel answered Q1–Q4 and Q-B to Q-F)

The SM prototype v1.1 implements it (`proto_111_v11.diff`; Reproduction Evidence, items 3 and 4). The dev writes the real code.

**The core (`core/custom_pseudonym.py`, new; `core/document_processor.py`; `exceptions.py`).**
1. **Normalization:** `normalize_custom_pseudonym(text, type)` = `mapping_key(text, type)`. Empty → ignored. Why: the dialog is pre-filled with the suggestion, which carries the title (`build_pseudonym_previews` `:888-896`), and the written text adds the occurrence's own title.
2. **Split (Q4):** for PERSON, at the last space; one word → no parts; other types → no parts. The name's real parts as `parse_full_name` reads them (`person_parts`: one word is a first name).
3. **Checks** (`check_custom_pseudonym(stored_rows, name, type, pseudonym, document_text, other_customs) -> Refusal | None`), in AC17's order:
   - (a) a stored row with `full_name == name` and that type → `ALREADY_STORED` (its pseudonym, Q-A's %1);
   - (b) Q-D: the parts real first and last names already have, from the stored rows (`first_name` with `pseudonym_first`, `last_name` with `pseudonym_last`, PERSON rows) and from this review's other custom pseudonyms; a differing first part → `PART_BOUND` with kind `first`, the real first name, the required part and the example "<part> <your last part>"; then the same for the last part;
   - (c) the custom pseudonym's values, each with the real text it stands for (the full one for the name; the first part for the real first name; the last part for the real last name, or `None` on a one-word name: PO R1) against each stored row's values (`pseudonym_full` for `full_name`, `pseudonym_first` for `first_name`, `pseudonym_last` for `last_name`) and against this review's other custom pseudonyms' values: equal values clash, except two parts standing for the same real text (neither `None`); two full values never take the exception → `PSEUDONYM_TAKEN` (with the other name);
   - (d) each of those values against the document: its words found as consecutive whole words (`\w+` tokens), separated by spaces only, the first of them capitalised in the document; then against every stored `full_name` → `REAL_NAME` (with the value).
   - Compared form (Q-C): NFKD, combining marks dropped, `casefold`, whitespace collapsed. `stored_rows` is `None` when the database could not be opened: the stored parts of (a)–(d) are skipped.
4. **Row fields** (`custom_entity_fields`): AC2; `is_ambiguous` and `ambiguity_reason` as the engine sets them ("Standalone component without full name context" for one word, "Multiple word name - parsing uncertain" for three or more; `pseudonym/assignment_engine.py:280`, `:419`, `:431`, `:444`).
5. **Finalization:** `_resolve_pseudonyms(ctx, validated_entities, custom_pseudonyms=None, document_text="")`. Before the loop, if the map is not empty: read `find_all()` once, run the checks for every entry (the others of the map as `other_customs`); a refusal → log `custom_pseudonym_refused` (reason code only) and raise `CustomPseudonymError` (a `ValidationError`) before anything is saved; then, in key order, build each row (`theme` `custom`), `ctx.pseudonym_manager.load_existing_mappings([row])`, add its untracked values to `self._custom_taken`, `entity_cache[key] = pseudonym`, `new_entities.append(row)`. In the loop, a cache hit on a custom key counts as new the first time. `finalize_document(…, custom_pseudonyms=None)` passes the map and `document_text`; `process_document` and `_process_document_tabular` pass a dict that `_run_validation(…, custom_pseudonyms=…)` fills (the tabular text is the joined cell text, `:1015`). `finalize_document_tabular` (no caller) gets the same optional argument for consistency, or is left as it is; the dev records which.
6. **The finalization error** (AC18): `CustomPseudonymError(finalization_message(refusal))`, "A pseudonym you chose can no longer be used: <reason>. Nothing was written.", one reason per refusal kind (Q-A group 3). `_handle_processing_error` turns it into "CustomPseudonymError: …" for every path.
7. **The guard on later generated pseudonyms (AC3, PO R8):** `untracked_custom_values(rows)`: for the rows whose `theme` is `custom` and type PERSON, a one-word `pseudonym_full` with no parts, a `pseudonym_first` without `first_name`, a `pseudonym_last` without `last_name` (folded). `DocumentProcessor.__init__` creates `self._custom_taken: set[str]`; `_reset_pseudonym_state` sets it from the rows it already reads; registration adds the run's own. After `_assign_new_pseudonym`, if the generated full or a part is in it, `_assign_untaken_pseudonym(ctx, new_entity, taken, self._custom_taken)` draws again; that function now rejects a draw whose full pseudonym is in `taken` (10.7, unchanged) or whose full or part is in the custom set, and keeps no component link (as for 10.7). Nothing changes when no custom row exists (AC13).

  - Correcting a name, or changing its type, removes the pseudonym you set on it; set it again if you want it.
  - In the command-line review, going back to a name with [P] and pressing Space no longer loses a correction you made with [E], and no longer leaves a name you rejected and then accepted in clear. These were in every version.
