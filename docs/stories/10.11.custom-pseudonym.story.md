## Acceptance Criteria

AC1 to AC10 are copied from the epic's Story 10.11 at `f388788` word for word. "AC precisions (story-level)" adds detail and does not change the epic text. AC11 to AC18 are story-level; AC15 to AC18 wait for Lionel's answers (Q-A to Q-E).

1. **AC1 — Used in the written file, at every place (Q3):** a custom pseudonym set in the desktop app or the CLI replaces that name, for that type, at every occurrence written (the file holds one pseudonym per name and type). In batch review, setting it on one place applies it to every place of that name and type, found or added by hand, except a place the user rejected on its own, as corrections do (10.9, 10.10); the list shows it on each of those rows, and one undo reverts it everywhere. The tests assert the written file, not the list.
2. **AC2 — Stored and reused (Q1, Q4):** the custom pseudonym is stored in a new mapping row for that (text, type), so later documents and later runs, in the desktop app and the CLI, reuse it. A name that already has a stored pseudonym keeps it: the custom pseudonym is refused, with a message that says why and how to proceed (remove the name with `delete-mapping` first). For a person, the custom pseudonym is split at its last space: the part before is stored as the first-name part, the part after as the last-name part, so a later first or last name used alone gets the matching part. A one-word custom pseudonym is stored for the full name only, so a later first or last name alone gets its own generated pseudonym.
3. **AC3 — Clashes are refused (Q2):** a custom pseudonym is refused, with a message that names the clash, when it equals the stored pseudonym of another name, or when it equals a real name found in the document. Two different names never end up with the same pseudonym.

16. **AC16 — What counts as a clash (story-level; Q-C and Q-D, pending; written as the recommendations).** The rules of AC2 (Q1) and AC3 (Q2), in this order; the first that fails gives the message (AC18):

Exception: a part equal to the part the same real first or last name already has (one real first name, one part: Story 2.8).

The stored pseudonym keeps the spelling the user typed, with titles (and, for a place, a leading preposition) removed and spaces collapsed (`mapping_key`'s normalization), because the written text keeps the title or preposition of each occurrence (`_compute_replacement_prefix`).

### Product Constraints (non-negotiable, verbatim from the epic)

### Q2 Lookup: Index and Encryption (SM findings, 2026-10-15)

- **No index on `pseudonym_full`.** The entity table's indexes are `full_name`, `entity_type`, `first_name`, `last_name` and a partial one on `is_ambiguous` (`data/database.py:42-51`; [Source: architecture/9-database-schema.md#9.2]). An index would be a schema change after 10.7's 1.1.0; it is not needed (below).
- **Every name and pseudonym column is encrypted, deterministically.** `_encrypt_entity` encrypts `first_name`, `last_name`, `full_name`, `pseudonym_first`, `pseudonym_last` and `pseudonym_full` (`mapping_repository.py:537-565`) with AES-256-SIV: "Same plaintext + key → same ciphertext (enables DB queries)" (`data/encryption.py:9`; [Source: architecture/9-database-schema.md#9.3]).
- **What that allows.** An exact match can be looked up in SQL on the ciphertext, as `find_by_full_name_and_type` does (`:170-203`): `Entity.pseudonym_full == encrypt(value)`, a table scan without an index, no decryption. A match that ignores case or accents (Q-C's recommendation), and the part checks (pseudonym parts compared with the real parts they stand for), cannot be done on ciphertext: they need the rows decrypted and compared in Python. `find_all()` does that (`:412-441`).
- **Cost.** Finalization already decrypts every row twice per document (`_init_processing_context` `:733`, `_reset_pseudonym_state` `:706`), and the desktop app opens the database once per document for the known-entity pass. The checks add one `find_all()` per set-time check (one dialog or [C]) and reuse finalization's rows otherwise. No new repository method is needed; the epic's Integration Points expected "a way to find a stored name by its pseudonym", which is only needed if Lionel answers Q-C "Exact" (then a `find_by_pseudonym_full` with ciphertext equality is the cheaper choice, and the part checks still read every row). ### Fix Design (pre-decided; product choices as Lionel answered Q1–Q4, and Q-A to Q-E as recommended)

The SM prototype implements it (`proto_111.diff`; Reproduction Evidence, items 3 and 4). The dev writes the real code.

**AC2 and AC3, the core (`core/custom_pseudonym.py`, new; `core/document_processor.py`; `exceptions.py`).**
1. **Normalization:** `normalize_custom_pseudonym(text, entity_type)` = `mapping_key(text, entity_type)` (titles, a place's leading preposition, whitespace). An empty result is ignored, as an empty text is today. Why: the dialog is pre-filled with the suggestion, which carries the title ("Dr. Luke Skywalker", `build_pseudonym_previews` `:888-896`), and the written text adds the occurrence's own title (`_compute_replacement_prefix`), so a title kept in the pseudonym would be written twice.
2. **Split (Q4):** for PERSON, at the last space (`rpartition(" ")`); one word → no parts; other types → no parts.
3. **Checks** (`check_custom_pseudonym(stored_rows, name, type, pseudonym, document_text, other_customs) -> Refusal | None`), in AC16's order: (a) a stored row with `full_name == name` and that type → `ALREADY_STORED` (with its stored pseudonym, for Q-A's %1); (b) the custom pseudonym's values (the full one, standing for the name; each part, standing for the real first or last name, `parse_full_name`'s split) against every stored row's values (`pseudonym_full` for its `full_name`; `pseudonym_first` for its `first_name`; `pseudonym_last` for its `last_name`) and against this review's other custom pseudonyms: equal values clash, except a part and a value standing for the same real text (not two full pseudonyms: that is 10.7's "one key, two types, two pseudonyms") → `PSEUDONYM_TAKEN` (with the other name); (c) the full pseudonym and its parts as whole words of the document's text (`(?<!\w)…(?!\w)` on the compared form), then against every stored `full_name` → `REAL_NAME` (with the real text). Compared form (Q-C): NFKD, combining marks dropped, `casefold`, whitespace collapsed. `stored_rows` is `None` when the database could not be opened: (a), (b)'s stored part and (c)'s stored part are skipped.
4. **Row fields** (`custom_entity_fields`): AC2; for (d) (Q-D), a real first or last name that already has a different part (`pseudonym_manager.get_component_mapping(real, kind)`, which holds the stored parts once `_reset_pseudonym_state` has run) is stored as `None` with its part `None`, so the existing part keeps serving lone mentions; the other part is stored.
5. **Finalization:** `_resolve_pseudonyms(ctx, validated_entities, custom_pseudonyms=None, document_text="")`. Before the loop: if the map is not empty, read `find_all()` once, run the checks for every entry (the others of the map as `other_customs`); any refusal → log `custom_pseudonym_refused` with the reason code only, raise `CustomPseudonymError` (a `ValidationError`) before anything is saved; then, in key order, build each row (`Entity`, theme of the run, `is_ambiguous=False`), `ctx.pseudonym_manager.load_existing_mappings([row])`, `entity_cache[key] = pseudonym`, `new_entities.append(row)`. In the loop, a cache hit on a custom key counts as new the first time, reused after. `finalize_document(…, custom_pseudonyms=None)` passes the map and `document_text`; `process_document` and `_process_document_tabular` pass a dict that `_run_validation(…, custom_pseudonyms=…)` fills, and their `document_text` (the tabular one is the joined cell text, `:1015`). `finalize_document_tabular` (no caller) gets the same optional argument for consistency, or is left as it is; the dev records which.
6. **The command line's checker:** `_run_validation` passes `pseudonym_checker=…` (a closure over `ctx` and `document_text` that reads `find_all()` and calls `check_custom_pseudonym`) and `custom_pseudonyms=…` to `run_validation_workflow`.

def change_pseudonym(self, entity_id, new_pseudonym):

### Technical Constraints

- All public functions have type hints, and imports are absolute. `mypy` is strict (`mypy.ini`, run by CI on `gdpr_pseudonymizer`). [Source: architecture/19-coding-standards.md#19.1]
- Quality commands: `black --check`, `ruff check`, `mypy gdpr_pseudonymizer/`, `pytest`. [Source: architecture/19-coding-standards.md#19.0]
- **Never log sensitive data:** the two new log events carry a reason code or a count only; no entity text and no pseudonym (a custom pseudonym can be a real-looking name). `CustomPseudonymError`'s message carries the reason code only. [Source: architecture/19-coding-standards.md#19.1, rule 3]
- No public CLI flag, mapping-schema or file-format change; the database stays 1.1.0. The new keyword arguments are optional. [Source: prd/epic-10 "Enhancement Details", "Compatibility Requirements"]
- Cost: one `find_all()` per set-time check and one per finalization that holds a custom pseudonym; nothing when none is set (Dev Notes "Q2 Lookup").
