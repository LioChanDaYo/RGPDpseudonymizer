The new test file sits in `tests/unit/gui/`, which both leakage guards scan (`tests/unit/**`), so every string in it is an invented name (Vorlan Mestrix, Zorbal Quentrix, Zorbal, Vorlan Zorbal, Zorbalix, Saint-Zorbal, Xantor Vellion), a main-corpus word pre-checked by the SM (Test Plan), or a code identifier. See Dev Notes "Isolation Rules".
12. **AC12 — The places of a name added by hand, exactly (story-level; Lionel's "Fix before release (Rec.)" and his 10.15 Q3 "A: Hyphen joins (Rec.)", 2026-10-16, whose question said "The desktop app (10.17) will use the same rule"; (e) waits for Q1, (d) for Q2).**
    - **(a) A place** is an occurrence of the exact text selected (the same characters, capitals and accents included) where neither the character just before it nor the character just after it (when there is one) is a letter, a digit, an underscore (Python's Unicode `\w`) or a hyphen (`-`, U+2010 or U+2011). So "Zorbalix", "Saint-Zorbal", "Zorbal-Quentrix" and "anti-Zorbal" hold no place of "Zorbal" (inside a longer word; a hyphen joins words), while "Zorbal.", "(Zorbal)" and « Zorbal » do; an apostrophe is not a word character, so an elided article in front ("l'", "d'") does not stop a place. Places are read left to right and do not overlap each other. This is 10.15's AC14 (a) without cells: the desktop reviews a spreadsheet as its extracted text.
    - **(b) Places already in the review are not added.** A place where the detector found the same text with the same type (same start and end, as detected, before any edit) keeps its own row and decision, whatever the user decides on it before or after the add (10.10; AC1). A place already held by a row added by hand with the same text and type is not added twice. A place where the detector found the same text with another type is a place of the added name (its name and type differ): see (e).
    - **(c) The selected place.** The place the user selected is always one of the places, whole word or not, as today: the user picked it.
    - **(d) How the places are held (AC2).** Single-document validation: one row added by hand, which stands for every place, as a found row stands for its variant group; its highlights are every place; accept, reject, correction, type change and custom pseudonym on it act on every place. Batch validation: one row added by hand per place, each "ajouté", made by one undo step; each row acts on its own for accept and reject (10.10, pending Lionel's Q2), and corrections, type changes and custom pseudonyms reach every row of the name (10.10 Q3, 10.11 Q3). In both modes one undo removes the add at every place and one redo restores it.
    - **(e) A place that partly overlaps another name that is written** (pending Lionel's Q1; the recommendation is his 10.15 Q4 rule): neither span holding the other, the place is widened to cover both, again until it overlaps no other name partly, and the whole span is written with the added name's pseudonym. "Another name that is written" is every row the user keeps: accepted, corrected, added by hand, and the known names the review accepted from the mapping database (`classify_known_entities`). Nothing of either name stays in plain text there; the other name keeps its row and its pseudonym everywhere else. A place that lies inside a longer place that is written is covered by it, and a place that holds a shorter one is written whole, both as today (`_apply_replacements`, the first, longest span kept). Where the detector found the same text with another type and that row is kept, the two spans are equal and the detected row, first in the list, gives that place its pseudonym, as in the CLI (10.15 Consumer Trace #29); where that row is to review or rejected, the place takes the added name's pseudonym. The review shows each name's own highlights; the widening applies to the list sent to finalization.

### Fix Design (pre-decided; Q1 and Q2 as recommended until Lionel answers)

The SM prototype implements it (`logs/proto_1017.diff`; Reproduction Evidence). **The prototype and the names below are the SM's (Claude's) sketches, to show the rules; they are indicative.** Forge writes the real code through Codex from the ACs, these rules and the Test Plan, on the code at `HEAD` after Task 0, and may name things its own way as long as every rule and every test holds.

**The mode (`gui/models/validation_state.py`, `gui/screens/validation.py`).**
1. `GUIValidationState.init_from_detection_result(detection_result, rows_per_place: bool = False)`: `True` in batch validation, where each place of a name is its own row; `False` in single-document validation, where a row stands for every place of its name. `ValidationScreen._begin_review` passes `rows_per_place=self._batch_mode` on its one call (`validation.py:333`), by keyword. The default keeps every existing direct caller (the unit tests that build a state by hand) on single-document behaviour. (Why not infer it from `variant_occurrences is None`: a single-document review with no detection also has an empty map, and the tests build states both ways.)

**The places (AC12 (a)-(c)).**
2. A module function, e.g. `whole_word_places(text, document_text) -> list[tuple[int, int]]`: `re.finditer` over `(?<![\w\-\u2010\u2011])` + `re.escape(text)` + `(?![\w\-\u2010\u2011])` (raw strings), left to right, non-overlapping; an empty text has no place. The same pattern as 10.15's `places_of`, without cells. [Source: architecture/gui-ux-specification.md#8.2 Entity Validation UX, "Word-snap by default (hyphens = intra-word)"]
3. The places of an add are those, plus the selected `(start_pos, end_pos)` if it is not among them, sorted.
4. **Found places:** `_found_places: set[tuple[str, int, int, str]]` (text, start, end, type), built in `init_from_detection_result` from `detection_result.detected_entities` and every list of `_variant_occurrences`, before any decision or edit, and never changed afterwards (like `_candidate_key_by_id`). A place whose (text, start, end, type) is there is left out of the add.
5. **Places already added:** `_hand_spans_by_id: dict[str, list[tuple[int, int]]]`, the spans each row added by hand was added with, set by `_AddEntityCommand.redo` and removed by its `undo`. A place held by a row whose `_hand_key_by_id` equals (text, type) is left out.
6. When no place is new, nothing is pushed and `add_entity` returns `""`. This is unreachable from the menu (step 1 of the Consumer Trace) and keeps a programmatic second add harmless (T10).

**Single-document validation (AC2).**
7. One `_AddEntityCommand` holds every new place: the row's own entity sits at the selected place (or at the first new place when the selected place is held); `_hand_places_by_id[entity_id]` lists one entity per place in document order, the row's own entity object among them (as a variant group holds its canonical), the others `dataclasses.replace(own, start_pos=…, end_pos=…)`, all with `source="manual"`. `redo` installs the list and `undo` removes it with the row, so one undo and one redo cover every place.
8. A helper, e.g. `_occurrences(review) -> list[DetectedEntity] | None`: an added row with places → its list; a detected row → its variant group by its stored key; else `None`. `_occurrence_spans_for_edit` and `_edited_occurrences` use it instead of their own variant lookups (a correction reaches every place of an added row, T12), `get_all_entity_ranges` gives an added row every place (T9), and `expand_validated_entities` sends every place of an added row, each with the row's current type (`dataclasses.replace(place, entity_type=row_type)` for the places other than the row's own entity, as 10.9 does for a retyped detected row; T13).
9. `expand_validated_entities` drops its early return when the variant map is empty (`:838-839`), so a document where the detector found nothing still sends every place of an added name. For detected rows nothing changes: with an empty map each row is sent as itself, as before.

**Batch validation (AC2).**
10. One `_AddEntityCommand` per new place, each row its own entity at its place, with `_hand_key_by_id` = (text, type) and in `_own_ids` as today, all inside one undo macro "Ajouter une entité" (the command's own label) when there is more than one; `add_entity` returns the id of the row at the selected place. Each row is an ordinary row added by hand: accept and reject act on it only (`_group_ids`, 10.10; Q2 (A)), corrections and type changes reach every row of the name (`_action_rows`, 10.10 Q3), a custom pseudonym reaches every row (`_pseudonym_rows`, 10.11 Q3; after 10.16, by current name). No new code in those functions.

**The overlap (AC12 (e); Q1 (A)).**
11. A module function, e.g. `widen_hand_places(entities) -> list[DetectedEntity]`: for each entity with `source == "manual"`, while its span partly overlaps the span of another entity of the list (they overlap and neither holds the other), widen it to their union; a widened entity is `dataclasses.replace(entity, start_pos=…, end_pos=…)`, its text and type kept; every other entity, and the order, unchanged. `get_validated_entities` (batch, `validation.py:993`) and `expand_validated_entities` (single, `:1043`) return their lists through it, so 10.13's count, 10.14's copies and both hand-offs read the same list. The writer then keeps the widened span (it holds the other one) with the added name's pseudonym (`_apply_replacements` `:836-843`); the other name keeps its row and its pseudonym at its other places. Pending and rejected rows are never sent, so they never widen anything. No log of any name or span.

**What the user sees:**
- Adding a name by selection replaces it at every place of that text and type in the document, as whole words: in single-document review the added row's highlights cover every place; in batch review a row "ajouté" appears for each place. A name inside a longer word or a hyphenated word is left alone, except the place the user selected. A place the detector found with that name keeps the decision the user makes there. One Ctrl+Z removes the add everywhere. Where the added name partly overlaps a name that is written, the whole span takes the added name's pseudonym.

**Not changed:** `core/`, `validation/`, `nlp/`, `resources/`, `utils/`, `data/`, `pseudonym/`, `cli/`, every GUI file except `gui/models/validation_state.py` and the one call in `gui/screens/validation.py`; `_group_ids`, `_action_rows`, `_pseudonym_rows`, `_sent_name`, `custom_pseudonym_refusal`, `get_custom_pseudonyms`, the accept, reject, edit, type and pseudonym commands; the editor's menu and its overlap check; every text.

`### Fixed`, one new bullet (AC4; the PM may prefer other wording; the overlap sentence follows Lionel's Q1):

- **Desktop app: a name you add by hand is now replaced at every place (Story 10.17).** A name you added by selecting it in the document ("Ajouter comme entité") was replaced only at the place you selected, while its pseudonym was stored in the mapping database: its other places stayed in clear. In single-document validation the added name is one row and its highlights show every place; in batch validation each place gets its own row. One undo removes the name at every place. The command-line validation is Story 10.15. Detection, the database schema and the accuracy figures do not change.
