### Product Constraints (non-negotiable, verbatim from the epic)

[Source: prd/epic-10-v2.3-detection-precision-quick-wins.md#Product Constraints]

These apply to every story in this epic. A story that cannot meet its goal inside them stops and goes back to Lionel; it does not relax them.

1. **Local NLP only.** No LLM, no generative model, no API call, no cloud service, no telemetry. Every change is a deterministic rule, lexicon or pattern that runs offline.
2. **No encoder NER models.** Introducing a transformer/encoder NER model (e.g. CamemBERT-NER) is a Lionel decision that belongs to Epic 9. It must not be introduced in this epic, including as an optional dependency or experiment committed to the repo.
3. **Mandatory human validation stays.** No auto-accept mode, no `--no-validate`, no confidence-based skipping. Precision gains reduce the reviewer's workload; they do not replace the reviewer.
4. **No user data** for training, tuning or evaluation. All corpus and held-out documents are synthetic.
5. **Recall over precision.** Missing a real person is worse than showing an extra candidate. Any drop in overall recall or in any per-type recall needs Lionel's sign-off (gate G3).
6. **No public accuracy claim without CI evidence.** Every number that reaches README, FAQ, docs, CHANGELOG or the QA report comes from a cited CI accuracy run (gate G1).

Constraint 3: validation stays mandatory; the add is still the user's own act on a selection, and a found place keeps the user's own decision. Constraint 5: no detection change; the fix removes a path that left a name the user added in plain text. Constraint 6: the CHANGELOG entry carries no accuracy number.

**Standing rules, word for word from the 10.6 story** (Dev Notes "Isolation Rules", "Standing rules (word for word, as given for every story from 10.6 on …)", at `main` `4f3cf30`):

- **Held-out isolation:** no agent opens, lists, reads or greps anything under `tests/test_corpus/held_out/`. Held-out results are used only as aggregate lines in a CI `accuracy-results` artifact. Any `tests/unit/held_out_leakage_allowlist.json` change needs Lionel's recorded approval.
- **Final-exam isolation, from the start of 10.6 authoring:** no agent opens, lists or greps the final-exam material (isolated workspace or `tests/test_corpus/final_exam/`). Orchestrating agents handle only paths, hashes and counts. Final-exam numbers are never used for a decision or for tuning.
- **Held-out-blind strings:** any real string in a new test or resource must occur in the main-corpus text or be Lionel-approved. Use invented names: Zorbalia, Quentrix, Zorbaville, Quentrel ("Quentin" is real).
- **CI must be all green to merge, and a red check is fixed inside the current PR.** Reruns are for infrastructure failures only. Absolute wall-clock test asserts are banned.
- **Recall over precision, and the coverage invariant:** not applicable to PR A, but restated so later stories keep them (see "Product Constraints and Cross-Story Rules" below).

- The leakage guard `tests/unit/test_held_out_leakage.py` (non-slow, runs in normal CI) fails if a held-out-only entity string appears in `gdpr_pseudonymizer/resources/**` or `tests/unit/**` (`SEARCH_TREES`, `:34`). This story adds files to both trees (new resources, new tests, edited `detection_patterns.yaml`). The guard is the only check that your strings and list entries are not held-out strings.
- **Allowlist:** `tests/unit/held_out_leakage_allowlist.json` is keyed by (path, sha256). Any change to it needs **Lionel's recorded approval in this story** (date + what). QA flags any PR diff on it.
- **If the leakage guard fires:** the message gives a path and a hash only. Do not try to find out which string it is.
  - **Unit test file with invented strings only:** replace your synthetic string with another clearly invented one.
  - **Unit test file that contains AC-named or other real strings:** treat it like a resource. Do **not** bisect, edit or remove strings to find the hit. HALT and send the whole file (path, hash, list of its real strings) to Lionel.
  - **A resource file** (stoplist, role words, particles, AC3 lexicon, `detection_patterns.yaml`): do **not** remove, edit or bisect entries, because each removal would reveal which entry is a held-out string. HALT and send the **whole frozen list** (or the lexicon reference) to Lionel with the path and hash. Lionel either allowlists it (path + hash + date recorded here and in the allowlist) or drops the category concerned. Record his decision in Decisions Recorded.
  - Either way, note it in Completion Notes by hash only.

- **Calibration (Lionel, 2026-10-09):** the guards target real channels: text actually in a prompt or a file, public CI logs, and the held-out and final-exam access rules. No guard assumes that a model session remembers anything across calls; each GPT or Gemini call starts from fresh context.

### Fix Design (pre-decided; Lionel's 10.15 Q3 and Q4 and his 10.17 Q2)

The SM prototype implements it (`logs/proto_1017.diff`; Reproduction Evidence). **The prototype and the names below are the SM's (Claude's) sketches, to show the rules; they are indicative.** The BMAD dev agent writes the real code from the ACs, these rules and the Test Plan, on the code at `HEAD` after Task 0, and may name things its own way as long as every rule and every test holds.

**The mode (`gui/models/validation_state.py`, `gui/screens/validation.py`).**
1. `GUIValidationState.init_from_detection_result(detection_result, rows_per_place: bool = False)`: `True` in batch validation, where each place of a name is its own row; `False` in single-document validation, where a row stands for every place of its name. `ValidationScreen._begin_review` passes `rows_per_place=self._batch_mode` on its one call (`validation.py:333`), by keyword. The default keeps every existing direct caller (the unit tests that build a state by hand) on single-document behaviour. (Why not infer it from `variant_occurrences is None`: a single-document review with no detection also has an empty map, and the tests build states both ways.)

**The places (AC13 (a)-(c)).**
2. A module function, e.g. `whole_word_places(text, document_text) -> list[tuple[int, int]]`: `re.finditer` over `(?<![\w\-\u2010\u2011])` + `re.escape(fold(text))` + `(?![\w\-\u2010\u2011])` (raw strings) with `re.IGNORECASE`, on `fold(document_text)`, left to right, non-overlapping, keeping a match only if the original place is a form of `text`: AC13 (a). The SM's sketch of the two helpers: `fold` sets each character's accents aside on its own (`unicodedata` NFD without the combining marks), keeping a character whose folding would not be one character, so that positions in the folded text are positions in the document; `is_form(place, text)` is true when `place == text`; or when `place` holds a capital letter and `place.lower() == text.lower()`; or when `place` is entirely in capitals (`place == place.upper()`, with a capital letter) and `fold(place).lower() == fold(text).lower()`. **Accents are set aside only for a place entirely in capitals** (mutant m15 sets them aside for any place with a capital and writes « Vorlene »). An empty text has no place. The boundaries are 10.15's `places_of`'s, without cells. The rule is one pure function with no Qt import, so that 10.19 and 10.17 share it (Ordering and Rebase). [Source: architecture/gui-ux-specification.md#8.2 Entity Validation UX, "Word-snap by default (hyphens = intra-word)": intent only; the editor does not snap selections, `entity_editor.py` has no snap code]
3. The places of an add are those, plus the selected `(start_pos, end_pos)` if it is not among them, sorted.
4. **Found places:** `_found_places: set[tuple[str, int, int, str]]` (text, start, end, type), built in `init_from_detection_result` from `detection_result.detected_entities` and every list of `_variant_occurrences`, before any decision or edit, and never changed afterwards (like `_candidate_key_by_id`). A place is left out of the add when one of them has its start, end and type and its text is a form of the name (`is_form(found_text, text)`): a found « ZORBAL » keeps its decision when « Zorbal » is added (T19), and so would a found « HELENE » when « Hélène » is added.
5. **Places already added:** `_hand_spans_by_id: dict[str, list[tuple[int, int]]]`, the spans each row added by hand was added with, set by `_AddEntityCommand.redo` and removed by its `undo`. A place held by a row whose `_hand_key_by_id` equals (text, type) is left out.
6. When no place is new, nothing is pushed and `add_entity` returns `""`. This is unreachable from the menu (step 1 of the Consumer Trace) and keeps a programmatic second add harmless (T10).

**Single-document validation (AC2).**
7. One `_AddEntityCommand` holds every new place: the row's own entity sits at the selected place (or at the first new place when the selected place is held); `_hand_places_by_id[entity_id]` lists one entity per place in document order, the row's own entity object among them (as a variant group holds its canonical), the others `dataclasses.replace(own, start_pos=…, end_pos=…)`, all with `source="manual"` and the text as added (whatever the form written at that place), so every form takes the added name's pseudonym and one row is stored (T15). `redo` installs the list and `undo` removes it with the row, so one undo and one redo cover every place.
8. A helper, e.g. `_occurrences(review) -> list[DetectedEntity] | None`: an added row with places → its list; a detected row → its variant group by its stored key; else `None`. `_occurrence_spans_for_edit` and `_edited_occurrences` use it instead of their own variant lookups (a correction reaches every place of an added row, T12), `get_all_entity_ranges` gives an added row every place (T9), and `expand_validated_entities` sends every place of an added row, each with the row's current type (`dataclasses.replace(place, entity_type=row_type)` for the places other than the row's own entity, as 10.9 does for a retyped detected row; T13).
9. `expand_validated_entities` drops its early return when the variant map is empty (`:838-839`), so a document where the detector found nothing still sends every place of an added name (T14; the PO's mutant m8 kept it and passed every v1.0 test). For detected rows nothing changes: with an empty map each row is sent as itself, as before. **After the rebase on 10.16:** steps 8 and 9 apply to 10.16's private expansion helper (the hand places expanded there, its early return removed); the widening of step 11 stays on the list `expand_validated_entities` returns.

**Batch validation (AC2).**
10. One `_AddEntityCommand` per new place, capital forms included, each row its own entity at its place with the text as added, with `_hand_key_by_id` = (text, type) and in `_own_ids` as today, all inside one undo macro "Ajouter une entité" (the command's own label) when there is more than one; `add_entity` returns the id of the row at the selected place. Each row is an ordinary row added by hand: accept and reject act on it only (`_group_ids`, 10.10; Lionel's 10.17 Q2, "A: Each row on its own (Rec.)"), corrections and type changes reach every row of the name (`_action_rows`, 10.10 Q3), a custom pseudonym reaches every row (`_pseudonym_rows`, 10.11 Q3; after 10.16, by current name). No new code in those functions.

**The overlap (AC8, AC13 (e); Lionel's 10.15 Q4 "A: Name you added (Rec.)", applied to the desktop; not re-asked, the PO's M1; corrections included, the 10.15 Codex P0 ruling).**
11. A module function, e.g. `widen_hand_places(entities, typed) -> list[DetectedEntity]`: for each **typed** entity of the list (AC13 (e): a place added by hand, or a place a correction reached), while its span partly overlaps the span of another entity of the list (they overlap and neither holds the other), widen it to their union; a widened entity is `dataclasses.replace(entity, start_pos=…, end_pos=…)`, its text and type kept; every other entity, and the order, unchanged. `get_validated_entities` (batch, `validation.py:993`) and `expand_validated_entities` (single, `:1043`) return their lists through it, so 10.13's count, 10.14's copies and both hand-offs read the same list. The writer then keeps the widened span (it holds the other one) with the added name's pseudonym (`_apply_replacements` `:836-843`); the other name keeps its row and its pseudonym at its other places. Pending and rejected rows are never sent, so they never widen anything. No log of any name or span. **Which entities are typed is the dev's choice** (the epic's AC8 leaves it open): the SM's prototype passes a list of flags built where the list is made: in `get_validated_entities`, a row with a text correction (`review.user_modification`) or added by hand; in `expand_validated_entities`, every occurrence `_edited_occurrences` returns for a corrected row, every place of a row added by hand, and nothing else. **Every occurrence a correction reaches must carry the typed mark, not only the corrected row's own place:** in single-document review the correction reaches the other places of its variant group (10.9), and the overlap may happen only there (T22; the PO's mutant m13, which marked the row's own place only, passed all of v1.4's tests and leaked). Another way is to mark the entities themselves. Ties need no code: two typed places widened to the same span are kept by the writer in list order (`sorted(…, key=(start, -end))` is stable).

**What the user sees:**
- Adding a name by selection replaces it at every place of that name and type in the document, as whole words, also where it is written with other capitals (« ZORBAL » for « Zorbal »), never in a word written entirely in small letters: in single-document review the added row's highlights cover every place; in batch review a row "ajouté" appears for each place. A name inside a longer word or a hyphenated word is left alone, except the place the user selected. A place the detector found with that name keeps the decision the user makes there. One Ctrl+Z removes the add everywhere. Where the added name partly overlaps a name that is written, the whole span takes the added name's pseudonym.

### Code Quality Assessment

The fix follows the Fix Design. The place rule is in three pure module functions with no Qt import (`fold`, `is_form`, `whole_word_places`):

- whole words, with a hyphen joining words;
- any capitals, but never a word written entirely in small letters;
- accents set aside only in a place written entirely in capitals.

**How an add works.**

- **Found places:** taken once from the detection, its variant occurrences included. A found place of the same name and type keeps its row and decision; so does a place a hand row already holds.
- **Single-document review:** one command whose row stands for every place. Highlights, corrections, type changes and the list sent all read those places through `_occurrences` and `_expand`. `_expand` no longer returns early when nothing was detected.
- **Batch review:** one row per place, all in one undo macro, which reuses the existing "Ajouter une entité" label (no screen shows it).

**The overlap rule.** Both lists sent go through 10.15's own `DocumentProcessor._widen_added_places`, imported lazily, so both apps keep one rule and `core/` does not change. Typed places are marked through their source: added by hand, or reached by a correction. The widening is the only reader of that mark.

**Scope.** The only other change is one keyword in `gui/screens/validation.py`. There is no new text and no new log line.

**The tests.** The 53 tests run the real paths and check the written text and the stored rows, with `pytest.fail` preconditions and no sleep. They catch 21 of QA's 24 mutants.
