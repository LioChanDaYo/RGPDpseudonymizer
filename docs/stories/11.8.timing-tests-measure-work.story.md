### Context

#### What fails

Four unit tests run the same code on a small and a large input and assert that the ratio of the two times stays under a cap. CI runs them with `pytest -n auto`, so they share the CPU with other test workers; GitHub's macOS runners are sometimes slow (the failing jobs took 13 to 18 minutes, against about 5 usually).

Since 2026-10-19 (292 CI runs, the orchestrator's count): 16 first-attempt failures on macOS, each green on one rerun. None on Ubuntu or Windows. On `main`, 4 of 24 merges went red (2026-11-04, 2026-11-13, 2026-11-17, 2026-11-18).

#### The trailing-particle test cannot fail on the bug it guards

QA 10.3b PERF-001 found a quadratic search: `_extend_particles` looked for a run of particles at the end of a person span with the regex `tail_parts`, `(?:HSPACE+(?:particles))+$`, searched over the whole span (`git show 81befe8^:gdpr_pseudonymizer/nlp/hybrid_detector.py`, l.885-887). The fix (`81befe8`) replaced it with `_trailing_particles_start` (`hybrid_detector.py:1274-1299`), which walks back over at most `_MAX_PARTICLES` (3) tokens.

Today's test times a span that **ends** with the particle run (`"Zorbal le le … le"`, then `" Quentrix"` outside the span). On that shape the old regex matches at the first particle and stops: it is linear. The SM ran the old search on the test's own input (`probe_particles.log`):

| Particles | Old regex, per call |
|---|---|
| 250 | 18.2 µs |
| 1,000 | 59.3 µs |
| 4,000 | 217.2 µs |

So today's test passes on the old code. The old regex is quadratic only when the particle run is followed by a token **inside** the span (`"Zorbal le le … le Quentrix"`, the whole of it the span): at each start position it runs to the end of the run, fails `$`, and backtracks. On that shape (`probe_particles_variants.log`): 2.03 ms at 250 particles, 32.6 ms at 1,000, 527 ms at 4,000, four times the cost for each doubling. At 32,000 particles that gives about 34 s, which matches QA's gate line "was 38 s at 32k" (`docs/qa/gates/10.3b-particles-roles-location-noise.yml:26`). Today's code on that shape: 8.0 µs at 1,000 particles, 554 µs at 80,000 (linear).

So this story changes the test's input as well as its measure (AC3).

#### Counting the work where it can be counted

The dedup walk and the wrapped-name join are Python loops over entity objects. Their bugs were scans of a whole list per entity, and a scan reads fields of every entity it passes. A `DetectedEntity` subclass that counts reads of its dataclass fields therefore counts the work done, deterministically: the same number on every runner and every run (Dev Notes "Measure per test", A and D).

Counting calls of a method does not work for the dedup: the full scan happens inside one walk, and the scan's position filter skips every kept entity that does not overlap before any method is called. Measured (`probe_negative_control.log`): one walk and 250 / 2,000 calls of `_resolve_same_type_pair` at 250 / 2,000 pairs, with the active window and with the full scan alike; only the field reads differ (13,249 / 105,999 against 261,750 / 16,094,000).

The two other tests guard regular expressions. A regex runs in C, so Python cannot count its steps. Those two keep timing, with a much bigger size gap and both sizes measured in alternation (Dev Notes "Measure per test", B and C).

#### A. Large-input test (`test_hybrid_overlap_role_filter.py:625-652`): count field reads

What it guards: `_dedup_walk`'s active window (`hybrid_detector.py:2608-2672`). Kept entities that end at or before the walk position are moved to `retired` (l.2619-2622), so each new entity is compared only with the few still active. The full scan it replaced (`0b9c15b`) compared each new entity with every kept one.

The counter (put it near the top of the file, after `_ent`):

```python
_ENTITY_FIELDS = frozenset(f.name for f in dataclasses.fields(DetectedEntity))


def _field_read_counter() -> tuple[type[DetectedEntity], dict[str, int]]:
    """A DetectedEntity subclass that counts reads of its dataclass fields.

    A scan of a list of entities reads fields of every entity it passes, so
    this count is the work done on entities, the same on every runner.
    """
    reads = {"n": 0}

    class Counted(DetectedEntity):
        def __getattribute__(self, name: str) -> Any:
            if name in _ENTITY_FIELDS:
                reads["n"] += 1
            return super().__getattribute__(name)

    return Counted, reads
```

- `dataclasses.replace` on a `Counted` gives a `Counted`, so entities the code makes from the inputs keep counting (probe: no error, exact counts).
- The test builds the same pairs as today, with `Counted(...)` in place of `_ent(...)` (or `_ent` given a keyword argument `cls` that defaults to `DetectedEntity`, so its 97 other calls in the file stay as they are), sets `reads["n"] = 0` just before `_dedup_same_type_overlaps`, and reads the count **right after the call, before** its own assertions touch entity fields (they would add reads).
- After reading the count, it asserts `all(type(e) is Counted for e in out)`. Today the output is the input entities themselves. A future change that rebuilds entities as plain `DetectedEntity` objects would hide its work from the count; this assertion makes such a change fail loudly instead of passing on a count that no longer sees the work.
- Sizes: 250 and 2,000 pairs (8x). Assert `ratio < 16`, with the two counts in the message.
- Arithmetic (`probe_counts.log`, Python 3.11): today 13,249 → 105,999 reads, ratio **8.00** (53 reads per pair, exactly linear). Full scan (P1): 261,750 → 16,094,000, ratio **61.49** (4 field reads per comparison, `other.entity_type`, `current.entity_type`, `other.end_pos`, `current.start_pos`, and each of the 2n entities is compared with every earlier kept one: about 4 × 2,000² = 16.0 million). The cap 16 sits 2x above healthy and 3.8x below the slowed copy. Healthy needs no noise margin (the count is exact); the 2x is room for a future change that adds a fixed or slowly growing cost (n·log n at these sizes gives 8 × log 2000 / log 250 ≈ 11).
- Python versions (PO check, `C:\Users\devea\Documents\GitHub\rgpd-analysis\r118\po\counter_versions.py`, the counter on a copy of `DetectedEntity`'s fields, Python 3.11.9, 3.13.4 and 3.14.0, with and without `slots=True`): plain field reads and `dataclasses.replace` give the same counts on every version, and `replace` keeps the counting class. Only a value comparison (`==`, `in`) changed: since 3.13 the dataclass `__eq__` compares field by field and stops at the first difference, so it reads fewer fields (still n² for a scan). Today's dedup decides by identity (`result is other`) and today's join tracks entities by `id()`, and `_resolve_same_type_pair` compares only offsets, cores and keys, so neither compares entities by value: their counts are the same on the 3.11, 3.12 and 3.13 legs (inferred from the code and the run above; 3.12 not run). P4's old join compares by value, so its counts in this story (`probe_counts.log`) are Python 3.11 figures; its ratio stays about 64 on any version.
- Run time: about 0.1 s healthy, about 3 s on P1.
- The 4x gap would also work (4.00 against 15.46) but leaves less room; use 8x.

#### B. Trailing-particle test (`test_hybrid_particles_location_noise.py:675-696`): new input, 64x gap, alternating rounds

What it guards: `_trailing_particles_start` (`hybrid_detector.py:1274-1299`), called by `_extend_particles` (l.1208). The old code (`81befe8^`) was the `tail_parts` regex search (Context).

- **Input:** `doc = "Zorbal" + " le" * n + " Quentrix"`, entity = the whole `doc` (`_ent(doc, "PERSON", 0)`), `blocked = hd._SpanIndex([])`. Today's code returns `None` on it (the last token is not a particle, nothing follows the span): assert that once per size, outside the timed part.
- **Measure:** a helper in the file:

```python
def _alternating_ratio(
    small: Callable[[], object], large: Callable[[], object], gap: int, rounds: int
) -> float:
    """Per-call time at the large size over per-call time at the small size.

    Each round times ``gap`` small calls, then one large call, so on linear
    code both intervals take about as long and see the same runner load;
    the best round is kept for each size.
    """
    best_small = best_large = float("inf")
    for _ in range(rounds):
        start = time.perf_counter()
        for _ in range(gap):
            small()
        best_small = min(best_small, (time.perf_counter() - start) / gap)
        start = time.perf_counter()
        large()
        best_large = min(best_large, time.perf_counter() - start)
    return best_large / best_small
```

- Sizes: n = 125 and 8,000 (64x); `gap=64`, `rounds=7`; assert `ratio < 300`.
- Arithmetic (`probe_timing_g64.log`, `probe_timing_final.log`, Python 3.11 on Windows): today **19.3 to 24.9** (quiet, and with one busy process per CPU); below 64 because a call's fixed cost (about 2.5 µs) weighs more at the small size. Slowed (P2): **3,903 to 3,948** (0.54 ms → 2.1 s per call). The cap 300 is near the middle on a log scale (√(23 × 3,900) ≈ 300): healthy code fails only if the large call is slowed about 12x more than the small calls in the same rounds (the worst inflation CI showed for this test is about 6x: 20 measured where about 3.5 is expected, without alternation); the slowed copy passes only if it ran about 13x faster at the large size, which a quadratic search cannot.
- Even against the linear bound (64), the cap leaves 4.7x.
