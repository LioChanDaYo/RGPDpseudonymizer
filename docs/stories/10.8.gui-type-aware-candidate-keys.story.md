## Story

**As a** desktop-app user reviewing a name found at one place with two types,
**I want** each type to be its own candidate, with its own preview, its own occurrences and its own accept or reject,
**so that** rejecting one type keeps the other, and no occurrence of a name I confirmed is left in clear.

**Priority:** HIGH — it is a leak path in the desktop app: an occurrence of a confirmed name can stay in clear. It must be fixed before any release. It is on `main` only (since 10.3c), unreleased.
**Change type:** desktop app and core preview keys only. No detection change, so G1, G3 and G5 are N/A. No file under `gdpr_pseudonymizer/nlp/`, `gdpr_pseudonymizer/resources/`, `tests/accuracy/` or `tests/test_corpus/` changes. If any file the accuracy suite loads is touched, one regular accuracy run on the branch shows the 16 lines identical to `38212303870`.
**Ordering:** outside the detector chain, like 10.5 and 10.7. It merges before 10.7 and does not depend on 10.7's continuity decision (10.7 AC3).
**Epic:** [Epic 10: v2.3 — Detection Precision Quick Wins](../prd/epic-10-v2.3-detection-precision-quick-wins.md) (story 10.8)
**Branch:** `story/10.8-gui-type-aware-keys`, cut from `main` at `51d8429` (PR #95, Story 10.6 B15 close-out). It carries the PM's epic commits `f7637a2` (adds Story 10.8) and `9047ec0` (the PO's edits), both `docs/prd/` only, and the story commits.

### Context

## Acceptance Criteria

AC1 to AC7 are copied from the epic's Story 10.8 at `9047ec0` word for word. "AC precisions (story-level)" adds detail and does not change the epic text. AC8 to AC11 are story-level.

1. **AC1 — Keys include the type:** the preview map and the variant map key on text, start and type, and the same-text group keys on text and type, as the CLI groups already do. This covers `build_pseudonym_previews`, `detection_worker.py`, `validation_state.py` and every caller and reader of these maps (including `gui/screens/batch.py:896`).
2. **AC2 — The probe case and its reverse:** ORG "Zorbaville" at 0 and at 21 with LOCATION "Zorbaville" at 0 finalizes to every occurrence with its own type, in both list orders. No occurrence is dropped or retyped.
3. **AC3 — Rejecting one type keeps the other:** accepting or rejecting one type of a same-span pair changes only that type's group; the other type keeps its state.
4. **AC4 — No variant-map collision:** two variant groups with the same canonical text and start but different types get separate entries, and the highlight ranges map each occurrence to its own review row.
5. **AC5 — Tests first, invented names only:** unit tests for AC1–AC4 use invented names only. Run on the unchanged code, every test of a changed behaviour fails; the dev records the list. The fix then makes them pass. Existing GUI and CLI validation tests stay green; tests that build the review list's key by hand change only how they build it.
6. **AC6 — CHANGELOG:** CHANGELOG `[Unreleased]` corrects the 10.3c line "Rejecting one candidate gives the earlier result for the other", so that it holds for the desktop app too, and records the desktop-app fix.
7. **AC7 — Gates:**
   - **G1, G3 and G5 are N/A:** there is no detection change. The PR states this explicitly. If any file the accuracy suite loads is touched, one regular `accuracy.yaml` run on the branch shows the 16 lines identical to `38212303870`, cited by ID.
   - **G4:** desktop app and core preview keys only, never in the same PR as a detector change.
   - **G2:** QA re-runs the AC5 tests, checks out the tests-first commit to see them fail on the old code, and reads the diff. QA's gate comes before the merge.

### AC precisions (story-level)

- **AC1, the key shape (pre-decided; Dev Notes "Fix Design"):** one function builds the per-run key of a candidate, `candidate_key(entity) -> CandidateKey`, with `CandidateKey = tuple[str, int, str]` = (text, start, type), in `gdpr_pseudonymizer/validation/models.py`, next to `EntityGroup`. The same-text group key is (text, type), the shape of the CLI's `EntityGroup.unique_key` (`validation/models.py:416`). Tuple keys, so that `mypy gdpr_pseudonymizer` flags any reader or writer still on the old string key.
- **AC1, "every caller and reader":** `build_pseudonym_previews` and its two callers (`detection_worker.py:199`, `batch.py:896`); the preview reader (`validation_state.py:86-88`); the variant map writer (`detection_worker.py:154-157`) and its readers (`validation_state.py:328`, `:344`); the group index (`:89-93`) and its readers (`:128`, `:144`). The full list, with the consumers that need no change, is the Consumer Trace.
- **AC1, keys taken once:** each detected row's key is computed once, when the validation state is built, and stored by row id. Expansion, highlights and group actions use the stored key, never one recomputed from the row after the user edits it (Fix Design, "Why stored keys"). Two exceptions keep today's computed lookup, now with the type (Fix Design, step 4): a row whose text the user edited (`review.user_modification`; its other occurrences are Story 10.9's), and a row added by hand, which has no stored key.
- **AC2, the expected lists:** with both rows accepted, the list sent to finalization holds (LOCATION, 0, 10), (ORG, 0, 10) and (ORG, 21, 31), each exactly once, in both list orders; the finalized output contains no "Zorbaville". "Dropped" is a detected (type, start, end) missing from the list; "retyped" is one that appears under another type, or twice.
- **AC3, scope:** every accept and reject reaches only the rows of the same text and type, in the single-document path and in the batch path, and for one text with different types at different places too. Undo of one group action restores only that group.
- **AC4, ranges:** for the pair, `get_all_entity_ranges` returns exactly three ranges: (0, 10) and (21, 31) for the ORG row, and (0, 10) for the LOCATION row.
- **AC5, the existing tests:** four existing tests build or assert the old `"{text}_{start}"` key by hand and fail once the key includes the type, as the SM's prototype showed (Dev Notes "Existing Tests That Build a Key by Hand"). The dev changes only how those four build or look up the key, using `candidate_key`, with a comment citing 10.8 AC1; no asserted value changes. The fourth edit is in the shared fixture `sample_detection_result` (`tests/unit/gui/conftest.py:134-155`, key at `:143`), and every test that uses that fixture stays green. Every other existing test passes unchanged. AC5's last sentence says this since `9047ec0`.
- **AC5 and AC8, the list:** the tests-first commit holds 15 tests that fail on the unfixed code (T1–T9) and 3 guard tests that pass on it (T10–T12). The dev records both lists with their local outcomes (Task 1.2).
- **AC6, the wording:** Dev Notes "CHANGELOG Entry".
- **AC7, G1 condition:** the accuracy suite loads 13 product files (SM import probe, Dev Notes "Code Map"): `gdpr_pseudonymizer/__init__.py`, eight files of `nlp/`, `resources/__init__.py`, `utils/__init__.py`, `utils/french_patterns.py` and `utils/logger.py`. The pre-decided fix touches none of them, so no G1 run is needed. If the diff touches one, the dev stops and reports, and the G1 run is required.
- **AC7, G2:** QA re-runs the new tests, checks out the tests-first commit and runs the new tests there with `--runxfail` to see the 15 fail, reads the diff against Fix Design, and probes (Task 7).

### Product Constraints (non-negotiable, verbatim from the epic)

[Source: prd/epic-10-v2.3-detection-precision-quick-wins.md#Product Constraints]

These apply to every story in this epic. A story that cannot meet its goal inside them stops and goes back to Lionel; it does not relax them.

1. **Local NLP only.** No LLM, no generative model, no API call, no cloud service, no telemetry. Every change is a deterministic rule, lexicon or pattern that runs offline.
2. **No encoder NER models.** Introducing a transformer/encoder NER model (e.g. CamemBERT-NER) is a Lionel decision that belongs to Epic 9. It must not be introduced in this epic, including as an optional dependency or experiment committed to the repo.
3. **Mandatory human validation stays.** No auto-accept mode, no `--no-validate`, no confidence-based skipping. Precision gains reduce the reviewer's workload; they do not replace the reviewer.
4. **No user data** for training, tuning or evaluation. All corpus and held-out documents are synthetic.
5. **Recall over precision.** Missing a real person is worse than showing an extra candidate. Any drop in overall recall or in any per-type recall needs Lionel's sign-off (gate G3).
6. **No public accuracy claim without CI evidence.** Every number that reaches README, FAQ, docs, CHANGELOG or the QA report comes from a cited CI accuracy run (gate G1).

For 10.8: constraints 1, 2 and 4 hold trivially (no detection change, no model, no data). Constraint 3: the fix makes the reviewer's choice reach each type separately; no review step is skipped or auto-accepted. Constraint 5: the fix closes a desktop-app path that left an occurrence of a confirmed name in clear. Constraint 6: the CHANGELOG entry carries no accuracy number.

### Fix Design (pre-decided)

1. **Key function**, in `gdpr_pseudonymizer/validation/models.py`, next to `EntityGroup` (with `from typing import TypeAlias`):

   ```python
   CandidateKey: TypeAlias = tuple[str, int, str]  # (text, start_pos, entity_type)


   def candidate_key(entity: DetectedEntity) -> CandidateKey:
       """Per-run key of one candidate in the desktop app: text, start and type."""
       return (entity.text, entity.start_pos, entity.entity_type)
   ```

   - A tuple, not a string: `mypy gdpr_pseudonymizer` (strict, `ci.yaml:49`) then flags any reader or writer left on the old string key, and no text can collide with a separator.
   - This module: `validation_state.py` already imports it (`:16-20`), `document_processor.py` already imports the validation package (`:47`), and it keeps the heavy `core` import out of the desktop app's review model. The accuracy suite does not load it.
   - The group key is `(text, entity_type)`, the shape of `EntityGroup.unique_key`.
   - `candidate_key` is the key of one review session's rows and previews. It is not the mapping-database key (`_normalize_entity_text`, `document_processor.py:211-232`), which is Story 10.7's. Neither story reuses the other's key.

2. **`build_pseudonym_previews`** (`document_processor.py:759-802`): returns `dict[CandidateKey, str]`; key `candidate_key(entity)` at `:786`; docstring `:775`. The assigner and the preview values do not change (#5 is 10.7's).

3. **Detection worker** (`detection_worker.py`): `pseudonym_previews: dict[CandidateKey, str]` (`:31`); `variant_occurrences: dict[CandidateKey, list[DetectedEntity]] | None` (`:40`) and its comment (`:38-39`); the map at `:154-157` keyed by `candidate_key(canonical)`. Import `CandidateKey` under `TYPE_CHECKING` (`:19-20`) and `candidate_key` inside `_run_detection` with the other local imports (`:88-90`, `:147`), as the module does today.

4. **`GUIValidationState`** (`validation_state.py`):
   - New `self._candidate_key_by_id: dict[str, CandidateKey]`, cleared with the other maps. `_pseudonym_previews` and `_variant_occurrences` take `CandidateKey` keys; the group index becomes `dict[tuple[str, str], list[str]]` (its comment `:47` updated; renaming it is allowed).
   - **`init_from_detection_result`:** for each row, `key = candidate_key(review.entity)` once; store it by `entity_id`; read the preview with it; append the id to the group `(key[0], key[2])`.
   - **Group lookup** (accept `:128`, reject `:144`) through one private helper: a row with a stored key uses its (text, type); a row without one (added by hand) uses `(review.entity.text, review.entity.entity_type)`, as it is now plus the type; fallback `[entity_id]`. A group action on a retyped row acts on its original (text, type) group: group membership is fixed at init, as today's text group is. That is intended (PO N5).
   - **`expand_validated_entities` and `get_all_entity_ranges`:** look up the variant map with the row's stored key. Two exceptions keep today's computed lookup, now with the type: a row with a text edit (`review.user_modification`), computed in `expand` from the entity `get_validated_entities` builds for it and in the ranges from `review.entity`, as today; and a row added by hand, which has no stored key.
   - To pair rows with the entities `get_validated_entities` builds, move its loop (`:287-311`) into a private helper that yields (row, entity). `get_validated_entities` returns the entities, with the same output as today.
   - **Why stored keys:** `_ChangeTypeCommand` (`:507`) and `_ModifyTextCommand` (`:436-437`) change `review.entity` in place, and that object is also the canonical inside the variant map's occurrence list. A key recomputed from the edited row would miss the map after a type change, and the group's other occurrences would be dropped from finalization: a new leak. Today's text-only key does not see the type, so today the row still expands (SM probe 6). T10 guards it.
   - Unchanged: `classify_known_entities` (10.7 AC4), the bulk actions, accept-all-of-type, accept-all-known, the undo commands, `is_entity_known`, `get_pseudonym`.

5. **Not changed:** `gui/screens/batch.py` (it passes the map through; its `except` branch's `{}` stays valid), `gui/screens/validation.py` apart from its `set_context` docstring line (`:332`), every `nlp/` file, the CLI, `data/`. Shape, for orientation only (the dev writes the real code):

