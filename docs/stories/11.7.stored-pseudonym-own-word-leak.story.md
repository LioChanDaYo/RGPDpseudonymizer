### Context

**The leak in stored rows.** Before Story 11.6, the library drew a new name's pseudonym without looking at the name. So a saved row can hold one of its own words: « Élodie Martin » saved as « Élodie Lucas », « Marseille » saved as « Marseille », « Mairie de Lyon » saved as « Groupe Commercial Lyon ». Story 11.6 stops new draws from doing this. It does not touch saved rows, by design: "a name already stored keeps its pseudonym" (its AC5, T9).

**They keep leaking, and they spread.** Reproduced on `main` `8bf265d` (`r117\sm\repro117.py`, `logs\repro117.log`), with three rows saved as 2.3.0 could have saved them, then two later documents through the real `DocumentProcessor.finalize_document`:

| Document written later | Written |
|---|---|
| « Élodie Martin a appelé. Élodie est partie. Élodie Petit est venue à Marseille. » | « Élodie Lucas a appelé. Élodie est partie. Élodie Sousa est venue à Marseille. » |
| « La Mairie de Lyon a écrit à Élodie Vaz. » | « La Groupe Commercial Lyon a écrit à Élodie Clément. » |

- The saved row is reused as saved: « Élodie » and « Marseille » stay in clear in every later document.
- One saved first name becomes everybody's: a lone « Élodie » is saved as « Élodie », and « Élodie Petit » and « Élodie Vaz » are saved with first name « Élodie », because one real first name keeps one pseudonym first name (Story 2.8, Story 10.11 Q-D). After the two documents, 6 rows leak: the 3 saved, plus 3 new ones that inherited « Élodie ».
- Story 11.6 does not change this: it compares only values the library draws, and these are reused, not drawn.

**Measured** (Dev Notes "Measurements"): on databases built with today's code from realistic documents (people recurring across documents, lone first names, « M. Dupont »), with the default `neutral` library:
- **Leaking rows: in the 11 « common » databases (10,816 rows), 120 rows, 11 in 1,000 (from 1 to 30 in 1,000 depending on the database); in the 11 « mix » databases (9,819 rows), 28 rows, 3 in 1,000 (from 0 to 6). People: 94 and 5 of those rows.**
- They come in groups: one leaking first or last name is shared by every row of that real name. The largest group held 51 rows.
- A replacement can move rows that do not leak: 11 of the 23 person groups held some, up to 48 in one group (the real last name Martin's part « Daniel » leaks only for « Daniel Martin », but 51 rows hold it, 48 of which leak nothing). The user sees every row that will change before confirming (Dev Notes "Groups").
- Places and organisations: 49 rows, of which 41 are organisations that share only a common word with their own name (« Centre », « Agence », « Chambre », « Institut de »), and 8 share a real place word (6 places saved as themselves, 2 organisations holding their own city). Lionel's rule reports only the 8 ("report only real leaks").

**Why the user decides, row by row.** Replacing a saved pseudonym breaks the link with documents already written: they keep the old pseudonym, and the database will no longer say which name it stood for. Processing those documents again writes the new pseudonym (checked: nothing in `gdpr_pseudonymizer/` calls `set_file_hash`, `get_file_hash` or `set_file_processed`, so a document processed again is never skipped). So the app finds and explains; the user replaces.

## Acceptance Criteria

AC1 to AC6 follow Epic 11's Story 11.7 scope. The others are story-level. Each AC names its check, run on the final head unless it says otherwise. `<base>` is `main` after Stories 11.6 and 11.4 merge, the commit the branch is created from.

1. **AC1: The check finds the saved rows that leak a word of their own name.**
   - For each saved row, its pseudonym is compared with its own name only: no document is needed. The comparison is Story 11.6's, through its helpers (Fix design 1): folded (capitals and accents ignored), every run of the pseudonym's whole words and each part of a hyphenated word (`_drawn_runs`, the runs Story 11.6 v1.4/v1.5 compares for a drawn value), a linking word followed by another word never compared alone (Q-I), for every type (Lionel's "widen"); a place's or an organisation's run is kept only when it is the whole pseudonym, the whole name, or holds a place of the pseudonym library (Lionel, "report only real leaks").
   - It covers a person's first part, last part (including a last part that is the person's own first name), a lone first or last name, a place, and an organisation.
   - It skips rows of theme `custom` (a custom pseudonym is refused when it holds a word of its own name, Story 10.16) and `neutral_id` (identifiers).
   - It is read-only: no row, no audit entry, no metadata changes.
   - Check: T1 to T3.
2. **AC2: Command line report.** `validate-mappings` shows `OWN` in its Flags column for each row found, and one summary line with their count. A new option `--own-words` lists only those rows, with their ID (8 characters, as `list-entities` shows it) and the word found, then the line that names `replace-pseudonym`. The command stays read-only. Without a row found, `--own-words` prints its "none" line and exits 0. Check: T1 to T3; `validate-mappings` on a database with no leaking row prints what it prints on `<base>` (T15, control).
3. **AC3: Desktop report.** The database screen ("Base de correspondances"), once a database is open, shows the count of rows found in one line under the database line, a tick box that shows only those rows, and, on each of their pseudonym cells, a tooltip naming the word. The check runs in the `DatabaseWorker` thread, never in the window's thread. Without a row found, none of these is shown. Check: G1.
4. **AC4: Command line replacement.** A new command `replace-pseudonym`, modelled on `delete-mapping` (Dev Notes "Why a new command"):
   - `--id <id>` (full or the 8-character prefix, as `delete-mapping --id`), or `--all` (every row found); exactly one of them;
   - it lists what will change: the rows that leak, with their word, and under a second heading the rows that share the replaced part and change with them; then the warning; then « Type 'yes' to replace these pseudonyms »; `--force` skips the question;
   - an `--id` whose row is not found by the check is refused with its message, and nothing changes;
   - after the replacement it prints each changed row's name, old pseudonym and new pseudonym once, on screen only;
   - exit codes as `delete-mapping`: 0 done or cancelled, 1 refused, 2 unexpected.
   - Check: T4 to T10.
5. **AC5: Desktop replacement.** On the database screen, a button « Remplacer la sélection (%1) » counts the ticked rows that the check found (ticked rows it did not find are ignored) and is enabled only when that count is above 0. It opens a confirmation that lists the rows that leak and the rows that change with them, with the warning, then a new `DatabaseWorker` operation `"replace"` replaces them and the screen reloads the table. A wrong passphrase sets `is_passphrase_error`, as the delete operation does, so the remembered passphrase is forgotten. Check: G2 to G5.
6. **AC6: What a replacement does** (Fix design 3 and 4):
   - **Groups.** A person's leaking part moves with every person row whose real word in that role is the same (folded; a one-word name in both roles, as `untracked_custom_values` reads it) and whose part in that role is the same (folded). A place, an organisation, or a person row whose pseudonym has no stored parts, is its own group.
   - **One new value per group,** drawn from the library of the leaking row's theme, with its stored gender for a first name. It is drawn again when:
     - a run of it is a word of the name of any row of the group, or of any saved name (Story 11.6's names half, over every saved name: no document exists here);
     - it is already a part, in either role, of any saved row, the group's own rows included (one part, one real word; no first part equal to a last part, the overlap of Dev Notes "Found while preparing"; and no row whose new last part equals its own first part). Only the replaced part itself is not counted, and it is refused anyway as the own word;
     - one of the group's new full pseudonyms is already a saved full pseudonym (of any row, any type), or takes a custom pseudonym's value (`takes_custom_value`).
     - In one replacement, "saved" includes what the groups drawn before this one now hold (PO, v1.4): all rows are written in one commit at the end (AC7), so each group is drawn on the rows as the earlier groups left them in memory, never on the database alone. Otherwise two groups of one `--all` can draw the same new part for two real words.
   - **Every candidate goes through these refusals.** No saved binding is reused without them: a row outside the group whose saved binding has the same real word in that role and another part must not hand its part to the group unchecked (Fix design 4, "Traps in that call"; Overfitting Check O12). A person part never comes from the library's fallback (`Person-NNN`); if it would, the group is treated as run out.
   - **The old value is freed** (Lionel, "forget"): nothing reserves it.
   - **The lists drawn from** are the library's as Story 11.6 leaves them: a last name it removed from the last-name list is never drawn; stored rows keep theirs (Dev Notes "Story 11.6's last-name list").
   - **Bounded.** At most 100 attempts per group, as the library's loops. A person group that runs out stops the whole replacement: nothing is written, and the user is told. A place or an organisation that runs out gets today's fallback (`Location-001`, `Org-001`), shown to the user.
   - **The rest stays.** Each row keeps its id, name, name parts, type, theme, gender, confidence, first-seen time and ambiguity flag; only `pseudonym_full`, `pseudonym_first` and `pseudonym_last` change, and only on the rows of the groups. Rows outside the groups do not change.
   - **A group that holds a custom row** (possible only when the leaking part is the other role's word, Dev Notes "Groups") stops the whole replacement, nothing written, and the user is told.
   - Check: T4 to T8, T11, T14, T19, T22.
7. **AC7: One transaction, under the lock, as confirmed.**
   - The groups are computed again under `pseudonym_lock`, from the rows read inside it. If the rows that will change differ from the rows the user confirmed (a document saved a row sharing the part in between), nothing is written and the user is told to run it again.
   - All rows of all groups are written in one commit, by a new repository method (Fix design 2); an error rolls everything back.
   - A document finalized at the same time either finishes before (and its new rows are then in the groups, so the check of the first point stops the replacement, or they are in no group), or waits and then reuses the new parts.
   - Check: T13 (three cases).

### The rule (find)

- **The runs** are Story 11.6's runs of a drawn value (`_drawn_runs`, its v1.4/v1.5): every run of the pseudonym's whole words (cut at spaces), except a linking word followed by another word (Q-I), then each part of a hyphenated word (« Saint-Denis » also as « Saint », « Denis »), a lone linking word still not. For every type (Lionel's "widen"). A saved pseudonym was drawn, so it is compared as Story 11.6 compares a drawn value, and the find and the redraw (`real_name_check`, which uses `_drawn_runs`) apply one rule. Measured on `3cd82ba` (v1.3, `logs\find117_main.log`): with `_drawn_runs` and main's library lists the find gives exactly the rows `_runs_by_word` gave, database by database (100 and 7; no hyphen part added a row).

- **The name** is the row's `full_name` (the mapping key: titles taken off, a place's leading preposition taken off).
- **A place or an organisation** (Lionel, "report only real leaks"): its run is kept only when it is the whole pseudonym, the whole name, or holds a place of the library of the row's theme as consecutive whole words (`_flatten_location_list`, `library_manager.py:237`, compared folded with `_occurrence`). ### Groups (what moves together)

One real first name keeps one pseudonym first name, and one real last name one pseudonym last name (Story 2.8; Story 10.11 Q-D). `load_existing_mappings` (`library_manager.py:818-897`) rebuilds that binding from every saved row, and `find_standalone_components` (`assignment_engine.py:352-393`) reuses the first saved match. So a replaced part must move on every row that holds it for the same real word, or the next document picks either one by query order.

**A group, for a person's leaking part** in role R (first or last), with real word W and part P:
- every person row (theme not `neutral_id`) whose real word in role R folds to W, and whose part in role R folds to P;
- a row's real word in a role is its `first_name` for "first" and its `last_name` for "last"; **a one-word row** (`last_name` None: a lone first or last name, saved with its word in `first_name`, `document_processor.py:727-730`) has its one word in both roles, as `untracked_custom_values` reads it (`custom_pseudonym.py:859-875`). Its part sits in `pseudonym_first` when the engine matched a first name and in `pseudonym_last` when it matched a last name (`assignment_engine.py:411-445`).

**A row with no stored parts** (a pseudonym drawn by `_assign_untaken_pseudonym`, `document_processor.py:785-846`, keeps none) that leaks, a place and an organisation are each their own group.

**A group can hold rows that do not leak.** Example, measured shape: « Thomas Durand » saved as « Paul Thomas » leaks « Thomas » through its **last** part, which is the real last name Durand's part; « Jean Durand » saved as « Luc Thomas » shares it and does not leak. Replacing the first moves the second, so that Durand keeps one part. The user is shown these rows under their own heading before confirming (AC4, AC5). Measured: 11 of the 23 person groups found in the 22 databases held rows that do not leak, up to 48 in one group: in `common_6.db` the real last name Martin had the part « Daniel », which leaks only for « Daniel Martin »; 51 rows hold it, and replacing it moves them all, 48 of which leak nothing.

**A custom row in a group.** A custom pseudonym is refused when it holds a word of its own name (Story 10.16), but Q-D makes it take the part its real word already has. So a custom row can share a group only in the cross-role case above: « Paul Durand » with the custom « Jean Thomas ». A custom pseudonym is the user's choice; this story does not change it, so the replacement stops with its message. Measured: no generated database holds one (they have no custom rows); T14 pins the behaviour.

### Why a new command (and not an option)

- `validate-mappings` is read-only by contract: its docstring says "This command does NOT modify the database" (`validate_mappings.py:66`), its table "This is a read-only view. No modifications will be made." (`:180`), and its interactive mode "no database changes are made". So it gets the report (`OWN`, `--own-words`), which is read-only, and nothing that writes.
- `delete-mapping` erases, with `ERASURE` audit entries and GDPR Article 17 texts; a replacement is not an erasure.
- `list-mappings` and `list-entities` are listings with search and export.
- So the write is a new command, `replace-pseudonym`, built like `delete-mapping` (the same options style, `--id`, `--force`, typed `yes`, one audit entry), so users find a familiar shape.
