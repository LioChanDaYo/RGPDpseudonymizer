### Context

Measured by the orchestrator on `9dafd44` (Epic 12, "Problem") and re-read by the SM:

- `!define INSTALLDIR "$PROGRAMFILES\${APPNAME}"` (l.17), `InstallDir "${INSTALLDIR}"` (l.27), `InstallDirRegKey HKLM "Software\${APPNAME}" "InstallDir"` (l.28). An upgrade reuses the previous folder. « Parcourir » appends « GDPR Pseudonymizer » to the folder chosen (NSIS §4.8.1.21). A folder typed by hand is used as typed.
- At install, `RMDir /r "$INSTDIR\_internal"` (l.109) runs before `File /r` (l.112), after the 2.3.2 check that the app and the command line are closed (l.84-100).
- At uninstall, `RMDir /r "$INSTDIR"` (l.158) deletes the whole folder; `RMDir /r "$SMPROGRAMS\${APPNAME}"` (l.161) the Start Menu folder.
- Risk (a): a typed folder such as `D:\Outils` is wiped entirely at uninstall, the user's own files included.
- Risk (b): a typed folder that already holds another PyInstaller app loses that app's `_internal` at install.
- The previous folder is saved at the end of the install section, `WriteRegStr HKLM "Software\${APPNAME}" "InstallDir" "$INSTDIR"` (l.138). On Lionel's machine it reads `C:\Program Files (x86)\GDPR Pseudonymizer` under `HKLM\Software\WOW6432Node\GDPR Pseudonymizer` (the 32-bit installer's registry view; `reg query`, read-only, 2026-11-18).
- The Windows installer has 25 downloads across 8 releases. No user report.

**What happens to the existing installs** (Epic 12, Lionel's third decision):
- Default folder or « Parcourir »: the folder already ends with « GDPR Pseudonymizer ». The new version upgrades in place and installs the new uninstaller. No message.
- Hand-typed folder (`D:\Outils`): the new version goes into `D:\Outils\GDPR Pseudonymizer`; nothing in `D:\Outils` is changed or deleted. At the end of the installation a message says where the new copy is, that the old copy is still in `D:\Outils` and can be deleted by hand, which files to delete, and not to run that folder's `Uninstall.exe` (the PM's addition: an NSIS uninstaller works on the folder it runs from, NSIS §4.2.2; the old one still runs `RMDir /r "$INSTDIR"` and would delete all of `D:\Outils`, the new subfolder included, plus the registry entries and shortcuts that now belong to the new copy).

**Known limitation (recorded in Epic 12, not fixed):** an install that is never upgraded keeps its old uninstaller, which still deletes its whole folder. The old copy left in a hand-typed folder keeps its old uninstaller too; the message covers that case. Lionel, 2026-11-18: it also goes to `docs/BACKLOG.md` as KL-012 (question 3 below, Task 5.1).

### Mechanism

Reference code follows. Its behaviour is the contract (the tests pin it); the dev may rename labels, not change the logic.

**1. The folder rule, one function used everywhere.**

- Why not `.onVerifyInstDir`: it only accepts or refuses the folder ("If this function calls Abort, the installation path in $INSTDIR is deemed invalid", NSIS §4.7.2.1.10). It cannot append the last part, and it runs on every edit of the field.
- Why not the page alone: a silent install shows no page, and `/D=` "sets the default installation directory ($INSTDIR), overriding InstallDir and InstallDirRegKey" (NSIS §3.2.1). So the rule also runs in `.onInit` ("called when the installer is nearly finished initializing", §4.7.2.1.2), where `$INSTDIR` already holds the `/D=` folder or the registry folder (§4.8.1.22: `InstallDirRegKey` "will override the InstallDir attribute if the registry key is valid"). The directory page then shows the final folder. Checked by the PO in the NSIS source (`kichik/nsis` master, 2026-11-18): `Source/exehead/Main.c` copies `/D=` into `$INSTDIR` while parsing the command line; `Source/exehead/Ui.c` (`ui_doinstall`) then reads the registry only if that folder is not valid, falls back to `InstallDir`, and only after that calls `.onInit`. Two consequences the tests model: the registry folder arrives with a **trailing backslash** (`mystrcpy(state_install_directory, addtrailingslash(p))`), so a default install starts `.onInit` as `C:\Program Files (x86)\GDPR Pseudonymizer\` and `TrimFolder` is what keeps it in place; and a `/D=` folder arrives raw. A drive root is never valid (`is_valid_instpath` with no `AllowRootDirInstall`), so `/D=D:\` is ignored and the page refuses `D:\`.
- The page: MUI2 "Page Custom Functions" (Modern UI 2 readme): "These defines should be set before inserting a page macro". **The leave function's change to `$INSTDIR` alone is lost** (PO, NSIS source): on Next, `Ui.c` (`DialogProc`) runs the page's leave function first, then sends `WM_NOTIFY_INIGO_MONTOYA`, on which `DirProc` does `GetUIText(IDC_DIR, dir)` and `validate_filename(dir)`, reading the folder field back into `$INSTDIR`. So `OwnFolderLeave` also writes its result into the field (control 1019, the same handle MUI2's `Pages\Directory.nsh` takes with `FindWindow ... "#32770" "" $HWNDPARENT` and `GetDlgItem ... 1019`), with `SendMessage ... ${WM_SETTEXT} 0 "STR:$INSTDIR"` (`WinMessages.nsh`, included by MUI2). In the leave function `$INSTDIR` is the raw field text (NSIS trims trailing backslashes and spaces only after it), hence `TrimFolder` removes spaces too.
- First in `SecMain`: this call is what guarantees AC1 and AC3 at install time, whatever set `$INSTDIR` (the page, `/D=`, the registry). The leave function only makes the page and the later pages show the final folder.
- The check compares the last 19 characters, backslash included, with `\GDPR Pseudonymizer`: `StrCmp` "compares (case insensitively)" (§4.9.4.25); `StrCpy` with a negative start offset "will start abs(start_offset) from the end of the string", and a negative maxlen truncates from the end (§4.9.8.1). The backslash matters: with 18 characters, `D:\XGDPR Pseudonymizer` would pass. `${GetFileName}` (FileFunc, Appendix E.1.16) is not used: its handling of a trailing backslash is not documented.

```nsis
Var OldInstDir  ; the previous install's folder, read in .onInit (declare before the LangStrings)

; In: a folder on the stack. Out: the same folder without trailing
; backslashes or spaces.
Function TrimFolder
    Exch $0
    Push $1
    trim_loop:
    StrCpy $1 $0 1 -1
    StrCmp $1 "\" trim_one
    StrCmp $1 " " trim_one trim_done
    trim_one:
    StrCpy $0 $0 -1
    Goto trim_loop
    trim_done:
    Pop $1
    Exch $0
FunctionEnd

; In: a folder on the stack. Out: that folder, trimmed, ending in
; \GDPR Pseudonymizer (capitals ignored): the folder itself when it already
; ends so, otherwise its « GDPR Pseudonymizer » subfolder.
Function OwnFolderOf
    Call TrimFolder
    Exch $0
    Push $1
    Push $2
    StrLen $2 "\${APPNAME}"   ; 19
    IntOp $1 0 - $2           ; -19
    StrCpy $1 $0 $2 $1        ; the last 19 characters
    StrCmp $1 "\${APPNAME}" own_done
    StrCpy $0 "$0\${APPNAME}"
    own_done:
    Pop $2
    Pop $1
    Exch $0
FunctionEnd

Function .onInit
    ReadRegStr $OldInstDir HKLM "Software\${APPNAME}" "InstallDir"
    Push $INSTDIR
    Call OwnFolderOf
    Pop $INSTDIR
FunctionEnd

; NSIS reads the folder field back into $INSTDIR after this function, so
; the result is also written into the field (control 1019).
Function OwnFolderLeave
    Push $1
    Push $INSTDIR
    Call OwnFolderOf
    Pop $INSTDIR
    FindWindow $1 "#32770" "" $HWNDPARENT
    GetDlgItem $1 $1 1019
    SendMessage $1 ${WM_SETTEXT} 0 "STR:$INSTDIR"
    Pop $1
FunctionEnd
```

**New helpers** (new functions or a small class; the existing ones keep their behaviour):
- `_block(kind, name)`: the statements (token lists, as `_tokens` gives) of `Function <name>` ... `FunctionEnd` or `Section "<name>"` ... `SectionEnd`; raises `AssertionError` when absent.
- `_defines()`: the `!define` values (`APPNAME`, `INSTALLDIR`, ...), to expand `${...}` in strings.
