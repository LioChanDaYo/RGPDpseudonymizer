#### Custom pseudonyms refused at finalization

Two people of one document share a first name. The user chooses « Aurore Bruneau » for « Élodie Martin », then « Aurore Le Goff » for « Élodie Dupont ». Both are accepted during review. Finalization refuses both, writes nothing, and says: "A pseudonym you chose can no longer be used: the first or last name now has a different part in the mapping database. Nothing was written." The database was empty. In the other order, the second choice is refused during review with "The first name 'Élodie' is already replaced by 'Aurore Le'…". New in v2.3.0 (Stories 10.11, 10.16).

**Cause, re-read on `283e211`:**
- When a custom pseudonym is checked, the review's *other* custom pseudonyms are split into a first-name part and a last-name part. That tells the check which part each real first or last name already has (Lionel's Q-D).
- `_bound_parts` (`core/custom_pseudonym.py:468-483`) splits each of them with the stored parts only (`:473-475`, `_bound_of(stored, other_name)`), never with the parts the pseudonym under check gives.
- At finalization, « Aurore Le Goff » is therefore split by the Q4/Q-G rule as « Aurore Le » + « Goff », and « Aurore Bruneau » then breaks Q-D.
- During review, « Aurore Le Goff » was split « Aurore » + « Le Goff », because « Aurore Bruneau » was already there. That is MW-001 (b): a part that another custom pseudonym of the review gives is matched whole first.
- The two sides disagree, and the outcome depends on which name is checked with which.

#### Particle surname split from its surname

« Inès Le Goff » chosen alone is stored as « Inès Le » + « Goff », by Lionel's 10.11 Q-G rule ("Keep the app's four whole": split at the last space except Da Silva, Le Gall, Da Costa, Espírito Santo; `docs/stories/10.11.custom-pseudonym.story.md:240`, `:366-376`). As a result:
- A later lone « Ségolène » is written « Inès Le ».
- A later « Ségolène Martin » gets « Inès Le Ferreira ».
- A custom pseudonym for another Ségolène must start with « Inès Le ».

On 2026-11-05 Lionel widened the rule (D1): a linking word just before the last word stays with the last name.

#### Import replace ignored

With `gdpr-pseudo import-mappings <source> --no-skip-duplicates`, answering yes to « Replace existing mapping? » (`cli/commands/import_mappings.py:182`) builds a new row (`:199-214`) instead of updating the existing one. The unique key `(full_name, entity_type)` refuses it, and `except DuplicateEntityError: skipped += 1` (`:217-218`) counts it as skipped. The summary says "Imported: 0", "Skipped: 1"; the old pseudonym stays. Already in v2.2.0.

### Fix design: custom pseudonyms refused at finalization

The change is in `core/custom_pseudonym.py` only. Every site goes through `_bound_parts`, which has two callers:
- `check_custom_pseudonym` (`:581`), used by the CLI check when a pseudonym is set (`core/document_processor.py:540`), the desktop check when a pseudonym is set (`gui/models/validation_state.py:760`) and the finalization check (`core/document_processor.py:588`);
- `custom_entity_fields` (`:710`), which gives the stored parts (`core/document_processor.py:611`).

The change:
1. **New argument.** `_bound_parts(stored, other_customs, own=None)`, where `own` is the `(name, entity_type, pseudonym)` under check.
   - When `own` is given, first split its pseudonym with its own stored parts: `split_custom_pseudonym(pseudonym, entity_type, *_bound_of(stored, name))`.
   - Put the parts it gives its real first and last name into a **hint**: a copy of `stored`, filled with `setdefault` per key, as today's loop does.
2. **Splitting the others.** Split each other custom pseudonym with `_bound_of(hint, other_name)` in place of `_bound_of(stored, other_name)` (`:474`).
   - Everything else in the loop is unchanged.
   - The returned mapping is built exactly as today: `stored`, then the others' parts.
   - The hint never enters it, so a pseudonym never satisfies Q-D by itself.
3. **The two calls.** `check_custom_pseudonym` (`:581`) and `custom_entity_fields` (`:710`) pass `own=(name, entity_type, pseudonym)`. Nothing else changes in this commit.

**Why it holds.** This is MW-001 (b) applied both ways. 10.11 AC17 (b): "a part that the real name already has is matched whole first", where a part that "another custom pseudonym of this review gives" counts. The result no longer depends on the order the names are checked in. So the checks while setting, the check at finalization and the stored parts agree.

### Fix design: particle surname split from its surname

1. **The new rule.** In `split_custom_pseudonym` (`:127-163`), after the `bound_last` and `bound_first` checks and before the loop over `library_two_word_last_names()`, add:

   ```python
   if len(words) >= 3 and fold(words[-2]) in LINKING_WORDS:
       return " ".join(words[:-2]), " ".join(words[-2:])
   ```

### Fix design: import replace ignored

1. **`MappingRepository.replace_mapping(self, entity_id: str, entity: Entity) -> Entity`**, abstract, beside `save` (`data/repositories/mapping_repository.py:348`).
   - Docstring: "Replace a stored row's mapping with another row's, in one transaction (Story 11.2)."
   - Raises `DatabaseError` if the row is gone or the write fails.
2. **`SQLiteMappingRepository.replace_mapping`:**
   - Load the row by id: `self._session.query(Entity).filter(Entity.id == entity_id).first()`, as `delete_entity_by_id` does (`:1078-1106`). If there is none, raise `DatabaseError("Entity to replace not found")`, with no name in it.
   - From `entity`, set `pseudonym_full`, `pseudonym_first`, `pseudonym_last`, `first_name` and `last_name`, each encrypted with `self._encryption.encrypt` as in `_encrypt_entity` (`:1143-1171`). Set `theme`, `gender`, `confidence_score`, `is_ambiguous` and `ambiguity_reason` unencrypted.
   - Keep the row's `id`, `entity_type`, `full_name` and `first_seen_timestamp`.
   - One `commit()`. On `OperationalError` or `IntegrityError`, `rollback()` and raise `DatabaseError` with the error kind only.
   - Return `self._decrypt_entity(row)`.
   - **Why `full_name` keeps the target's bytes:** since Story 10.20, `find_by_full_name_and_type` (`:476-515`) also finds a row saved in another Unicode form, and the key that matched is the target's.
   - **Why `theme` comes along:** it says where the pseudonym came from, and `custom` rows are read by `untracked_custom_values` (`core/custom_pseudonym.py:735`).
3. **`import_mappings_command`:**
   - After a yes at `:182`, call `target_repo.replace_mapping(existing.id, entity)`, add 1 to a new `replaced` counter (initialised beside `imported`, `:121-123`), and `continue`.
   - A `DatabaseError` there adds 1 to `errors` and logs `import_entity_error` with `entity_type` and `error_type` only, like `:219-226`.
   - Unchanged: the insert path for a name not in the target (`:186-218`), its `DuplicateEntityError` branch, and the no branch (`:182-184`).
4. **The summary (Lionel's Q-T1, option a):**
   - Right after the "Imported:" line (`:230`), add `if replaced: console.print(f"  Replaced: [green]{replaced}[/green]")`.
   - `replaced=replaced` joins the `import_complete` log fields (`:235-241`); it is a count, no name.
5. **Not in scope:** no check that the imported pseudonym is free in the target, and no first-name/last-name consistency check after a replace. The plain import inserts without either today, and nothing in the evidence asks for them.
6. **Not prototyped (PO, v1.2).** Unlike the two custom-pseudonym changes, this design was not run before the story. The dev measures, and pastes in the Debug Log:
   - T13: the encrypted `full_name` column byte-identical, and `id` and `first_seen_timestamp` unchanged, read from the table after the replace;
   - that `_decrypt_entity(row)` after `commit()` returns the new pseudonym (the commit expires the loaded attributes, which are then read again);
   - that the diff of `replace_mapping` holds exactly one `commit()`;
   - that `tests/unit/cli/commands/test_import_mappings.py` and `test_import_mappings_type_aware.py` pass unchanged (the PO's grep: the only existing `--no-skip-duplicates` test answers no).

   If one of them does not hold, the dev stops and the orchestrator is told before any change to this design.
