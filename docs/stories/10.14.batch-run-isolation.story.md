## Story

**As a** desktop-app user,
**I want** each batch and each finalization to write exactly the review I validated, and a running batch never to be replaced or lost by opening something else,
**so that** no name is left in clear because another run or a late change got mixed in.

**Priority:** HIGH — release blocker for v2.3.0 (Lionel, 2026-10-16). Both are leaks (Codex P0).
**Change type:** desktop app: every route that opens a document or a folder while a batch runs, and its message; the batch run's hand-offs between screen and worker; the finalization hand-off; the review's controls while a document is written. No detection change, so G1, G3 and G5 are N/A. No file under `gdpr_pseudonymizer/nlp/`, `gdpr_pseudonymizer/resources/`, `tests/accuracy/` or `tests/test_corpus/` changes.
**Ordering:** outside the detector chain. Its own PR; stories that change the same file are sequenced and the later one is rebased on the earlier, never merged together. It comes after 10.13: both change `gui/screens/validation.py` (`_on_finalize`'s batch branch) and the `gui/i18n/` files; the `.qm` files are binary, regenerated after the rebase, never merged. ## Acceptance Criteria

AC1 to AC10 are copied from the epic's Story 10.14 at `1f35dae` word for word. "AC precisions (story-level)" adds detail and does not change the epic text.

1. **AC1 — Refused while a batch runs (#1, Q1):** while a batch runs (from "Démarrer" until its summary), every route that opens a document or a folder shows the AC6 message, and nothing else happens: File › "Ouvrir un document..." and Ctrl+O; File › "Ouvrir un dossier..." and Ctrl+Shift+O; File › "Fichiers récents"; and on the home screen, the "Traitement par lot" button, the drop zone (a file, a folder or several files) and the recent list. A second worker never runs beside the first.
2. **AC2 — The way back (Q1):** the message's button, « Revenir au lot », opens the running batch where it waits: the review of the document it waits on, or its progress screen. No route resets the batch screen or drops its worker while a batch runs; the batch comes back as it was. « Annuler le lot » stays the way to stop a batch, with its confirmation window, as today.
3. **AC3 — Every hand-off tied to its run (#1):** each batch run has its own identifier, carried by every signal of its worker, every kept review and every submission. This holds even if a second run starts by a route AC1 missed.
4. **AC4 — Finalization gets copies (#4):** the entities and the custom pseudonyms a finalization receives, in single-document validation and in batch, are copies made when the user confirms; nothing done in the review afterwards changes them.

### AC precisions (story-level)

- **AC1, "while a batch runs".** From the moment "Démarrer" creates the worker until the run's own `finished` (its summary) or `error`: `BatchScreen.is_running`, i.e. the batch screen holds a worker (`batch.py:59`, set at `:676`, dropped at `:778` and `:819`). It covers a batch with or without validation per document, a paused batch, and a batch whose « Annuler le lot » was confirmed but whose worker has not ended yet.
- **AC1, the routes and where each is refused** (Fix Design AC1; Consumer Trace R1 to R9):
  - File › "Ouvrir un document..." and Ctrl+O (`MainWindow._on_open_file`), File › "Ouvrir un dossier..." and Ctrl+Shift+O (`_on_open_folder`), File › "Fichiers récents" (`_open_recent`): refused **before** the file chooser opens and before the recent-files list is touched.
  - Home screen: the batch card's button "Ouvrir un dossier" (`_batch_btn`), the drop zone's file, folder and several-files drops, the drop zone's click (its own file chooser, then the refusal when a file is chosen; `drop_zone.py` does not change), and the recent list: refused in `HomeScreen` before `add_recent_file`, before any toast and before any navigation. A several-files drop shows the message once and no "Un seul fichier à la fois" toast.
  - "Nothing else happens": no file chooser (except the drop zone's own), no `ProcessingScreen.start_processing`, no new `BatchWorker`, no navigation, no change to `recent_files`, no toast; the batch screen keeps its phase, files and worker; the screen shown stays the same.
  - "A second worker never runs beside the first": `BatchWorker` is constructed once per run (T1, T11).
- **AC1 and AC2, the window.** `ConfirmDialog.informational(title, message, dismiss_label=…, parent=main window)`: one button, « Revenir au lot » / "Back to the batch" (`confirm_dialog.py:116-136`; no "OK", UX spec 5.7). Its button opens the running batch (AC2); Escape or closing the window only closes it, and nothing else happens (UX spec 5.7: "Escape key: always dismisses"). [Source: architecture/gui-ux-specification.md#5.7 ConfirmDialog]
- **AC2, "where it waits".** If a document waits (`awaiting_doc_index` is set and its context is kept), the validation screen with that document's kept review, re-attached as it was left (10.10's `set_context` path, no rebuild, no known-entity pass): the same `GUIValidationState` object, its decisions and its undo history. Otherwise the batch screen as it is (`navigate_to("batch")` with no context, so its phase does not change). From an earlier document (after "◀ Précédent"), « Revenir au lot » goes to the waiting one.
- **AC2, the home screen's batch button.** It is an AC1 route, so it shows the message; its « Revenir au lot » opens the running batch as it is, with no reset (T2[review_from_home]). It resets the batch screen as today only when no batch runs (T10).
- **AC2, "No route resets the batch screen or drops its worker".** Behind the routes, `BatchScreen.set_context` returns at once while a batch runs (no reset, no folder, no phase change), and logs `batch_context_ignored_while_running` with the run id only. "Démarrer" (`_start_batch`) reached while a batch runs shows the message and starts nothing (T11).
- **AC3, the identifier.** An `int` per batch screen, incremented by each `_launch_worker` (the first run is 1). The worker gets it (`BatchWorker(…, run_id=…)`, keyword with default 0, read-only property `run_id`). "Carried by every signal of its worker": each of the worker's four signals (`progress`, `finished`, `error`, `validation_required`) is connected with the run id bound (`functools.partial(handler, run_id=…)`), and each handler takes `run_id: int | None = None`; `None` is a direct call (existing tests) and counts as the current run. The SM measured that PySide6 6.7.3 runs such slots on the GUI thread when the signal is emitted from a pool thread (Reproduction Evidence, item 6).
  - **Ignored:** a handler given another run's id returns before any change and logs `batch_stale_signal_ignored` with the signal's name and the two ids (no name, no text, no path).
  - **Kept review:** the validation context carries `run_id`; `review_state(doc_index, run_id=None)` and `store_review_state(doc_index, state, run_id=None)` key the kept reviews by (run, document); `ValidationScreen` keeps the context's run id and `_is_awaiting_document` also requires it to be the current run.
  - **Submission:** `ValidationScreen.validation_complete` carries the run id as a fourth argument (`Signal(int, object, object, object)`); `_on_validation_complete` refuses a list of another run (logged as `batch_validation_result_refused` with the ids only) and submits only to a worker whose `run_id` is the current run's.
  - **A route AC1 missed:** `_launch_worker` with a live worker first stops it with `cancel()` (what « Annuler le lot » does; its written files are removed), retires its id and logs `batch_previous_run_cancelled`; its later signals are ignored. It never waits for the old thread (no GUI block). No user route reaches this after AC1 (Notes for the PO and PM, item 1).
  - **Codex #10 (backlog) is not made worse:** the worker's wait and wake-up code (`batch_worker.py:152-179`, `:369-378`) does not change.
- **AC4, the copies.** "Copies made when the user confirms": in batch, in `_on_finalize`'s batch branch after its guards (after Story 10.13's warning, once rebased: the list its count read), `copy.deepcopy` of the list and of the custom pseudonyms, emitted; in single-document validation, in `_start_finalization` (called after "Confirmer"), `copy.deepcopy` of `expand_validated_entities()` and of `get_custom_pseudonyms()`, handed to `FinalizationWorker`. Where the single-document copy is made (the screen, or the worker's constructor, which runs on the GUI thread at that moment) is the dev's choice; the tests check identity and the written file. `validation_state.py`, `finalization_worker.py` and `batch_worker.py`'s hand-off code do not need to change for AC4.

**Preconditions fail with `pytest.fail`.** A helper `pre(condition, message)` calls `pytest.fail(f"PRE: {message}")` when the condition is false; no precondition is an `assert`. `pytest.fail` raises `Failed`, not `AssertionError`, so a strict `xfail(raises=AssertionError)` reports a failed precondition as a failure and never as the expected one.

**Harness** (both files; `tests/unit/gui/` gives the `main_window` fixture of `conftest.py:29` and the autouse `_isolate_gui_config`):

### Project Structure Notes

The refusal lives on the batch screen, which owns the batch run (`gui/screens/batch.py`), and the main window only asks it (`gui/main_window.py`), so the routes of the menu and of the home screen share one rule and one set of texts. The run id stays inside the GUI layer (`gui/screens/`, `gui/workers/`); no core module changes. The tests follow the existing layout: desktop tests in `tests/unit/gui/` (autouse settings isolation; both leakage guards scan them). No new module and no new dependency. No conflict found with the project structure.

### Technical Constraints

- Python 3.10 to 3.12 (CI legs), PySide6 6.7 (`QT_QPA_PLATFORM=offscreen` in tests); `functools.partial` slots run on the GUI thread (Reproduction Evidence, item 6). [Source: architecture/3-tech-stack.md; architecture/gui-framework-decision.md#6.3 Threading Model]
- `from __future__ import annotations` and full type hints (mypy clean). [Source: architecture/19-coding-standards.md]
- No entity text in any log: the new log lines carry run ids and document indexes only. [Source: architecture/19-coding-standards.md#19.1 Critical Rules, rule 3]
- Translatable desktop text only through `self.tr(…)`, no f-strings inside `tr()`, no `\u` escapes. [Source: docs/stories/6.6.internationalization-and-french-ui.story.md; architecture/gui-framework-decision.md#9.2 GUI i18n Workflow]
- The confirmation windows follow the `ConfirmDialog` rules: a specific button label, never "OK"; Escape always dismisses. [Source: architecture/gui-ux-specification.md#5.7 ConfirmDialog]
