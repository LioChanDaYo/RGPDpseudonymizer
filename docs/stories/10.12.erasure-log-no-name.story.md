## Story

**Added by Lionel, 2026-10-16 (release blocker B1 for v2.3.0):** "Fix before release (Rec.)". The question he answered: "B1. When you delete a name from the mapping database with delete-mapping, the database's operation log still records that name. So a deletion request for a person leaves their name in the file. This has been the case in earlier versions too. Fix it before releasing 2.3.0?" The option he chose: "The log keeps a record that a deletion happened (date, row id, type), but not the name. ### Context

Copied word for word from the epic at `1f35dae`:

At `main` `fb7917c`. The PO checked every fact below on 2026-10-16 and measured the marked ones with probes on invented names (PO review notes for 10.12 and 10.13).

- **What is written:** `delete-mapping` writes one ERASURE entry per deleted row into the `operations` table (`gdpr_pseudonymizer/cli/commands/delete_mapping.py:169-192`). Its `user_modifications` holds `deleted_entity_id`, `deleted_entity_name` (the erased text, `:180`), `deleted_entity_type` and `reason`; the entry also has the date, `theme_selected` and `entity_count`. The deleted rows come back decrypted (`data/repositories/mapping_repository.py`, `delete_entities_by_full_name`), so the name is stored as plain text.
- **Not encrypted (measured):** `user_modifications` is a JSON column (`data/models.py`, `Operation`), written as is by `AuditRepository.log_operation` (`data/repositories/audit_repository.py:52-77`). The module says the operations table holds no sensitive data and needs no encryption (`:6`, `:26-27`). Only the entity name and pseudonym columns are encrypted (`mapping_repository.py:551-556`); the operations, the metadata, the types and the themes are plain. After `delete-mapping` by name and by `--id`, both erased names could be read with plain `sqlite3`, without the passphrase. A name with an accent is stored escaped (`"Quentrelle Z\u00e9brandine"`), as `json.dumps` writes by default.
- **Copied out by `export` (measured):** `export` writes the audit log to JSON or CSV (`cli/commands/export.py:174-190`), `user_modifications` included (`audit_repository.py:286`, `:393-395`). The JSON file holds the name in UTF-8 (`ensure_ascii=False`, `:310`); the CSV file holds it escaped (`json.dumps`, `:394`). Only exports that include the ERASURE entries hold names: `--type` and the date filters can leave them out. `stats` shows only counts and the type of the last operation (`cli/commands/stats.py:104-173`); it shows no name.
- **Encrypted copies left by every deletion (measured):** after a deletion whose log entry holds no name, 7 encrypted copies of the person's name stay in the file: the full name 3 times (the table, `idx_entities_full_name`, the unique index), the first name twice, the last name twice. They sit in freed space inside pages still in use (`freelist_count` 0). The encryption is deterministic (AES-256-SIV, `data/encryption.py:1-10`): the same name always gives the same encrypted text, so anyone with the passphrase and a raw-byte reader can find them; the app never shows them. With `PRAGMA secure_delete=ON` on the deleting connection, 0 copies stay.
- **The desktop app:** its database screen erases rows with the same function as `--id` (`gui/workers/database_worker.py:281`; `delete_mapping.py:158`), so its deletions leave the same encrypted copies. It writes one ERASURE entry with a count, and no name, row id or type (`:296-307`).
- **Cleaning old entries (measured):** removing the names in one `BEGIN IMMEDIATE` transaction, then `VACUUM`, then `PRAGMA wal_checkpoint(TRUNCATE)`, leaves 0 copies of any form and a 0-byte `-wal`. `VACUUM` fails inside a transaction ("cannot VACUUM from within a transaction"), so it runs after the COMMIT. After `VACUUM` alone, the main file still holds the names until the checkpoint. A reader in another process makes the checkpoint report busy (`(1, 16, 0)`), and the names stay in the main file until that reader closes. The removal without `VACUUM` leaves the 7 encrypted copies of each erased person. On a 14.9 MB file (20,000 entity rows, 2,000 old entries): removal 0.009 s, `VACUUM` 0.101 s, checkpoint 0.002 s; the `-wal` grew to 14.8 MB during `VACUUM`.
- **The 10.7 pattern:** `_ensure_current_schema` (`data/database.py:551-610`) runs on its own `sqlite3` connection in autocommit mode, takes `BEGIN IMMEDIATE`, checks the file again inside the transaction, and is all or nothing. 2. **AC2 — Deleted data overwritten (Q2):** from 2.3.0, every connection the app opens to the mapping database has `PRAGMA secure_delete=ON`, so a deletion writes zeros over the deleted row and its index entries. 3. **AC3 — Names already in the log (Q1):** on the first open by 2.3.0 of a file that has not been cleaned (whatever its schema version), after the passphrase check and the 10.7 conversion, the name is removed from every ERASURE entry; the date, row id, type, reason and every other field of the entry stay as they were. Then the file is compacted once.
   - **Removal:** the 10.7 pattern: its own connection, autocommit, `BEGIN IMMEDIATE`, a check again inside the transaction, all or nothing. A second process that waited finds the work done and changes nothing. Only entries whose JSON is valid are edited (a `json_valid` guard): `json_remove` raises on malformed JSON, which would block that file's opens for good; an entry skipped this way is counted in the log, without its content. SQLAlchemy always writes valid JSON, so the guard should never fire.
   - **A failed removal stops the open** and leaves the log unchanged (the 10.7 conversion of the same open has already committed), as a failed 10.7 conversion stops it; otherwise `export` could copy the old names out right after the failed open. It raises the 10.7 error class with its own text, not the conversion text, which would be false here. That text is new user copy, approved with the AC4 texts. This is the PM's reading of the 10.7 precedent, checked by the PO: for files of released versions it adds no file that cannot be opened, since the same open converts them and a file 2.3.0 cannot write to is already stopped by the conversion. It does not hold for files converted by unreleased `main` builds since 10.7 (schema 1.1.0, not yet cleaned), such as developers' databases; that case is negligible.
   - **Compaction:** after the COMMIT, `VACUUM`, then `PRAGMA wal_checkpoint(TRUNCATE)`. It runs once per file, even when no name was found, because that also clears the encrypted copies left by earlier deletions (desktop deletions included).
   - **Retry:** a metadata row, written in the removal transaction, records that the compaction is due. It is cleared only after a checkpoint that reports no busy page. A compaction that fails, or a checkpoint held up by another reader, is retried at the next open; it never stops the open.

### AC precisions (story-level)

- **AC1, "the erased name in no field of the entry":** the entry's `user_modifications` holds exactly `deleted_entity_id`, `deleted_entity_type` and `reason` (T1); the name is in no value. "The date" is the row's `timestamp` column, as today. "The same holds for the entry as `export` writes it": no UTF-8 and no `\u`-escaped form of the name in the JSON or CSV file (T2). The deletion, the confirmation and the success lines stay as they are, the name printed to the terminal included (a precondition of T1).
- **AC2, "every connection the app opens":** the app reaches the mapping database through `init_database` (`data/database.py:218`), `open_database` (`:338`) and the 10.7 conversion's own connection (`:571`); every command and every desktop worker goes through them (Dev Notes "Code Map"). The fix sets `secure_delete` in one place per kind: an engine `connect` listener for the two SQLAlchemy engines, and a shared helper for the module's own `sqlite3` connections (the conversion, the removal and the compaction). T3 (by name, by `--id`) and T4 (the desktop worker) read the raw bytes.
- **AC3, "a file that has not been cleaned (whatever its schema version)":** recognised by SQLite's `user_version`, which no version of the app ever set (0 in every file written before 2.3.0; the SM checked the code and the fixtures). The removal sets it to 1 in its transaction; `init_database` sets it to 1 on a new file, so a file created by 2.3.0 needs neither step. It is not `schema_version` and no schema change (Fix Design, AC3; Notes for the PO and PM). Tested on a file written by the real v2.2.0 code (schema 1.0.0, converted by 10.7 then cleaned in the same open) and on one written by the `1f35dae` code (schema 1.1.0, cleaned only).
- **AC3, "every other field of the entry stay as they were":** the parsed JSON minus the name equals the parsed JSON before; every other column of the row is byte-equal (T5). SQLite's `json_remove` writes the JSON without spaces after `,` and `:` and keeps `\u` escapes as stored (measured, SQLite 3.45.1).
- **AC3, "Compaction ... It runs once per file, even when no name was found":** T6 removes the names with plain SQL first, so the open finds none, and still requires the deleted rows' ciphertexts gone.
- **AC3, "Retry":** the metadata row `erasure_log_compaction_due` (value "1"), written in the removal transaction, is deleted only after `PRAGMA wal_checkpoint(TRUNCATE)` returns busy 0 with every WAL frame checkpointed. T8 holds a reader open during the open (the row stays), closes it, opens again (the row is gone and the file holds no copy).
- **AC3, "A failed removal stops the open" (with PO F1):** it stops only when the log holds a name: when no ERASURE entry holds one, a failed write is logged (`erasure_log_mark_deferred`) and the open goes on; the file stays unmarked and the next open tries again. Nothing can leak from such a file, which is AC3's reason for stopping, and it makes Lionel's Q-D true ("only at the first open by 2.3.0 of a database whose audit log still holds names"). T12 opens a read-only uncleaned file with no name. T9 makes the removal fail with a test trigger that aborts any update of `operations` (a deterministic write failure; no permission change, so it runs the same on every OS): the open raises `DatabaseConversionError` with the new text, the log is unchanged, the v2.2.0 file's 10.7 conversion has committed, and once the trigger is dropped the next open cleans.
- **AC3, the `json_valid` guard:** T10 adds an ERASURE entry with malformed JSON: the open succeeds, the valid entries are cleaned, the malformed one is left as it is, and the log event `erasure_log_cleaned` carries `skipped=1` and no entity text.

Why not a metadata row: a new file's metadata keys (Story 10.5, `tests/unit/test_database.py:31-36`, `:58`) and a converted file's metadata (Story 10.7, `tests/unit/test_database_conversion.py:140`) are asserted by existing tests that AC5 does not let this story change. AC3's metadata row is kept for what it describes, the compaction still due, and it is deleted once the compaction completes, so a converted, cleaned and compacted file has the metadata rows it had before. `user_version` is a header field: not the schema, not `schema_version`.
  - **The removal uses SQLite's JSON functions** (`json_valid`, `json_type`, `json_remove`), as AC3 states, inside the transaction. A `CASE WHEN json_valid(…) THEN json_type(…) END` keeps `json_type` away from malformed JSON, because SQLite does not promise the order in which `AND` terms are evaluated and `json_type` raises on malformed JSON.
  - **The checkpoint never waits for a reader.** `PRAGMA busy_timeout = 0` just before `PRAGMA wal_checkpoint(TRUNCATE)`: with a busy timeout, a TRUNCATE checkpoint waits for every reader, so a desktop app left open would hold every other open for the whole timeout. The compaction's own connection waits at most 1 s for another writer (`COMPACTION_BUSY_TIMEOUT_SECONDS`); the removal waits 30 s, as the 10.7 conversion does.
  - **The compaction is a second step on its own connection, after the removal's COMMIT,** so a failure of either is told apart: the removal stops the open (AC3), the compaction never does.
  - **The error class is `DatabaseConversionError` itself**, with its own message (AC3), so every place that handles the 10.7 error today handles this one the same way; no new handler. In `batch` it shows under the existing title "Database Conversion Failed" with the existing hint (`cli/commands/batch.py:740-747`); Q-D says so.
  - **The likely-cause phrases are shared:** `_conversion_failed_message`'s cause selection moves into `_likely_cause(error)`, used by both messages; the 10.7 message stays the same, byte for byte.

### Fix Design

**The SM's prototype and sketch are Claude-written measurement scaffolding (PO F2): never committed, never applied in the worktree, never pasted or handed to Forge as code; Forge works from this section's text.** The SM prototype implements AC1 to AC3 and the help change (`r1012\sm\proto_1012.diff` on a fresh `git archive 1f35dae`: `data/database.py`, `delete_mapping.py`, `cli/main.py`, `cli.po` and `cli.mo`, 227 lines added and 17 removed in v1.1; Reproduction Evidence). The dev writes the real code, through Forge.

**AC1 — the entry (`cli/commands/delete_mapping.py`).**
1. Remove `"deleted_entity_name": deleted.full_name,` (`:180`); the entry keeps `deleted_entity_id`, `deleted_entity_type` and `reason`. A one-line comment says why (the operations table is not encrypted).
2. Not changed: the confirmation, the deletion, the success lines, `entity_deleted`, the exit codes.

**AC2 — `secure_delete` (`data/database.py`).** Where the connections are created: the SQLAlchemy engines of `init_database` (`:218`) and `open_database` (`:338`), and the module's own `sqlite3` connections (the 10.7 conversion `:571`, and the two new steps).
1. `_secure_delete_on_connect(dbapi_connection, connection_record)` runs `PRAGMA secure_delete=ON` on a cursor; `_create_engine(db_path)` = `create_engine(f"sqlite:///{db_path}")` plus `event.listen(engine, "connect", _secure_delete_on_connect)`. `init_database` and `open_database` use it. A `connect` listener runs once for every new DBAPI connection of the pool, so every connection of every session has it (a `PRAGMA` on one checked-out connection, as `foreign_keys` is set at `:341-343`, would reach one pooled connection only).
2. `_connect(db_path, timeout)` = `sqlite3.connect(db_path, timeout=timeout, isolation_level=None)` plus `PRAGMA secure_delete=ON` (closed if the pragma fails). `_ensure_current_schema` uses it (`:571-573`), and so do the two new steps.
3. The CLI and the desktop deletion need no change: both go through `open_database`. The desktop's ERASURE entry stays as it is.

**AC3 — the cleaning (`data/database.py`).**
1. **Constants:** `ERASURE_LOG_CLEANED_USER_VERSION = 1`; `ERASED_NAME_FIELD = "deleted_entity_name"`; `COMPACTION_DUE_KEY = "erasure_log_compaction_due"`; `COMPACTION_BUSY_TIMEOUT_SECONDS = 1.0`. A comment states the design (Decisions Recorded, SM).
2. **`init_database`:** in the block that sets WAL and foreign keys (`:224-229`), `PRAGMA user_version=1`: a new file is born cleaned and is never compacted.
3. **`open_database`:** right after `_ensure_current_schema(db_path)` (`:399`): `_clean_erasure_log(db_path)` then `_compact_if_due(db_path)`. A `DatabaseConversionError` from the first goes through the existing `except` (`:404-408`): session closed, engine disposed, re-raised. Docstring: the open now also cleans, once.
4. **`_clean_erasure_log(db_path) -> bool`**, the 10.7 pattern: `_connect(db_path, CONVERSION_BUSY_TIMEOUT_SECONDS)`; if `PRAGMA user_version` ≥ 1, return False (nothing to do; no write); else count the ERASURE entries that hold a name (`named`: the `CASE WHEN json_valid … json_type … IS NOT NULL` condition below; a read), then `_begin_immediate(conn)`; inside, the check again (another process cleaned it: `ROLLBACK`, return False), `named` counted again; count the ERASURE entries whose `user_modifications` is not NULL and not `json_valid` (skipped); `UPDATE operations SET user_modifications = json_remove(user_modifications, '$.deleted_entity_name') WHERE operation_type = 'ERASURE' AND CASE WHEN json_valid(user_modifications) THEN json_type(user_modifications, '$.deleted_entity_name') END IS NOT NULL` (removed = its row count); `INSERT OR REPLACE INTO metadata ("key", value, updated_at) VALUES ('erasure_log_compaction_due', '1', <now, as _write_schema_version writes it>)`; `PRAGMA user_version = 1`; `COMMIT`. Any error: `ROLLBACK` (a rollback error is logged, never raised); then **if `named` is 0 (PO F1)**, log `erasure_log_mark_deferred` with the error type and return False: the open goes on, the file stays unmarked (`user_version` 0) and the next open tries again; **otherwise** (names in the log, or the count itself failed: `named` starts at -1) log `erasure_log_cleaning_failed` with the error type and raise `DatabaseConversionError(_erasure_log_failed_message(exc))` from it; the log is unchanged. Success: log `erasure_log_cleaned` with `removed`, `skipped` and the duration (counts only); return True. The connection is closed in `finally`.
5. **`_compact_if_due(db_path) -> bool`:** `_connect(db_path, COMPACTION_BUSY_TIMEOUT_SECONDS)` (a failure is logged, return False); if the due row is absent, return False; `VACUUM` (autocommit, outside any transaction: inside one it fails, measured by the PO); `PRAGMA busy_timeout = 0`; `PRAGMA wal_checkpoint(TRUNCATE)` → `(busy, log, checkpointed)`; if `busy` or `log != checkpointed`, log `erasure_log_compaction_pending` (reason `checkpoint_busy`) and return False; else restore the busy timeout, `DELETE FROM metadata WHERE "key" = 'erasure_log_compaction_due'`, one more `PRAGMA wal_checkpoint(TRUNCATE)` (result ignored), log `erasure_log_compacted` with the duration, return True. Any exception is logged as `erasure_log_compaction_failed` with its type and returns False: it never stops the open. In a file not in WAL mode the checkpoint returns `(0, -1, -1)`, which counts as complete.
6. **The messages:** `_likely_cause(error)` holds `_conversion_failed_message`'s cause selection (`:532-543`) unchanged; `_conversion_failed_message` uses it and returns the same text, byte for byte; `_erasure_log_failed_message(error)` returns the approved Q-D text ("Approved Texts", text 9) with `%1` = `_likely_cause(error)` and `%2` = `f"{type(error).__name__}: {error}"`. Neither holds entity text.
7. **Docstrings and notes:** `DatabaseConversionError` (`exceptions.py:100-107`) also covers a failed removal; `audit_repository.py:6` and `:26-27` say that ERASURE entries hold no name since Story 10.12, that the operations table is not encrypted, and that free text (`--reason`) and file names are stored as given. Comments only.
8. **Several processes:** the removal waits for another process's write lock (30 s) and re-checks inside its transaction; two processes may both compact, which is harmless. Story 10.7's two-process test (`test_database_conversion_concurrency.py`) now runs the removal and the compaction in both processes and must stay green (measured).

  - Every deletion, in the command line and in the desktop app, now overwrites the deleted data with zeros.
  - Not changed: files already written by `export` or by a mapping export (`list-mappings --export`, the desktop app's CSV export), copies of a database that this version never opens, and text typed in `--reason`. The `--reason` help now asks for a request reference, never the person's name.

### Technical Constraints

- All public functions have type hints, and imports are absolute. `mypy` is strict (`mypy.ini`). [Source: architecture/19-coding-standards.md#19.1]
- Quality commands: `black --check`, `ruff check`, `mypy gdpr_pseudonymizer/`, `pytest`. [Source: architecture/19-coding-standards.md#19.0]
- **Never log sensitive data:** the new log events carry counts, durations and error types only; the error text carries no name. [Source: architecture/19-coding-standards.md#19.1, rule 3]
- The database stays SQLite in WAL mode with AES-256-SIV column encryption; the cleaning decrypts nothing and copies values as stored. [Source: architecture/9-database-schema.md#9.1, #9.3, #9.5]
- The Compatibility Requirements line for 10.12, word for word from the epic:

- [ ] Database after 10.12 (Lionel, 2026-10-16, Q1 and Q2): no schema change and no version bump. On the first open by 2.3.0, after the 10.7 conversion, the names are removed from the ERASURE entries written by earlier versions and the file is compacted once (`VACUUM`, then a TRUNCATE checkpoint); a metadata row records a compaction still due, retried at the next open. Every connection deletes with `secure_delete`. New ERASURE entries hold no name

- Cost: an already cleaned file costs two connections and two reads more per open (one for each step; PO F5); an old file is cleaned and compacted once (Reproduction Evidence, item 5).
