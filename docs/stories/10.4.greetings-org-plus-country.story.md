### AC precisions (story-level)

- **"Salutation line" and "salutation context" (AC1, AC2, AC3; the definition AC2 asks the story to write down):**
  - A **salutation line** is one line of the document (between two line breaks, as `_LINE_BREAK_RE` defines them, `hybrid_detector.py:82`) that has one of these shapes, after optional leading horizontal whitespace:
    1. `<names>,` : one or two known first names and nothing else on the line, ending with a comma ("Marie,", "Laurent, Marie,"). The whole line, with leading and trailing horizontal whitespace removed, is at most `max_line_length` characters (a value in the new resource, Dev Notes "Salutation Resource").
    2. `<opener> <names>` **at the start of the line**, followed by `,` `.` `!` or the end of the line: an opener from the resource, then one or two known first names ("Bonjour Marie,", "Merci Laurent.", "Bonne initiative Laurent."). Only this leading part is matched; the rest of the line does not matter, and no length limit applies to shape 2.
  - **Why the limit is on shape 1 only (PO validation S1, 2026-10-09):** the `email_chain` line that holds "Bonne initiative Laurent." is 100 characters long, because the message goes on after the name. A whole-line limit would never reach the annotated PERSON there (@2252), which AC2 gives as its own example. Shape 2 is held in place by its start (an opener at the line start) and by its end (punctuation or the line end right after the names).
  - A **known first name** is a single token that starts with a capital letter in the text, hyphenated allowed, for which `HybridDetector._known_first_name` is true (`hybrid_detector.py:1059-1061`: `NameDictionary.is_first_name`, `name_dictionary.py:81-91`, on the first-name list of `french_names.json`: 505 entries, 451 distinct names). The capital letter is part of the test because `is_first_name` is case-insensitive (`:91`): without it, the common noun "pierre" would count. Every rule of this story uses this one test.
  - A **salutation context** is a salutation line. The address and signature shapes of Dev Notes "Candidate Rules" (R-SAL-ADDR, R-SIG) are information rows only: spaCy already covers the two annotations they target (PO validation S3).
  - **The call AC2 asks for, written down here:** compliment and thanks phrases that address a person by first name ("Bonne initiative Laurent.", "Merci Laurent.") **are in scope**. They are openers of kind `compliment` or `thanks` in the resource. Reason: GUIDELINES Q1 (approved by Lionel, 2026-10-02) annotates every bare first name "used to address or sign" as PERSON, and names "Bonne initiative Laurent." as such a case. This is a story call, reported at STOP R as information, not a question.
  - "Maximum line length" (shape 1 only) is a technical parameter. The dry-run reports the reach at 40, 60 and 80 characters (Task 1.4), and the dev picks the value as information.
- **AC1:**
  - "Split" means: the PERSON span "X, Y" is replaced by PERSON "X" and PERSON "Y" (document slices, same source and confidence, not flagged ambiguous). The comma and the space between them are no longer covered; they are not name characters (Coverage Invariant, level 1).
  - **Interaction with `last_first_names`** (`detection_patterns.yaml:41`, `require_known_first_name: true` at `:47`, pattern `:49`): the pattern checks only the part after the comma (`RegexMatcher._has_known_first_name`, `regex_matcher.py:215-236`, last group, split on "-"). "Laurent, Marie" passes because "Marie" is known; the first part is not checked. The YAML pattern is **not** changed by this story. AC1 adds the test on X, and only on a salutation line. The documented cases, each a unit test (Dev Notes "Testing"):
    - salutation line, X and Y both known first names → two PERSONs;
    - salutation line, X not a known first name ("Dubois, Jean-Marc,"-shaped) → one PERSON, unchanged (GUIDELINES Q2 keeps a real "Last, First" whole);
    - the same "X, Y" in running text, not a salutation line → one PERSON, unchanged ("today's behaviour");
    - Y not a known first name → no `last_first_names` match today, and none after.
  - A spaCy PERSON "X, Y" on a salutation line is split by the same rule: the rule looks at the span, not at the source.

**Shared definitions.**
- **Line:** the text between two line breaks of `_LINE_BREAK_RE` (`hybrid_detector.py:82`); "horizontal whitespace" is the `HSPACE` class (`regex_matcher.py:27`: space, tab, U+00A0, U+202F).
- **Name token:** `[A-ZÀ-ÖØ-ÞĀ-ſ][A-ZÀ-ÖØ-ÞĀ-ſa-zß-öø-ÿĀ-ſ]*(?:-[A-ZÀ-ÖØ-ÞĀ-ſ][A-ZÀ-ÖØ-ÞĀ-ſa-zß-öø-ÿĀ-ſ]*)*`. **Known first name:** a name token for which `HybridDetector._known_first_name` is true (the whole token; `french_names.json` holds no hyphenated entry, so a hyphenated token is never one today).
- **Salutation line** (AC precisions): shape 1 = the line, with leading and trailing horizontal whitespace removed, is `N(?:HSPACE*,HSPACE*N)?HSPACE*,` with every N a known first name, and is at most `max_line_length` (40) characters long; shape 2 = after optional leading horizontal whitespace, an opener of `salutations.yaml` (case as written; a two-word opener matches with one or more horizontal whitespace between its words), one or more horizontal whitespace, then either two known first names `N HSPACE*,HSPACE* N` or one `N`, directly followed by `,`, `.`, `!` or the end of the line (horizontal whitespace allowed before the end); the two-name form is tried first. Shape 1 is tried before shape 2. The names "end with a comma" when the character right after the last name is `,` (shape 2) or always (shape 1).

### Dry-Run Protocol (lessons from 10.2 to 10.3c)

- **Reproduce first.** No dry-run number is trusted until the baseline dump reproduces run P exactly (1.1) and the local per-document JSON gives an all-zero paired delta against `37975010715` (1.2).
- **Patch in the script, run the real pipeline.** Every rule is patched in the script (monkeypatched method or subclass), never in product code, and every document goes through `detect_entities`, so the 10.3b steps (both `_fix_person_boundaries` calls, the guarded re-merge), the 10.3c exact match, R-SPLIT late, W-JOIN and R-ROLE-LATE all see it. A rule that needs the spaCy parse reads `last_doc` in the script the way the product would.
- **Net, not gross.** `match_entities` (`tests/accuracy/conftest.py:108-149`) is exact text + type, one-to-one, with position only as a tiebreaker. Re-score the **whole** post-rule dump and report the per-type net delta. STOP R and STOP G3 use the net delta.
- **Classify every lost TP:** **position loss** (no detection now matches that annotation at its position), **taken over** (another detection now matches it), **cross-position scorer artefact** (the lost TP was matching a same-text annotation elsewhere). Gained TPs are classified the same way (real fix or artefact). Q8 makes first names and short company forms annotations at every occurrence, so a new "Marie" or "BRS" can match an annotation elsewhere: check the position.
- **Coverage table** for every rule and composition (levels 1, 2 and 2b, Coverage Invariant), with "Pierre" and "BRS" named.
- **Fires on non-targets.** Report every firing of a rule on a shape it was not meant for, even when the net delta is zero (10.3a's first W-JOIN fired on a label line; 10.3b caught two misfires this way). For Slice S, every fire outside a salutation context is a non-target fire (AC3).
- **Dumps include `is_ambiguous`.** Compare text, type, offsets, source and `is_ambiguous`.
- **Scripts:** start from `scripts/accuracy_type_aware_match_dryrun.py` (10.3c) and `scripts/accuracy_particles_noise_dryrun.py` (10.3b). ### Pseudonym Continuity (CHANGELOG upgrade note, AC7)

The schema is unchanged. The mapping key is the entity text with titles stripped (and prepositions, for places) and every whitespace run collapsed to one space (`DocumentProcessor._normalize_entity_text`, `core/document_processor.py:211`). The key has no entity type, and every lookup is type-blind (Story 10.7 will change that). [Source: prd/epic-10 "Risk Mitigation"] Describe, with invented examples only:

1. **Split greetings.** "Zorbalia, Quentrel," used to give one key, "Zorbalia, Quentrel". Now each name gets its own key ("Zorbalia", "Quentrel"): an existing pseudonym for either name is reused; the old two-name key is no longer used.
2. **New bare first names.** A first name that was left in clear on a greeting line is now offered. If the user confirms it, it gets the pseudonym already stored for that first name, or a new one.
3. **Organisation + place.** "Zorbtech" followed by "France" used to give the key "Zorbtech" (and "France" as a place). Now the organisation key is "Zorbtech France", a different key from "Zorbtech", so the branch gets its own pseudonym. The place "France" is still offered on its own; at that span the output applies one replacement, the organisation's, which covers the place (`_apply_replacements`).
4. **Acronyms** tied to an organisation in the same text get their own key (the acronym), not the organisation's pseudonym.
5. **Defined aliases (only if R-DEF is taken).** A nickname the text defines ('ci-après dénommée "ZORBTECH"') is now offered as an organisation at every occurrence. It gets its own key ("ZORBTECH"), so its own pseudonym, not the full name's: the nickname no longer appears in clear, but the output does not show that the two pseudonyms are the same company.
6. **A first name used alone after the full name** ("Zorbalia" after "Zorbalia Quentrel", R-FN-DOC) is now offered. It is looked up like any first name (key "Zorbalia"); the existing PERSON component match applies unchanged.
7. **Recommendation:** as in 10.2–10.3c, keep the same mapping database across versions, and re-process with the old version if byte-identical output is required.
