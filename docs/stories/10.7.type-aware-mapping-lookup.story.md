## Story

**Added by Lionel at the 10.3c STOP R, 2026-10-09.** Asked "the pseudonym database looks names up without their type. Plan a later story to make that lookup type-aware?", he answered "Add a follow-up story". The orchestrator had recommended keeping it out of Epic 10. It is not a detection-precision change: like 10.5, it is a data-layer story found along the way.

**As a** user who confirms the same text under two entity types (for example a person and a place),
**I want** each type to get its own pseudonym and its own mapping row, and a text already known under one type to reach validation when it shows up under another,
**so that** the type I choose during validation is the type that is stored and pseudonymized.

**Priority:** MEDIUM — no text is left in clear today in the CLI (the desktop app's same-span case is Story 10.8), but 10.3c keeps more different-type pairs, and for those the type choice can be lost.

### Context

The epic's Context, word for word, as of the PM's drift fix `279311e`. Its first bullets cite lines at `4f3cf30`; the bullet the PM added cites lines at `51d8429`. All of them hold at `51d8429`.

At `main` `4f3cf30`, mapping keys carry no entity type:

- `Entity.full_name` is unique on its own (`gdpr_pseudonymizer/data/models.py:38`). Each row stores an `entity_type` (`:31`), but no lookup uses it.
- `SQLiteMappingRepository.find_by_full_name` (`gdpr_pseudonymizer/data/repositories/mapping_repository.py:148`) queries by the encrypted text only.
- In `gdpr_pseudonymizer/core/document_processor.py`, `_normalize_entity_text` (`:211`) builds the key from the text alone (titles stripped, and prepositions for LOCATION). Three places then look it up without the type: the validation preview and its `preview_cache` (`:254`), the known/unknown split before validation (`:297-308`), and `_resolve_pseudonyms` with its per-run `entity_cache` (`:489`, lookup `:507`).
- Other callers look up by name alone too: `delete-mapping` (`gdpr_pseudonymizer/cli/commands/delete_mapping.py:118`, and its delete call at `:146`), `import-mappings` (`gdpr_pseudonymizer/cli/commands/import_mappings.py:164`), the GUI known-entity check (`gdpr_pseudonymizer/gui/models/validation_state.py:111`), the repository's race fallback (`mapping_repository.py:345`) and `delete_entity_by_full_name` (`:388`).
- `build_pseudonym_previews` (`core/document_processor.py:759-802`, key `:786`) fills the desktop app's preview map through the same validation preview (`:254`); its callers are `gui/workers/detection_worker.py:199` and `gui/screens/batch.py:896`. The desktop app also keys three per-run maps without the type: the preview map (read at `validation_state.py:86-88`), the variant map (`gui/workers/detection_worker.py:154-157`, read at `validation_state.py:313-331`) and the same-text group that accept and reject act on (`validation_state.py:89-93`, `:128`, `:144`). Story 10.8 keys these three on type (they were AC9 of the 10.7 SM draft).

Consequences once 10.3c keeps both detections of a different-type pair:

- If the user confirms both, they share one pseudonym and one database row.
- If the text is already in the database, both are auto-accepted as known and never shown, so the type choice never reaches the user.
- In the CLI, no text is left in clear: every confirmed occurrence is still replaced. In the desktop app, the text-only variant map can drop one type's occurrences from finalization, so one can stay in clear (10.7 SM probe; 0 positions on the main corpus). Story 10.8 fixes that before 10.7.

**What the SM found on re-reading at `51d8429` (2026-10-13)** (Dev Notes "Code Map" and "SM Probes"):

- **The desktop app's three text-only keys** (now in the epic's Context) are **Story 10.8**, by Lionel's decision of 2026-10-13. 10.8 merges first and does not depend on this story's AC3 decision. This story does not change those keys. The SM's evidence is kept in Dev Notes "SM Probes" for 10.8.
- **The one-row-per-name rule is part of the table definition** (`UNIQUE (full_name)`, read from a file made by `init_database` at `51d8429`). SQLite cannot drop it in place. A second row for the same text needs the `entities` table to be rebuilt, in old files and in the definition new files get.
- **`schema_version` is written and never read.** `init_database` writes "1.0.0" (`data/database.py:161`); `open_database` (`:199-297`) reads the salt, the iteration count and the canary only. Versions up to 2.2 open any file without checking its version.

The mechanism is the lock, inside `open_database`: a busy timeout (the dev sets it, at least 30 s, and records it), then `BEGIN IMMEDIATE`, then the version re-checked inside the transaction; a process that finds the file already converted ends the transaction and carries on. This covers every caller, including two separate commands started at once. In addition, `batch` opens the file once before its pool starts (after `ensure_database`, `batch.py:452`), so the conversion happens once, before any worker, and a failed conversion stops the run before it starts.

**Order first.** Story 10.8 merges before 10.7 (Lionel, 2026-10-13). It fixes the desktop app's text-only keys and does not depend on this question. The options below are about the mapping database only.

**What the question is about.** Today the mapping database holds one row per name, whatever its type. The first time a name is confirmed, its row is stored with that type. After that, the name gets the same pseudonym under every type, and a name already in the database is accepted without review, under any type. 10.7 gives each (name, type) its own row. The question: what to do with the databases made before 10.7, which hold one row per name.

**One example for every option.** An old database holds one row: "Zorbaville", type LOCATION, pseudonym P1. A new document contains "Zorbaville" as a company (ORG) and as a town (LOCATION).

| | Today | (a) Change the file once, automatically | (b) Leave old files as they are | (c) Change the file when the user asks |
|---|---|---|---|---|
| "Zorbaville" the town | P1, accepted without review | P1, accepted without review | P1, accepted without review | P1, accepted without review |
| "Zorbaville" the company | P1, accepted without review | shown for review; if confirmed, a new row with a new pseudonym P2 | P1, accepted without review (as today) | as (b) until the user asks, then as (a) |
| A new name, met first as a company, later as a town | one row, P3 for both | two rows, P3 and P4 | one row, P3 for both: an old file allows one row per name | as (b), then as (a) |
| A database made with `init` after 10.7 | (not applicable) | one row per type | one row per type | one row per type |

**(a) Change the file once, automatically. Recommended; the default.**
- When 10.7 first opens an old file, after the passphrase check, it rebuilds the table so that a name can have one row per type. Every existing row keeps its name, type, pseudonym and id. The stored values are copied as they are; nothing is decrypted.
- **Stable pseudonyms:** every stored row keeps its pseudonym, for the type it records. Where an old document used the name under another type, those occurrences shared the stored pseudonym. Processed again with 10.7, they reach review and, if confirmed, get a new pseudonym.
- **Older version opening the file afterwards:** it opens it (versions up to 2.2 do not check the file's version) and works by name only. With two rows for a name it uses one of them, and its `delete-mapping` removes one row without saying that another remains. The CHANGELOG warns: do not go back to an older version with a changed file.
- **Article 17:** `delete-mapping "Zorbaville"` lists both rows and removes both.
- **Backup and restore:** the change is one SQLite transaction. If it fails, the file stays as it was. The tool keeps no copy, because a kept copy would still hold names erased later. The CHANGELOG asks users to make their own copy before upgrading. A restored old copy is changed again the next time 10.7 opens it.
- **Cost:** the upper end of the estimate (1 week): the rebuild, its lock for processes opening the file at the same time, and their tests.
- **Possible add-on:** lock older versions out, so they refuse a changed file with "database may be corrupted". Not included unless Lionel asks.

**(b) Leave old files as they are (read-compatibility).**
- Old files keep today's behaviour exactly: one row per name, the stored pseudonym for every type, accepted without review. Only databases made with `init` after 10.7 get one row per type.
- **Stable pseudonyms:** nothing changes in an old file. It keeps one pseudonym per name even when the name appears under another type (note added in v1.2, PO S2).
- **Older version:** old files are unchanged. A file made by 10.7 has the same risk as in (a).
- **Article 17:** on an old file, `delete-mapping` works as today (one row per name). On a new file, it lists and removes every row of the name.
- **Backup and restore:** no change.
- **Cost:** two behaviours to keep and test for as long as old files exist. Users who keep one database across versions, as the upgrade notes of 10.2 to 10.4 advise, never get the fix unless they start a new database, and a new database gives new pseudonyms to everything.
- **Variant** ("old rows match any type, new rows are typed"): it still needs the file change of (a), because an old file allows one row per name, and the problem stays for every name already stored.

**(c) Change the file only when the user asks.**
- An old file behaves as in (b) until the user runs an upgrade: a new CLI command (for example `gdpr-pseudo upgrade-db`) or a prompt when the desktop app opens an old file. After that, as in (a).
- **Stable pseudonyms, older version, Article 17, backup and restore:** as in (b) before the upgrade, as in (a) after it. The user can make a copy right before upgrading.
- **Cost:** a new command, a new desktop-app dialog and their tests: the most work of the three. The epic's Compatibility Requirements keep the CLI and the GUI unchanged, so the PM would record the addition.

**Why (a).** Every database that exists today was made before 10.7, and the upgrade notes of 10.2 to 10.4 tell users to keep using the same one. With (b), none of them gets the fix unless the user starts a new database. (a) keeps every stored pseudonym, changes the file once in one step that either completes or leaves the file untouched, and leaves one behaviour to test. Its risk is going back to an older version afterwards, which the CHANGELOG warns against.

**Whatever the option** (AC3): no row is deleted or given a new pseudonym; the file opens with its passphrase; an old file is recognised by its `schema_version` and its table definition; a failure leaves the file as it was.

### Decided Continuity Rule (a) (STOP C, Lionel, 2026-10-13; with the PO's B1, S1, S6, S7 and N10)

**When.** Every open of a pre-10.7 file converts it: `open_database` does it, so every caller does it, the read-only commands included (`list-entities` `list_entities.py:107`, `list-mappings` `list_mappings.py:126`, `stats` `stats.py:82`, `export` `export.py:153`, `validate-mappings` `validate_mappings.py:110`, the source of `import-mappings` `import_mappings.py:134`, the passphrase check of `destroy-table` `destroy_table.py:85`), the desktop app's opens, and backup copies the user opens. It happens once per file: a converted file has the new `schema_version` and is not converted again.

**Order of the open.**
1. The file must exist (as today, `database.py:223-225`).
2. The passphrase is checked against the canary (`:270-283`). A wrong passphrase converts nothing.
3. The file is recognised as pre-10.7 when both hold: `schema_version` is "1.0.0", and `PRAGMA index_list('entities')` with `PRAGMA index_info` shows a unique index on `full_name` alone. Neither holds: a 10.7 file, nothing to do. Only one holds: the open stops with a clear error and changes nothing.
4. The conversion (below). Then the open goes on as today.

**How the file is converted.**
- On its own connection, in autocommit mode (`isolation_level=None` on the pysqlite connection, or SQLAlchemy's documented pysqlite recipe that emits `BEGIN` itself), with an explicit `BEGIN IMMEDIATE`. The driver's defaults are not enough: pysqlite opens no transaction before `CREATE TABLE` (PO probe B1).
- Inside that one transaction, after `BEGIN IMMEDIATE` takes the write lock, the version is checked again (step 3). If another process converted the file meanwhile, the transaction ends with nothing changed.
- Then: create the new `entities` table with the (text, type) unique key; copy every row by named columns (`INSERT INTO new (id, entity_type, first_name, …) SELECT id, entity_type, first_name, … FROM entities`), values as stored, nothing decrypted; drop the old table; rename the new one; recreate the indexes; write the new `schema_version`; `COMMIT`.
- The change happens inside the file: no copy of the file, no rename of the file (PO N10).
- The row count before and after is compared inside the transaction; a mismatch rolls back.

**Several processes.** A busy timeout (at least 30 s; the dev records the value) makes a second process wait for the lock instead of failing; it then sees the converted file in its re-check. `batch` also opens the file once before its pool starts (Task 6.3), so its workers (up to 8) start on a converted file. (Preview line Lionel saw: "Batch runs: first converts, others wait".)

**When the conversion cannot be made** (read-only file or folder, disk full, file locked longer than the busy timeout, any error inside the transaction):
- the transaction rolls back: the whole `sqlite_master` (tables, indexes) and every row are as before, and the file is never deleted;
- the open stops with its own error class (a subclass of `DatabaseError`, `exceptions.py:73`; name fixed in Task 2.2) and a clear message: the database could not be converted to the new format, the file is unchanged, and the likely cause (read-only, disk full, in use);
- nothing goes on with an unconverted file. (Preview line: "All or nothing; if it can't, open stops".)

**Callers that swallow open errors (PO S7).** Their behaviour on a failed conversion:
- desktop-app known-entity check (`validation_state.py:116-117`): every error is swallowed, so no entity is marked known and all of them reach review. Safe; the later finalization opens the file again and shows the conversion error. A test pins it.
- desktop-app previews (`gui/screens/batch.py:897-898`, `gui/workers/detection_worker.py:200-201`): previews are left empty, as for any error today; the later open shows the conversion error. No edit.
- `destroy-table` (`destroy_table._verify_passphrase`, `destroy_table.py:70-90`): it turns any exception into "wrong passphrase". It must show the conversion error instead (Task 6.4).

**Events.** One log event when a file is converted (row count, old and new `schema_version`, duration), and one when a conversion fails (error class); no entity text, no file content.

**What is not part of the rule:** no lock-out of 2.2 and older (not requested); no automatic copy of the file (a kept copy would still hold names erased later); no new command or dialog.

### Pseudonym Continuity (CHANGELOG upgrade note, AC6)

The decided rule is (a). Describe, with invented names only:

1. **Same name, two types.** "Zorbaville" the town and "Zorbaville" the company now get two pseudonyms and two rows. Before, they shared one.
2. **A name stored under one type and met under another** now reaches review. It used to be accepted without review, with the stored pseudonym.
3. **Existing databases are converted once.** The first time this version opens a database made by an earlier version, it converts the file in place to the new format. Any open does it: processing, the read-only commands (`list-entities`, `list-mappings`, `stats`, `export`, `validate-mappings`), the source database of `import-mappings`, the desktop app, and a backup copy you open. Every stored pseudonym is kept. The conversion is all or nothing: if it cannot be made (read-only file, disk full, file in use), the command stops with a message and the file is unchanged. Occurrences that older documents had under another type got the stored pseudonym; processed again, they reach review and, if confirmed, get their own pseudonym.
4. **Batch runs** have no review: a name found under two types gets one pseudonym per type. When several workers start on a database made by an earlier version, the conversion happens once, before they start.
5. **One position found with both types, both confirmed:** the output shows one pseudonym there, the first in the validated list (a type already known comes before a newly reviewed one), as before. Other positions get each type's own pseudonym.
6. **`delete-mapping "Name"`** removes every row with that name and lists them; `--id` removes one row and says what remains. Do not write that the erased name is gone from the file: the erasure audit entry keeps it (`delete_mapping.py:167`).
7. **Desktop app:** a name already stored is recognised as known by the same key and type as in the CLI, so a titled form ("Dr Zorbalia") is known when "Zorbalia" is stored (before, the raw text and any type). The fix for names found twice at one place with two types is Story 10.8's entry.
8. **Going back:** after the conversion, opening the database with version 2.2 or older is unsafe: that version reads by name only, and its `delete-mapping` removes one row of a name without saying another remains. Make a copy of the database file before upgrading if going back may be needed; such a copy also keeps names erased later.
9. **Recommendation,** as in 10.2–10.4: keep using the same database across versions.

### Technical Constraints

- Python `>=3.10,<3.14` (`pyproject.toml:30`); SQLAlchemy `>=2.0.0,<2.1.0` (`:37`).
- Absolute imports; type hints on public functions; the core uses the repository interface, not the SQLite class. [Source: architecture/19-coding-standards.md#19.1, rules 1 and 2]
- Quality commands: `black --check`, `ruff check`, `mypy gdpr_pseudonymizer/`, `pytest`. [Source: architecture/19-coding-standards.md#19.0]
- SQLite cannot drop a table constraint with `ALTER TABLE`. Changing `UNIQUE (full_name)` means rebuilding the table (create the new table, copy the rows by named columns, drop the old table, rename, recreate the indexes), inside the file, with no copy and no rename of the file.
- **The rebuild must be one explicit transaction (PO B1).** SQLite can roll back DDL, but Python's sqlite3 driver (pysqlite) under its default settings opens no transaction before `CREATE TABLE`, so each statement commits on its own: in the PO's probe, create new, copy, drop old, a forced error and a rollback left both `entities` and `entities_new` in the file. So the conversion runs on its own connection in autocommit mode (`isolation_level=None` on the pysqlite connection, or SQLAlchemy's documented pysqlite recipe that turns off the driver's own transaction handling and emits `BEGIN` itself), with an explicit `BEGIN IMMEDIATE`, and the new `schema_version` is written inside that same transaction before `COMMIT`.
- No public API, CLI flag or GUI screen changes; rule (a) adds no command and no dialog. [Source: prd/epic-10 "Compatibility Requirements"]
- Lookups stay single indexed queries; an index on (text, type) replaces or complements `idx_entities_full_name`.
