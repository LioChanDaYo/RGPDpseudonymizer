## Story

**As a** user running several CLI processes against a new mapping database (e.g. from a script),
**I want** a failed initialization never to delete a database that another process just created,
**so that** I do not lose the winner's mappings and passphrase setup to a race.

**Priority:** LOW — rare: it needs two processes initializing the same new DB at the same moment. Single CLI or GUI runs initialize once.
**Change type:** Data-layer only. No file under `gdpr_pseudonymizer/nlp/`, `gdpr_pseudonymizer/resources/`, `tests/accuracy/` or `tests/test_corpus/` changes.
**Ordering:** outside the detector chain. It changes no detection, so it has no accuracy baseline and may run before, between or after the detector stories. It does not move the epic close-out baseline.
**Epic:** [Epic 10: v2.3 — Detection Precision Quick Wins](../prd/epic-10-v2.3-detection-precision-quick-wins.md) (story 10.5)
**Branch:** `story/10.5-db-init-safety`, cut from `main` at `51d8429` (PR #95, Story 10.6 B15 close-out). The story commit is the branch's first commit.
**Baseline:** none. There is no accuracy baseline (epic "Ordering"), and no G1 run is required (AC5, AC8). The behavioural baseline is `init_database` as it is at `51d8429` (Dev Notes "Code Map") and the SM's reproduction of its failure modes (Dev Notes "Reproduction Evidence").

### Context

Copied word for word from the epic:

`init_database` (`gdpr_pseudonymizer/data/database.py:60`) checks that `db_path` does not exist, creates it, and on **any** exception deletes `db_path` (`database.py:180-184`, "Clean up partial database file on failure"). If two processes create the same new database at once, the loser's cleanup can delete the winner's freshly created file. PR #83 (open at the time of writing) makes index creation idempotent (`CREATE INDEX IF NOT EXISTS`). That only moves the loser's failure to the metadata key collision; the delete stays.

**State at `main` `51d8429` (SM re-read and probes, 2026-10-13; the details are in Dev Notes "Code Map" and "Reproduction Evidence"):**

- PR #83 merged as `5790970` (2026-10-06). It made the seven `CREATE INDEX` statements idempotent (`database.py:111-153`); the delete stays. The cleanup now sits at `database.py:192-196` (`except Exception` at `:192`, `unlink` at `:194-195`, the "Database initialization failed" wrap at `:196`).
- Most losers do not reach the metadata insert. With two processes started together, the loser fails first at `Base.metadata.create_all` (`:100`, "table entities already exists"), which #83 did not cover. Then its cleanup deletes the file.
- **Linux (and so macOS, same unlink semantics):** in the SM's probe, 40 out of 40 barrier-started pairs ended with **no database at all**. The winner reported success, and the loser's cleanup deleted its file.
- **Windows:** the cleanup's own `unlink` fails with `PermissionError` [WinError 32], because the loser's engine is never disposed on the failure path (`engine.dispose()` runs only on success, `:190`). So the winner's database survives by accident, and the loser stops with a raw `PermissionError` instead of the `ValueError` AC2 asks for (20 out of 20 pairs).
- The same missing dispose means a late failure in a **single, uncontended** initialization leaves a partial `mappings.db` behind on Windows. On Linux it leaves the `-wal` and `-shm` files. AC4's "still leaves no partial file behind" is therefore the target, not today's behaviour (Notes for the PO and PM, item 4).
- The #83 unit test `test_init_database_index_creation_idempotent` (`tests/unit/test_database.py:172-198`) patches `Path` in `database.py`, so the cleanup's `db_file.exists()` also returns `False`. The mock suppresses the very delete this story removes, and that is why the test passes.

## Acceptance Criteria

AC1 to AC5 are copied from the epic's Story 10.5 word for word. "AC precisions (story-level)" adds detail and does not change the epic text. AC6 to AC8 are story-level.

1. **AC1 — No deletion of a pre-existing DB:** on failure, `init_database` deletes `db_path` only if this call itself created the file. A database that existed before the call, or that another process created during it, is never deleted. The mechanism is chosen and documented in the story: create the file exclusively and track ownership, or take a lock on first-time creation, or both.
2. **AC2 — Clear failure for the loser:** the process that loses the race fails with the existing "Database already exists" `ValueError`, or a documented equivalent, not a generic initialization exception. The winner's database opens with `open_database` and its own passphrase, and its metadata (schema version, encryption parameters, passphrase canary) is intact.
3. **AC3 — Concurrency test:** a test runs two initializations of the same new `db_path` concurrently, in separate processes, repeated enough times to make the race likely (the story states the count). Each iteration passes only if exactly one initialization succeeds, the file exists, it opens with the winner's passphrase, and the loser failed as AC2 says. The test is deterministic in its pass criteria and uses a temporary directory per iteration.

### AC precisions (story-level)

- **AC1, the mechanism (pre-decided; Dev Notes "Fix Design"):** **create the file exclusively and track ownership.** `init_database` creates `db_path` with `os.open(db_path, O_CREAT | O_EXCL | O_WRONLY, 0o644)`, keeps that descriptor open until the call ends, and records its identity (`os.fstat`). On failure, it disposes its engine first, then deletes `db_path` and its `-wal`, `-shm` and `-journal` files only if `db_path` is still the file it created (`os.path.samestat`). The descriptor stays open so that, on POSIX, the identity cannot be reused by a new file; on Windows it also stops any other process from deleting or replacing the file during the call. No lock is taken (rejected alternatives in "Fix Design").
- **AC1, "another process created during it":** with an exclusive create, another process can create `db_path` during the call only after someone deleted this call's file (for example `init --force`, `init.py:92`, or a user). The identity check covers that case: the replacement is never deleted (test T6).
- **AC2, the loser's error:** the existing `ValueError`, with the existing message (`database.py:85-87`: "Database already exists at {db_path}. Use open_database() to open existing database."), raised in two places: the existing fast-path check, and the exclusive create's `FileExistsError` (chained with `from`, so a test can tell the two apart). It is raised before the `try`, so it is never wrapped. No new exception class, unless Lionel picks "carry on" in Q1.
- **AC2, "metadata intact":** the winner's database opens with `open_database` and the winner's passphrase. It holds exactly the four metadata keys, `schema_version` = `"1.0.0"` and `kdf_iterations` = `"100000"`, and the loser's passphrase is rejected ("Incorrect passphrase"). The tests check this in one helper, `_assert_winner_db` (Test Plan).
- **AC3, the count:** **20 iterations**, in two long-lived worker processes (`multiprocessing`, `spawn` context on every OS), lined up by a `Barrier(2)` before each iteration, each iteration in its own temporary directory. With a barrier start, the SM's probe on the unfixed code hit the race in 40 out of 40 iterations on Linux and 20 out of 20 on Windows. The race test is backed by a **deterministic** cross-process test (T9): three events order the two processes, so the loser always passes the fast-path check before the winner creates its file. Neither test sleeps or asserts on elapsed time. Timeouts exist only as hang guards: a timeout makes the iteration fail with a message; it is never the thing being tested.
- **AC4:** "without touching the file" is checked as an unchanged sha256 and `st_mtime_ns`, with no sidecar created. "Leaves no partial file behind" means no `db_path`, `-wal`, `-shm` or `-journal` file after a failure, for an exception raised at the schema step or at the metadata step, and for a `KeyboardInterrupt` at the metadata step. "Existing database tests stay green": every test in `tests/unit/test_database.py`, and every test under `tests/unit/` and `tests/integration/` that calls `init_database`. The exception is `test_init_database_index_creation_idempotent` (`:172-198`), which asserts the old path on purpose: it is replaced by T1, with a comment citing 10.5 AC1 and AC2 (Task 1.3).
- **AC5, G2:** QA re-runs T9 and T10 itself, reads the diff, and checks the CI evidence of AC6 (Task 7).

### Fix Design (pre-decided)

`init_database(db_path, passphrase)`, in this order:

1. **Validate the passphrase.** Unchanged (`:78-80`).
2. **Fast path.** Unchanged (`:82-87`): if `db_path` exists, raise the existing `ValueError`, and nothing is touched (AC4).
3. **Salt and key derivation.** Unchanged code (`:89-93`), and still **before** the file exists. The slow PBKDF2 step therefore never runs while a half-built file is visible to other processes.
4. **Exclusive create (new).** `fd = os.open(db_path, os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)`.
   - `FileExistsError` → `raise ValueError(<the message of step 2>) from exc`. Nothing is deleted (AC2). Raised outside the `try`, so it is never wrapped.
   - Any other `OSError` (missing directory, no permission) → wrapped as today: `Exception(f"Database initialization failed: {e}") from e`. Callers and test `:115` see the same type as today.
   - `created = os.fstat(fd)`. **Keep `fd` open until the call ends.** On POSIX the inode cannot be reused while it is open. On Windows the handle (no `FILE_SHARE_DELETE`) stops other processes from deleting or replacing the file; SQLite's own handles open alongside it (checked on Windows by the prototype).
   - Mode `0o644`: SQLite's own default for new files (`SQLITE_DEFAULT_FILE_PERMISSIONS`), so the on-disk permissions stay as today (the prototype checked this on both OSes). A tighter mode is out of scope.
5. **`try`:** the existing body, unchanged: engine, schema, PRAGMAs, indexes, metadata with its inner wrap, then `engine.dispose()`. Then `os.close(fd)`.
6. **`except BaseException as exc`** (new cleanup), in this order:
   1. **Dispose:** if the engine was created, `engine.dispose()`. This is new: without it the delete fails on Windows (WinError 32).
   2. **Identity:** `ours = os.path.samestat(created, os.stat(db_path))`, or `False` if `stat` raises `OSError`. The descriptor is still open here, so on POSIX the inode cannot have been reused.
   3. **Close** `fd` (Windows cannot delete a file this process still holds open).
   4. **Delete, only if `ours`:** `db_path`, then `db_path + "-wal"`, `"-shm"` and `"-journal"` if present (a missing file is fine). The first error stops this step, so a sidecar is never deleted while its main file stays. Sidecars go only with a main file that is this call's own: if the main file is someone else's, so are its sidecars, and deleting its `-wal` would lose that database's data.
   5. **Cleanup errors:** steps 1 and 4 each sit in their own `try`/`except Exception as err`. A failure is logged once, as `logger.warning("database_init_cleanup_failed", step="dispose" or "delete", error_type=type(err).__name__)`, and never replaces `exc`. No path, no passphrase and no message text go in the log (coding standards 19.1, rule 3). Step 3 runs whatever happens in steps 1 and 2.
   6. **Re-raise:** an `Exception` is wrapped exactly as today (`Exception(f"Database initialization failed: {exc}") from exc`); a `BaseException` that is not an `Exception` (`KeyboardInterrupt`, `SystemExit`) is re-raised unchanged.

   Shape, for orientation only (the dev writes the real code):

   ```python
   fd = _create_exclusively(db_path)      # step 4: ValueError on FileExistsError
   created = os.fstat(fd)
   engine = None
   try:
       ...                                 # step 5: today's body, unchanged
       engine.dispose()
   except BaseException as exc:
       _dispose_quietly(engine)            # 6.1
       ours = _same_file(created, db_path) # 6.2
       os.close(fd); fd = -1               # 6.3
       if ours:
           _delete_quietly(db_path)        # 6.4, 6.5
       if isinstance(exc, Exception):
           raise Exception(f"Database initialization failed: {exc}") from exc
       raise
   finally:
       if fd >= 0:
           os.close(fd)
   ```

7. `open_database` is not touched. The callers are not touched (unless Q1 is "carry on").

**Rejected alternatives (AC1 asks the story to document the choice):**
- **A lock on first-time creation** (a lock file, `fcntl` or `msvcrt`): platform-specific code; a lock file left behind by a crash blocks later runs; and a lock alone does not say which file is this call's. Not needed for AC1–AC4.
- **Build in a temporary file, then publish it atomically without overwriting:** other processes would never see a half-built file, but POSIX has no portable "rename without overwrite" (it needs `os.link`, which FAT/exFAT drives and some network shares lack); the WAL files must be checkpointed before publishing; and a crash leaves a temporary file. Too much for a LOW, 0.5-week story.

**Known residuals (documented, not fixed; outside AC1–AC4):**
- A caller that checks `exists()` first (`ensure_database`, the GUI workers) can arrive while the winner is still writing its metadata. It then skips `init_database`, and `open_database` may fail with "Encryption salt missing - database may be corrupted" (`CorruptedDatabaseError`), if it opens inside that window, which lasts less than a second. `process` and `batch` open the database only after detection, which loads the NLP model (`core/document_processor.py:865-868`), so the window is normally over by then. Nothing is deleted either way. Q1 is related.
- `init --force` deletes the main file only, not its `-wal` and `-shm` (`init.py:92`). Unchanged.
- The GUI workers' `"12" in error_str` heuristic (`detection_worker.py:109`, `processing_worker.py:102`) would show the "Database already exists" message as a passphrase-length error if the database path contains "12". This is pre-existing and out of scope, noted for the PM (Notes, item 7).
