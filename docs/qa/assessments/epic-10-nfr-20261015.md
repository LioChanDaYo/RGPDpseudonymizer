### 2.2 The flaky-test lesson (10.11 MW-001)

- **What happened.** Four new 10.11 tests (T9[other_last_name], T9[one_word_name], T9b[last_name], T9b[both]) typed a value built from a stored part that a random draw had generated. When the library drew one of its four two-word last names (about 4 in 500), the tests failed. QA estimated about one CI run in eight would go red (four exposed draws per leg, four legs). QA's own gate commit `26ebcb0` went red on Windows, attempt 1 (CI `38730457990`, T9[other_last_name], "no message shown").
- **Why it mattered.** The flake was not test noise. It was a product defect (MW-001: a two-word stored part defeated the Q2 check and the Q-D example) that the tests reached only by chance. QA did not re-run: the failure was not infrastructure. The stories allow a re-run for an infrastructure failure only, and G6 only for the known macOS flake. The next QA commit, `603cb7c`, was green "by the draw, not by a fix" (gate `first_review.evidence.ci.qa_commit_603cb7c`). QA raised the gate from CONCERNS to FAIL anyway.
- **How it was fixed.** The product defect was fixed under Lionel's Q-G. The tests now store fixed rows and read no random value that could change an outcome (AC20). QA ran the 39 amendment tests 20 times in a row and the full suite three times, all green, and all four CI legs passed.
- **Lessons for Epic 9:**
  1. A red CI run that the next run does not repeat is still evidence. Look for the input that varied before calling it a flake or re-running it.
  2. A test must not assert on a value drawn at random when the value's shape can change the outcome. Fix or seed the value, and keep one test per shape.
  3. A green run after a red one is not a fix. Only a cause found and removed is.
  4. A loop of 20 local runs of the new tests is a cheap guard. It belongs in the dev checklist for any test that touches the pseudonym library.

### 2.3 Settings-file isolation (10.10 Task 1.0)

- **The problem.** Local GUI test runs had been overwriting the user's real settings file (`.gdpr-pseudo.yaml` in the home folder). Patching `save_gui_config` was not enough: building the main window writes the file, and five modules and the main window hold their own reference to the function (10.10 story, Test Plan).
- **The fix.** An autouse fixture, `_isolate_gui_config`, in `tests/unit/gui/conftest.py:160-166` and `tests/integration/gui/conftest.py:120`, points `gdpr_pseudonymizer.gui.config._config_path` at `tmp_path`. It went in as its own test-only commit, `b2ef449`, byte-identical to the story's text (10.10 gate `conftest_commit`).
- **QA's own runs went further.** From 10.7 on, QA also pointed `USERPROFILE` and `HOME` at a scratch folder, used a scratch working folder and a plugin patching `_config_path`. QA checked the user's file before and after each run: it was never opened, with the same mtime and hash (10.7 gate `settings_isolation`, 10.9, 10.10, 10.11).
- **Complete today.** At `b2042c7`, no test outside `tests/unit/gui/` and `tests/integration/gui/` builds the GUI or touches its config: a grep for `qtbot`, `MainWindow`, `save_gui_config` and `gui.config` in the rest of `tests/` is empty.
- **Residual (low, new at close-out).** A future GUI test placed outside those two folders would not be isolated. Moving the fixture to `tests/conftest.py`, or adding a guard test that fails when a GUI test sits outside them, would close it for good. Scripts and probes that run outside pytest still need the manual `USERPROFILE`/`HOME` redirection.
